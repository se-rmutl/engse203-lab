1.4 แต่ละชั้นรู้อะไรและไม่รู้อะไร

ชั้นรู้จักไม่รู้จักไฟล์
Middlewareคำขอทุกคำขอไม่รู้ว่าเป็น route ไหนapp.js
Routemethod + pathไม่รู้ว่าข้อมูลเก็บที่ไหนroutes/
Controllerreq · res · status codeไม่รู้จัก SQLcontrollers/
ServiceSQL · โครงสร้างตารางไม่รู้จัก req/resservices/
🟩 ช่องขวาสำคัญกว่าช่องซ้าย

สิ่งที่แต่ละชั้น ไม่รู้ คือสิ่งที่ทำให้เปลี่ยนชั้นอื่นได้โดยไม่กระทบกัน

เพราะ service ไม่รู้จัก req/res → เปลี่ยนจากไฟล์ JSON เป็นฐานข้อมูลได้โดย controller ไม่ต้องแก้
เพราะ controller ไม่รู้จัก SQL → เปลี่ยนจาก SQLite เป็น MongoDB ในสัปดาห์หน้าก็ยังไม่ต้องแก้

🟥 สัญญาณว่ากำลังทำผิดทาง

ถ้าเขียนไปแล้วรู้สึกว่าต้องแก้ controller ด้วย — ให้หยุดแล้วตรวจก่อน
แปลว่า signature ของ service เปลี่ยนไปแล้ว ซึ่งผิดข้อตกลงของสัปดาห์นี้
เช่น เปลี่ยนให้คืน { rows: [...] } แทน array ตรง ๆ หรือเปลี่ยนเป็น async

บทที่ 2 · กลุ่มที่ 1

node:sqlite — เปิดฐานข้อมูลจากโค้ด

เวลาอ่าน ≈ 11 นาที

node:sqlite

โมดูลที่มากับ Node.js 22 อยู่แล้ว ใช้เปิดและสั่งงานฐานข้อมูล SQLite ได้โดย ไม่ต้อง npm install อะไรเลย

2.1 เปิดฐานข้อมูล

import { DatabaseSync } from 'node:sqlite';

const db = new DatabaseSync('./data/campus.db');
db.exec('PRAGMA foreign_keys = ON');   // ⚠ ต้องสั่งทุกครั้ง
🟥 ลืม PRAGMA foreign_keys = ON = constraint ไม่ทำงานเลย

เรื่องนี้ย้ำมาตั้งแต่สัปดาห์ที่แล้ว และยังสำคัญตรงนี้ — ต้องสั่งทุกครั้งที่เปิดฐานข้อมูล ไม่ใช่สั่งครั้งเดียวแล้วจำไปตลอด
ถ้าลืม จะใส่ requester_id มั่วเข้าไปได้โดยไม่มี error บอก

2.2 สามวิธีสั่งงานฐานข้อมูล

คำสั่งใช้เมื่อคืนอะไร
db.exec(sql)รัน SQL ที่ไม่ต้องการผลลัพธ์ · หลายคำสั่งพร้อมกันไม่คืนอะไร
db.prepare(sql).all(...)ต้องการหลายแถวarray ของ object
db.prepare(sql).get(...)ต้องการแถวเดียวobject หรือ undefined
db.prepare(sql).run(...)INSERT · UPDATE · DELETE{ changes, lastInsertRowid }
// หลายแถว
const rows = db.prepare('SELECT * FROM requests').all();

// แถวเดียว
const one = db.prepare('SELECT * FROM requests WHERE id = ?').get('REQ-001');

// เปลี่ยนแปลงข้อมูล
const result = db.prepare('DELETE FROM requests WHERE id = ?').run('REQ-006');
console.log(result.changes);   // ลบไปกี่แถว — ใช้เช็คว่าเจอหรือไม่
🟨 result.changes ใช้แทนการเช็คว่าพบหรือไม่

ถ้า changes === 0 แปลว่าไม่มีแถวไหนตรงเงื่อนไข — ใช้ตัดสินว่าควรคืน null เพื่อให้ controller ตอบ 404
ไม่ต้อง SELECT เช็คก่อนแล้วค่อย UPDATE — สั่งครั้งเดียวแล้วดู changes พอ

2.3 ทำไมชื่อ DatabaseSync

Sync (synchronous)

ทำงานเสร็จทันที ไม่ต้อง await · ต่างจาก fetch() ที่ต้องรอ

🟩 ทายก่อนอ่านต่อ

ตอน Week 07 เราเรียก API ต้องใช้ await ทุกครั้ง — ทำไมเรียกฐานข้อมูลไม่ต้อง

เฉลย

เพราะ ไฟล์ฐานข้อมูลอยู่ในเครื่องเดียวกัน — อ่านจากดิสก์เสร็จในเสี้ยววินาที ไม่ต้องรอ

ส่วน API ของ Week 07 อยู่คนละโปรแกรม (และอาจคนละเครื่อง) ต้องส่งข้อมูลผ่านเครือข่าย จึงต้องรอ
สัปดาห์หน้าเราจะเจอ MongoDB ที่อยู่คนละเครื่องจริง ๆ แล้วจะได้เห็นว่าทำไมต้อง async

🟨 ผลดีที่ตามมา — controller ไม่ต้องแก้

เพราะ service ยังเป็น sync เหมือนเดิม · ถ้าเปลี่ยนเป็น async ทุกฟังก์ชัน controller จะต้องเติม await ทุกบรรทัด
นี่คือเหตุผลที่สัปดาห์นี้แก้ไฟล์เดียวได้จริง

🟥 จะเห็น ExperimentalWarning

node:sqlite ยังเป็นฟีเจอร์ทดลองใน Node 22 · รันแล้วจะขึ้นคำเตือนทุกครั้ง
ไม่ใช่ error — ซ่อนได้ด้วย node --disable-warning=ExperimentalWarning ซึ่งใส่ไว้ใน package.json ให้แล้ว

สรุปบทที่ 2
  • node:sqlite มากับ Node 22 — ไม่ต้องติดตั้งอะไรเพิ่ม
  • สั่งงาน 4 แบบ — exec · all (หลายแถว) · get (แถวเดียว) · run (เปลี่ยนข้อมูล)
  • result.changes บอกว่ากระทบกี่แถว — ใช้เช็คว่าพบหรือไม่
  • เป็น sync เพราะไฟล์อยู่ในเครื่อง — controller จึงไม่ต้องแก้
  • อย่าลืม PRAGMA foreign_keys = ON ทุกครั้งที่เปิด

3.1 วิธีแก้ — อ้างจากตำแหน่งไฟล์

import path from 'node:path';
import { fileURLToPath } from 'node:url';

// ตำแหน่งของ "ไฟล์นี้" ไม่ใช่ตำแหน่งที่รันคำสั่ง
const HERE = path.dirname(fileURLToPath(import.meta.url));
const API_ROOT = path.resolve(HERE, '../..');
const DB_FILE = process.env.DB_FILE ?? path.join(API_ROOT, 'data', 'campus.db');
ส่วนทำอะไร
import.meta.urlURL ของไฟล์นี้ เช่น file:///.../services/requestService.js
fileURLToPath()แปลง URL เป็น path ปกติ
path.dirname()ตัดชื่อไฟล์ออก เหลือแต่โฟลเดอร์
path.resolve(HERE, '../..')ถอยขึ้นไป 2 ชั้น (services/ → src/ → api/)
process.env.DB_FILE ??ให้ตั้งค่าจากภายนอกได้ (บทเรียนจาก Week 07)
🟪 เทียบกับของที่คุ้น

./data เหมือนบอกว่า "ร้านข้าง ๆ" — ขึ้นกับว่าคุณยืนอยู่ตรงไหน คำตอบเปลี่ยนไปเรื่อย
path.join(API_ROOT, 'data') เหมือนบอกที่อยู่เต็ม — ยืนตรงไหนก็หาเจอที่เดียวกัน

🟥 ทำไมปัญหานี้หายาก

SQLite ไม่บ่นเมื่อไฟล์ไม่มี — มันสร้างฐานข้อมูลเปล่าให้เลย
error ที่ได้จึงเป็น no such table: requests ซึ่งทำให้คิดว่า "ลืมสร้างตาราง" ทั้งที่จริง ๆ คือ เปิดไฟล์ผิดตัว

บทที่ 4 · กลุ่มที่ 2

อ่านข้อมูล — เอา JOIN จากสัปดาห์ที่แล้วมาใช้

เวลาอ่าน ≈ 12 นาที

ตรงนี้คือจุดที่ query ที่เขียนสัปดาห์ที่แล้วกลายเป็นโค้ด

4.1 ปัญหาที่ต้องแก้

ฐานข้อมูลเก็บfrontend ต้องการ
ผู้แจ้งrequester_id: 1requesterName: "สมชาย ใจดี"
ประเภทrequest_typerequestType

สองรูปแบบนี้ไม่ตรงกัน — และ เราจะไม่แก้ frontend เพราะสัญญาไว้แล้ว

🟩 ทางออก — ใช้ JOIN + AS ที่เรียนไปแล้ว 
const SELECT_SHAPE = `
  SELECT r.id,
         u.name          AS requesterName,
         r.request_type  AS requestType,
         r.location,
         r.details,
         r.priority,
         r.status
  FROM requests r
  JOIN users u ON u.id = r.requester_id`;

เก็บไว้เป็นค่าคงที่ตัวเดียว แล้วเอาไปต่อ WHERE ตามต้องการ — ไม่ต้องเขียน JOIN ซ้ำในทุกฟังก์ชัน

4.2 findAll()

export function findAll({ status } = {}) {
  return status
    ? db.prepare(`${SELECT_SHAPE} WHERE r.status = ? ORDER BY r.id`).all(status)
    : db.prepare(`${SELECT_SHAPE} ORDER BY r.id`).all();
}
🟥 สังเกตให้ดี — ค่า status ไม่ได้ต่อเข้าไปใน SQL

${SELECT_SHAPE} ต่อได้เพราะเป็นโค้ดของเราเอง ที่เขียนไว้ตายตัว
แต่ status มาจากผู้ใช้ จึงต้องส่งผ่าน ? เท่านั้น — บทที่ 7 จะอธิบายว่าทำไม

4.3 findById()

export function findById(id) {
  return db.prepare(`${SELECT_SHAPE} WHERE r.id = ?`).get(id) ?? null;
}
🟥 ต้องมี ?? null

.get() คืน undefined เมื่อไม่พบ · แต่ Week 07 เราสัญญาไว้ว่าจะคืน null
ถ้าลืมใส่ ?? null controller จะยังตอบ 404 ได้ (เพราะ undefined เป็น falsy) แต่ผิดสัญญาที่เขียนไว้ใน API contract และอาจพังตอนเอาไปใช้ที่อื่น

🟩 ทายก่อนอ่านต่อ

ถ้าใช้ LEFT JOIN แทน JOIN ใน SELECT_SHAPE — จะต่างกันอย่างไร

เฉลย

ผลลัพธ์เหมือนกันในกรณีปกติ เพราะ requester_id มี NOT NULL และ Foreign Key บังคับว่าต้องมีอยู่จริง — คำร้องทุกใบจึงจับคู่ได้เสมอ

แต่ JOIN ธรรมดาดีกว่าตรงนี้ — ถ้าวันหนึ่งข้อมูลเสียจนมีคำร้องที่ชี้ไปหาคนที่ไม่มีจริง JOIN จะทำให้รายการนั้นหายไป ซึ่งสังเกตง่ายกว่าการเห็น requesterName: null ที่อาจหลุดไปแสดงบนหน้าจอ

สรุปบทที่ 4
  • ใช้ JOIN + AS แปลงรูปแบบฐานข้อมูลให้ตรงกับที่ frontend ต้องการ
  • เก็บ SELECT_SHAPE ไว้ตัวเดียว ไม่เขียน JOIN ซ้ำ
  • ค่าจากผู้ใช้ส่งผ่าน ? เสมอ ไม่ต่อเข้า SQL
  • .get() ต้องมี ?? null เพื่อรักษาสัญญาจาก Week 07

บทที่ 5 · กลุ่มที่ 2

แปลงชื่อเป็น id — หน้าที่ของ Service

เวลาอ่าน ≈ 12 นาที · บทที่สำคัญที่สุดของสัปดาห์

สัปดาห์ที่แล้วเราสรุปไว้ว่า "โครงในฐานข้อมูลไม่จำเป็นต้องเหมือนรูปแบบที่ API ส่งออก นี่คือหน้าที่ของชั้น service"

บทนี้คือตอนที่ประโยคนั้นกลายเป็นโค้ดจริง

5.1 ปัญหา

frontend ส่งมาแบบนี้ (ไม่เปลี่ยนตั้งแต่ Week 05)

{ "requesterName": "สมชาย ใจดี", "requestType": "แจ้งซ่อม", ... }

แต่ตาราง requests เก็บ requester_id เป็นตัวเลข

🟩 ทายก่อนอ่านต่อ

มี 3 ทางเลือก — ทางไหนดีที่สุด และทำไมอีกสองทางไม่ดี

  1. ให้ frontend ส่ง requester_id มาแทน
  2. เก็บ requesterName เป็นคอลัมน์ในตาราง requests ด้วย
  3. ให้ service หา id จากชื่อเอง
เฉลย
ทางเลือกปัญหา
① frontend ส่ง idต้องแก้ frontend — เสียคำสัญญาที่ให้ไว้ตั้งแต่ Week 05 · และผู้ใช้ไม่รู้จัก id อยู่แล้ว ต้องทำหน้าจอเลือกคนเพิ่ม
② เก็บชื่อซ้ำด้วยกลับไปมีข้อมูลซ้ำ — เสียบทเรียนทั้งหมดของสัปดาห์ที่แล้ว · เปลี่ยนชื่อทีต้องแก้หลายที่อีก
③ service แปลงให้ไม่มีใครเสียอะไร — frontend เหมือนเดิม ฐานข้อมูลไม่ซ้ำ

5.2 resolveUserId()

/** แปลงชื่อผู้แจ้งเป็น id — ถ้ายังไม่มีในระบบก็สร้างให้ */
function resolveUserId(name) {
  const found = db.prepare('SELECT id FROM users WHERE name = ?').get(name);
  if (found) return found.id;

  const slug = Date.now().toString(36);
  return db.prepare('INSERT INTO users (name, department, email) VALUES (?, ?, ?)')
           .run(name, 'ไม่ระบุ', `user-${slug}@rmutl.ac.th`).lastInsertRowid;
}
บรรทัดทำอะไร
SELECT id ... WHERE name = ?หาว่ามีคนชื่อนี้อยู่แล้วไหม
if (found) return found.idมีแล้ว — ใช้ id เดิม ไม่สร้างซ้ำ
INSERT INTO users ...ยังไม่มี — สร้างให้
lastInsertRowidid ที่ฐานข้อมูลเพิ่งสร้าง (จาก AUTOINCREMENT)
🟨 ทำไม email ต้องมี slug

เพราะ users.email มี UNIQUE — ถ้าใส่ค่าเดิมทุกครั้งจะชนกันตั้งแต่คนที่สอง
Date.now().toString(36) ให้ค่าที่ไม่ซ้ำโดยไม่ต้องคิดมาก · นี่คือทางออกชั่วคราวของวิชาเรียน — ระบบจริงต้องให้ผู้ใช้กรอกอีเมลเอง

5.3 create()

export function create(input) {
  const id = nextId();
  db.prepare(
    `INSERT INTO requests (id, requester_id, request_type, location, details, priority)
     VALUES (?, ?, ?, ?, ?, ?)`
  ).run(
    id,
    resolveUserId(input.requesterName.trim()),   // ← แปลงตรงนี้
    input.requestType,
    input.location.trim(),
    input.details.trim(),
    input.priority ?? 'normal'
  );
  return findById(id);   // คืนรูปแบบที่ frontend ต้องการ
}
🟩 สังเกตความสมมาตร

ขาเข้า — resolveUserId() แปลง ชื่อ → id ก่อนเก็บ
ขาออก — JOIN แปลง id → ชื่อ ก่อนส่งกลับ

service ทำหน้าที่เป็นล่ามระหว่างสองภาษา — ภาษาของฐานข้อมูล (ไม่ซ้ำ ประหยัด) กับภาษาของผู้ใช้ (อ่านเข้าใจ)

5.4 nextId() — สร้างรหัสถัดไป

function nextId() {
  const row = db.prepare(
    "SELECT id FROM requests WHERE id LIKE 'REQ-%' ORDER BY id DESC LIMIT 1"
  ).get();
  const n = row ? Number(String(row.id).replace('REQ-', '')) + 1 : 1;
  return `REQ-${String(n).padStart(3, '0')}`;
}
🟥 วิธีนี้ใช้ได้ในวิชาเรียน แต่ไม่ปลอดภัยในระบบจริง

ถ้ามีคนสร้างคำร้องพร้อมกัน ทั้งสองอาจอ่านได้ REQ-005 แล้วสร้าง REQ-006 ทั้งคู่ — ชนกัน
Primary Key จะปฏิเสธคนที่สอง จึงไม่ถึงกับข้อมูลเสีย แต่ผู้ใช้จะเจอ error โดยไม่ผิดอะไร
ระบบจริงใช้ AUTOINCREMENT หรือ UUID · เราใช้รหัสที่คนอ่านได้เพราะเป็นข้อกำหนดของโจทย์ตั้งแต่ Week 05

สรุปบทที่ 5
  • frontend ส่งชื่อมา แต่ฐานข้อมูลเก็บ id — service เป็นตัวแปลง
  • resolveUserId() หา id จากชื่อ · ไม่มีก็สร้างใหม่
  • lastInsertRowid คือ id ที่ฐานข้อมูลเพิ่งสร้างให้
  • ขาเข้าแปลงชื่อเป็น id · ขาออกแปลง id เป็นชื่อ — สมมาตรกัน
  • create() จบด้วย findById() เพื่อคืนรูปแบบที่ frontend ต้องการ

บทที่ 6 · กลุ่มที่ 2

เขียนข้อมูล — INSERT · UPDATE · DELETE

เวลาอ่าน ≈ 10 นาที

สองฟังก์ชันที่เหลือตรงไปตรงมากว่า create() เพราะไม่ต้องแปลงชื่อ

6.1 updateStatus()

export function updateStatus(id, status) {
  const result = db.prepare('UPDATE requests SET status = ? WHERE id = ?')
                   .run(status, id);
  return result.changes ? findById(id) : null;
}
🟨 result.changes บอกว่าพบหรือไม่

ถ้าไม่มีแถวไหนตรง changes จะเป็น 0 → คืน null → controller ตอบ 404
ไม่ต้อง SELECT เช็คก่อน — สั่ง UPDATE ครั้งเดียวแล้วดูผลพอ · ประหยัดกว่าและไม่มีช่องว่างระหว่างสองคำสั่ง

🟥 ลำดับของ ? ต้องตรงกับลำดับใน SQL 
-- SQL: SET status = ?  WHERE id = ?
.run(status, id)   // ✅ ถูก — status มาก่อน id
.run(id, status)   // ❌ ผิด — สลับกัน

ถ้าสลับ จะไม่มี error แต่ไม่มีแถวไหนตรงเงื่อนไข → คืน null → ได้ 404 ทั้งที่คำร้องมีอยู่จริง
เป็นบั๊กที่หาสาเหตุยาก เพราะดูเหมือนแค่ "ไม่พบข้อมูล"

6.2 remove()

export function remove(id) {
  const target = findById(id);      // ① หาก่อน
  if (!target) return null;          // ② ไม่พบ → null
  db.prepare('DELETE FROM requests WHERE id = ?').run(id);
  return target;                     // ③ คืนของที่ลบ
}
🟩 ทายก่อนอ่านต่อ

updateStatus ใช้ result.changes เช็ค แต่ remove กลับ findById ก่อน — ทำไมต่างกัน

เฉลย

เพราะ Week 07 กำหนดว่า remove() ต้องคืนรายการที่ลบ — ซึ่งต้องอ่านมาก่อนลบ ไม่งั้นข้อมูลหายไปแล้ว

ส่วน updateStatus() คืนรายการหลังแก้ จึงอ่านทีหลังได้ · signature กำหนดวิธีเขียน ไม่ใช่เราเลือกตามใจ

6.3 ⭐ Transaction — ทำให้สำเร็จหรือล้มเหลวพร้อมกัน

Transaction

กลุ่มคำสั่งที่ต้องสำเร็จทั้งหมดหรือไม่สำเร็จเลย · ถ้าคำสั่งใดพัง ระบบจะย้อนทุกอย่างกลับเหมือนไม่เคยทำ

🟩 ปัญหาที่ซ่อนอยู่ใน create()

ถ้า resolveUserId() สร้าง user ใหม่สำเร็จ แต่ INSERT INTO requests ล้มเหลว (เช่น request_type ผิด CHECK) — จะเกิดอะไรขึ้น

เฉลย

จะเหลือ user ที่ไม่มีคำร้องเลยค้างอยู่ในฐานข้อมูล — เป็นขยะที่ไม่มีใครใช้และไม่มีใครรู้ว่ามาจากไหน

ยิ่งเกิดบ่อยยิ่งสะสม · และตาราง users จะมีคนปลอมปนกับคนจริง

export function create(input) {
  const id = nextId();
  db.exec('BEGIN');               // ① เริ่ม transaction
  try {
    const requesterId = resolveUserId(input.requesterName.trim());
    db.prepare(`INSERT INTO requests (...) VALUES (...)`).run(...);
    db.exec('COMMIT');            // ② สำเร็จทั้งคู่ → ยืนยัน
  } catch (err) {
    db.exec('ROLLBACK');          // ③ พัง → ย้อนกลับทั้งหมด
    throw err;
  }
  return findById(id);
}
🟪 เทียบกับของที่คุ้น

เหมือนการโอนเงิน — หักจากบัญชีหนึ่งแล้วเพิ่มอีกบัญชีหนึ่ง · ถ้าทำได้แค่ครึ่งเดียวคือหายนะ
transaction รับประกันว่า จะไม่มีสถานะครึ่ง ๆ กลาง ๆ

สรุปบทที่ 6
  • result.changes บอกว่ากระทบกี่แถว — ใช้แทนการ SELECT เช็คก่อน
  • ลำดับของ ? ต้องตรงกับใน SQL — สลับแล้วไม่มี error แต่ผลผิด
  • remove() ต้อง findById ก่อนลบ เพราะ signature กำหนดให้คืนของที่ลบ
  • ⭐ transaction ทำให้หลายคำสั่ง สำเร็จทั้งหมดหรือไม่สำเร็จเลย

บทที่ 7 · กลุ่มที่ 3 🏠 ทำที่บ้าน

Parameterized Query และ SQL Injection

เวลาอ่าน ≈ 12 นาที · เรื่องความปลอดภัยที่ต้องรู้จริง

ถึงตอนนี้เราใช้ ? มาตลอดโดยยังไม่ได้อธิบายว่าทำไม — บทนี้คือคำตอบ

7.1 ถ้าต่อ string เข้า SQL จะเกิดอะไร

// ❌ อันตราย — ต่อค่าจากผู้ใช้เข้า SQL โดยตรง
const rows = db.prepare(
  `SELECT * FROM requests WHERE status = '${status}'`
).all();

ถ้าผู้ใช้ส่ง status มาเป็น

x' OR '1'='1

SQL ที่ได้จริงจะกลายเป็น

SELECT * FROM requests WHERE status = 'x' OR '1'='1'
🟥 '1'='1' เป็นจริงเสมอ

เงื่อนไขทั้งหมดจึงเป็นจริงทุกแถว — คืนข้อมูลทั้งตารางออกไป แม้ผู้ใช้จะไม่มีสิทธิ์เห็น
และถ้าส่ง '; DROP TABLE requests; -- มา ตารางอาจหายทั้งตาราง

SQL Injection

การโจมตีโดยแทรกคำสั่ง SQL เข้าไปในค่าที่ผู้ใช้กรอก · เป็นช่องโหว่ที่พบบ่อยที่สุดอันดับต้น ๆ ของเว็บแอปพลิเคชันมานานหลายสิบปี

7.2 Parameterized query แก้ปัญหาอย่างไร

// ✅ ปลอดภัย
const rows = db.prepare(
  'SELECT * FROM requests WHERE status = ?'
).all(status);

? ไม่ใช่การ "แทนที่ข้อความ" — ฐานข้อมูลแยกคำสั่งกับข้อมูลออกจากกันตั้งแต่ต้น

ต่อ stringparameterized
ฐานข้อมูลได้รับSQL ก้อนเดียวที่ปนค่าผู้ใช้โครง SQL + ค่า แยกกัน
ค่า x' OR '1'='1ถูกตีความเป็นคำสั่งถูกตีความเป็นข้อความธรรมดา
ผลลัพธ์คืนทั้งตารางคืน 0 แถว
🟪 เทียบกับของที่คุ้น

ต่อ string = เขียนจดหมายแล้วให้คนอื่นเติมข้อความลงกลางประโยค — เขาเติมประโยคใหม่แทรกเข้ามาได้
parameterized = มีแบบฟอร์มที่เว้นช่องไว้ — เขากรอกได้แค่ในช่อง จะเขียนล้นออกมาเป็นคำสั่งไม่ได้

7.3 ทดลองเอง (CP31)

ยิงคำสั่งเหล่านี้ใส่ API ของตัวเองแล้วดูผล

ยิงอะไรต้องได้
GET /api/requests?status=x' OR '1'='10 รายการ
GET /api/requests?status='; DROP TABLE requests; --0 รายการ และตารางยังอยู่
GET /api/requests?status=pending' OR status='completed0 รายการ
🟨 ทำไมทดสอบเองสำคัญ

เพราะ โค้ดที่ปลอดภัยกับโค้ดที่ไม่ปลอดภัย หน้าตาต่างกันแค่นิดเดียว — ใช้ ? กับใช้ ${}
การได้เห็นด้วยตาว่าอันหนึ่งกันได้ อีกอันหลุด จะจำได้นานกว่าการอ่าน

7.4 สิ่งที่ ? ใช้แทนไม่ได้

// ❌ ใช้ ? แทนชื่อคอลัมน์หรือชื่อตารางไม่ได้
db.prepare('SELECT * FROM requests ORDER BY ?').all(sortBy);

? ใช้แทนได้เฉพาะ ค่า ไม่ใช่ โครงสร้างของคำสั่ง

🟩 ถ้าจำเป็นต้องให้ผู้ใช้เลือกคอลัมน์เรียง 
// ตรวจกับรายการที่อนุญาตก่อนเสมอ (allowlist)
const ALLOWED = ['id', 'status', 'priority', 'created_at'];
const col = ALLOWED.includes(sortBy) ? sortBy : 'id';
db.prepare(`SELECT * FROM requests ORDER BY ${col}`).all();

หลักการ — ถ้าต้องต่อ string จริง ๆ ให้ต่อได้เฉพาะค่าที่เราอนุญาตไว้ล่วงหน้า ไม่ใช่ค่าที่ผู้ใช้ส่งมาตรง ๆ

สรุปบทที่ 7
  • ต่อ string เข้า SQL = เปิดช่องให้แทรกคำสั่ง (SQL injection)
  • ? ทำให้ฐานข้อมูลแยกคำสั่งกับข้อมูลออกจากกัน
  • ค่าที่แทรกมาจะถูกมองเป็นข้อความธรรมดา ไม่ใช่คำสั่ง
  • ? ใช้แทนได้เฉพาะค่า ไม่ใช่ชื่อคอลัมน์หรือตาราง
  • ถ้าต้องต่อ string ให้ใช้ allowlist เท่านั้น

จัดการ Error จากฐานข้อมูล

เวลาอ่าน ≈ 9 นาที

ฐานข้อมูลมี constraint ที่จะปฏิเสธข้อมูลผิด — คำถามคือ เมื่อถูกปฏิเสธแล้ว ผู้ใช้ควรเห็นอะไร

8.1 error ที่อาจเกิดจากฐานข้อมูล

ข้อความ errorเกิดเมื่อใครผิดควรตอบ
FOREIGN KEY constraint failedชี้ไปหาแถวที่ไม่มีจริงผู้ใช้400
CHECK constraint failedค่านอกรายการที่กำหนดผู้ใช้400
UNIQUE constraint failedค่าซ้ำกับที่มีอยู่ผู้ใช้409 หรือ 400
NOT NULL constraint failedไม่ได้ใส่ค่าที่จำเป็นผู้ใช้400
no such tableฐานข้อมูลยังไม่ถูกสร้างเซิร์ฟเวอร์500
🟩 ทายก่อนอ่านต่อ

ถ้าไม่จัดการอะไรเลย error จากฐานข้อมูลจะไปจบที่ errorHandler ของ Week 06 ซึ่งตอบ 500 ทั้งหมด — มีอะไรไม่ดี

เฉลย

500 แปลว่า "เซิร์ฟเวอร์ผิด" — แต่กรณีเหล่านี้ส่วนใหญ่ ผู้ใช้ส่งข้อมูลผิดมาเอง

ผลที่ตามมา — ① ผู้ใช้ไม่รู้ว่าต้องแก้อะไร เพราะ 500 บอกแค่ "ระบบพัง" · ② ทีมจะเห็น 500 เยอะในระบบเฝ้าระวังแล้วตกใจ ทั้งที่ระบบปกติดี

8.2 แปลง error ให้เป็น status ที่เหมาะสม

// ใน service — จับ error จากฐานข้อมูลแล้วใส่ status ให้
import { AppError } from '../middleware/errorHandler.js';

function toAppError(err) {
  const m = err.message ?? '';
  if (m.includes('FOREIGN KEY'))  return new AppError('อ้างถึงข้อมูลที่ไม่มีอยู่จริง', 400);
  if (m.includes('CHECK'))        return new AppError('ค่าที่ส่งมาไม่อยู่ในรายการที่กำหนด', 400);
  if (m.includes('UNIQUE'))       return new AppError('ข้อมูลนี้มีอยู่แล้วในระบบ', 409);
  return err;   // error อื่นปล่อยผ่าน → errorHandler ตอบ 500
}
🟨 ใช้ AppError ที่ทำไว้ตั้งแต่ Week 07

ตอนนั้นเป็น Challenge ที่หลายคนข้าม — ตอนนี้ได้ใช้จริงแล้ว
errorHandler จะอ่าน err.status แล้วตอบตามนั้น · ไม่ต้องแก้ errorHandler เลย

🟥 อย่าส่งข้อความ error ของฐานข้อมูลตรง ๆ ให้ผู้ใช้

FOREIGN KEY constraint failed บอกโครงสร้างภายในของระบบ — ผู้ใช้ทั่วไปไม่เข้าใจ และคนไม่หวังดีจะได้ข้อมูลไปหาช่องโหว่
แปลเป็นภาษาคนเสมอ — หลักการเดียวกับ apiClient ที่ทำใน Week 07 บทที่ 7

สรุปบทที่ 8
  • constraint ส่วนใหญ่พังเพราะผู้ใช้ส่งข้อมูลผิด — ควรตอบ 4xx ไม่ใช่ 500
  • ใช้ AppError จาก Week 07 กำหนด status เอง
  • errorHandler ไม่ต้องแก้ — มันอ่าน err.status อยู่แล้ว
  • แปลข้อความ error เป็นภาษาคน ไม่ส่งของฐานข้อมูลตรง ๆ

9.1 ทดสอบกับฐานข้อมูลจริง (CP33)

test('คืน requesterName ไม่ใช่ requester_id', async () => {
  const r = await request(app).get('/api/requests');
  assert.ok('requesterName' in r.body[0]);
  assert.ok(!('requester_id' in r.body[0]));

test('SQL injection ผ่าน ?status= ไม่หลุด', async () => {
