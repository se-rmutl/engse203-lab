## 1. ทำไมต้องวางสองสัปดาห์คู่กัน

อาจารย์ตั้งข้อสังเกตถูกว่า **สัปดาห์ 9 ไม่ได้แตะโค้ดเลย** — ซึ่งเป็นเรื่องที่ตั้งใจ แต่ถ้าดูสัปดาห์เดียวจะรู้สึกว่าไม่ครบ

**สองสัปดาห์นี้คือหน่วยเดียวกันที่แบ่งครึ่ง**

```
สัปดาห์ 9                        สัปดาห์ 10
─────────────                    ─────────────
เรียน SQL                    →   เอา SQL ไปใส่ในโปรแกรม
ออกแบบตาราง                  →   เขียน service ที่ใช้ตารางนั้น
สร้าง campus.db              →   Node เปิดไฟล์นั้น
เขียน queries.sql            →   query กลายเป็นโค้ด

ไม่แตะโค้ดเลย                    แก้โค้ดไฟล์เดียว
```

### สิ่งที่สัปดาห์ 9 ส่งมอบให้สัปดาห์ 10

| ไฟล์ | สัปดาห์ 10 ใช้ทำอะไร |

| `schema.sql` | สร้างฐานข้อมูลใหม่ถ้าไฟล์เสีย · ใช้ตอน `loadSeed()` ครั้งแรก |
| `queries.sql` | **คัดลอก query ไปใส่ใน service ได้เลย** |
| `DATA_MODEL.md` | เอกสารอ้างอิงตอนเขียนโค้ด |

> **ถ้าสัปดาห์ 9 ทำไม่ครบ สัปดาห์ 10 เริ่มไม่ได้** — นี่คือเหตุผลที่งานที่บ้านสัปดาห์ 9 คิดเป็น 70% ของคะแนน

## 3. ⚠ ประเด็นสำคัญที่เจอตอนทดลอง — และเป็นแกนของสัปดาห์ 10

### 3.1 POST ส่ง `requesterName` มา แต่ฐานข้อมูลต้องการ `requester_id`

Frontend ส่งมาแบบนี้ (ไม่เปลี่ยนตั้งแต่ Week 05)

```json
{ "requesterName": "สมชาย ใจดี", "requestType": "แจ้งซ่อม", ... }
```

แต่ตาราง `requests` เก็บ `requester_id` เป็นตัวเลข

**ทางเลือกที่พิจารณา**

| ทางเลือก | ผล |
|---|---|
| ให้ frontend ส่ง `requester_id` มา | ❌ ต้องแก้ frontend — เสียคำสัญญา |
| เก็บ `requesterName` เป็นคอลัมน์ด้วย | ❌ กลับไปมีข้อมูลซ้ำ — เสียบทเรียนสัปดาห์ 9 |
| **ให้ service แปลงชื่อเป็น id ให้** ⭐ | ✅ **ไม่กระทบใคร และเป็นบทเรียนที่ดี** |

```js
/** แปลงชื่อผู้แจ้งเป็น id — ถ้ายังไม่มีในระบบก็สร้างให้ */
function resolveUserId(name) {
  const found = db.prepare('SELECT id FROM users WHERE name = ?').get(name);
  if (found) return found.id;
  return db.prepare('INSERT INTO users (name, department, email) VALUES (?, ?, ?)')
           .run(name, 'ไม่ระบุ', `user-${Date.now().toString(36)}@rmutl.ac.th`).lastInsertRowid;
}
```

> **นี่คือสิ่งที่เราสัญญาไว้ในบทที่ 9 ของสัปดาห์ 9** — *"โครงในฐานข้อมูลไม่จำเป็นต้องเหมือนรูปแบบที่ API ส่งออก นี่คือหน้าที่ของชั้น service"*
>
> สัปดาห์ 10 จะได้เห็นว่ามันไม่ใช่แค่คำพูดสวย ๆ แต่เป็นโค้ดจริงที่ต้องเขียน

### 3.2 กับดัก path สัมพัทธ์ — เจอจริงตอนทดลอง

ตอนแรกผมเขียนแบบนี้แล้ว **checker พังทั้งหมด**

```js
const DB_FILE = './data/campus.db';   // ❌ อ้างจากที่ที่รันคำสั่ง
```

เพราะ `npm run dev` รันจาก `api/` แต่ checker รันจาก root — **หาไฟล์คนละที่**

```js
// ✅ อ้างจากตำแหน่งไฟล์นี้
const HERE = path.dirname(fileURLToPath(import.meta.url));
const API_ROOT = path.resolve(HERE, '../..');
const DB_FILE = process.env.DB_FILE ?? path.join(API_ROOT, 'data', 'campus.db');
```

**เก็บไว้เป็น checkpoint หนึ่งของสัปดาห์ 10** เพราะนักศึกษาจะเจอแน่นอน และเป็นกับดักที่หาสาเหตุยาก

### 3.3 `node:sqlite` เป็น sync — service จึงไม่ต้องเปลี่ยนเป็น async

| ฟังก์ชัน | Week 07 | Week 10 |
|---|---|---|
| `findAll()` | sync | **sync เหมือนเดิม** |
| `findById()` | sync | **sync เหมือนเดิม** |
| `create()` | sync | **sync เหมือนเดิม** |
| `loadSeed()` | async | async เหมือนเดิม |

**controller จึงไม่ต้องแก้เลย** — เพราะ signature ไม่เปลี่ยน

> **เรื่อง async ย้ายไปสัปดาห์ 11** ตามที่ตกลงกัน · ตอนเจอ MongoDB ที่เป็น async จริงเพราะคุยข้ามเครือข่าย เหตุผลจะเป็นของจริงไม่ใช่การบังคับ

### 5.4 บทที่ 7 — Parameterized Query (ต้องเน้นที่สุด)

เป็นหัวข้อที่ มคอ. 4.1.2 ระบุไว้ชัด และเป็นเรื่องความปลอดภัยจริง

```js
// ❌ อันตราย — ต่อ string
db.prepare(`SELECT * FROM requests WHERE status = '${status}'`).all();

// ✅ ปลอดภัย — ใช้ ?
db.prepare('SELECT * FROM requests WHERE status = ?').all(status);
```

**สาธิตให้เห็นจริง** — ส่ง `x' OR '1'='1` เข้าไปแล้วเทียบผล

| วิธีเขียน | ผลที่ได้ |
|---|---|
| ต่อ string | คืนข้อมูล**ทั้งหมด** — เงื่อนไขถูกข้าม |
| parameterized | คืน **0 แถว** — ถูกตีความเป็นข้อความธรรมดา |

> ทดสอบแล้วในสัปดาห์ 9 — ยืนยันว่าใช้สาธิตได้จริง
