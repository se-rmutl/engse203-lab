บทที่ 1 · กลุ่มปูพื้นฐาน

Backend คืออะไร และทำไมเราต้องมีมัน

เวลาอ่าน ≈ 10 นาที · ยังไม่มีโค้ด

ห้าสัปดาห์ที่ผ่านมาเราเขียนโค้ดที่ทำงานอยู่ที่เดียว — ในเบราว์เซอร์ของผู้ใช้ React, HTML, CSS ทั้งหมดถูกดาวน์โหลดไปที่เครื่องผู้ใช้แล้วทำงานที่นั่น

แต่มีปัญหาที่เบราว์เซอร์อย่างเดียวแก้ไม่ได้ ลองนึกถึงแอป Campus Service Request ที่เราทำ

🟩 ทายก่อนอ่านต่อ

ถ้านักศึกษา 2 คนเปิดแอป Campus Service Request คนละเครื่อง แล้วคนแรกเพิ่มคำร้องใหม่ — คนที่สองจะเห็นคำร้องนั้นไหม ในเมื่อข้อมูลเก็บใน localStorage ของแต่ละเครื่อง

เฉลย

ไม่เห็น เพราะ localStorage อยู่แยกกันในแต่ละเบราว์เซอร์ · คำร้องที่คนแรกเพิ่มอยู่แค่ในเครื่องคนแรกเท่านั้น

นี่คือข้อจำกัดพื้นฐานของ frontend อย่างเดียว — ไม่มีที่กลางให้ทุกคนใช้ข้อมูลร่วมกัน และนี่คือเหตุผลที่เราต้องมี backend

1.1 สองฝั่งของแอปพลิเคชัน

Backend / Server-side

ส่วนของแอปที่ทำงานบนเครื่องเซิร์ฟเวอร์ ไม่ใช่ที่เครื่องผู้ใช้ · ผู้ใช้มองไม่เห็นโค้ดส่วนนี้ เห็นแต่ผลลัพธ์ที่มันส่งกลับมา · ทำหน้าที่เก็บข้อมูลกลาง ประมวลผล และตัดสินใจว่าใครทำอะไรได้บ้าง

Server (เซิร์ฟเวอร์)

โปรแกรมที่รอรับคำขออยู่ตลอดเวลา · เมื่อมีคำขอเข้ามาก็ประมวลผลแล้วตอบกลับ แล้วรอคำขอถัดไป · คำว่า "server" มาจาก "serve" (ให้บริการ) — มันคอยให้บริการคำขอ

🟪 เทียบกับของที่คุ้น

คิดถึงร้านอาหาร — frontend คือเมนูและโต๊ะที่ลูกค้าเห็น · backend คือครัวที่ลูกค้าไม่เห็น · ลูกค้า (เบราว์เซอร์) สั่งอาหาร (ส่งคำขอ) พนักงานเสิร์ฟส่งให้ครัว ครัวทำเสร็จแล้วส่งกลับ · ครัวมีที่เดียวแต่รับออเดอร์จากทุกโต๊ะ — เหมือนเซิร์ฟเวอร์ที่รับคำขอจากผู้ใช้ทุกคน

1.2 backend ทำอะไรได้ที่ frontend ทำไม่ได้

สิ่งที่ต้องการfrontend อย่างเดียวมี backend
ทุกคนเห็นข้อมูลชุดเดียวกัน❌ แยกกันแต่ละเครื่อง✅ ที่กลางเดียว
ข้อมูลอยู่ถาวรจริง◐ อยู่แค่ในเบราว์เซอร์นั้น✅ เก็บที่เซิร์ฟเวอร์
ควบคุมสิทธิ์ว่าใครทำอะไรได้❌ ผู้ใช้แก้โค้ดเองได้✅ เซิร์ฟเวอร์ตัดสิน
เก็บความลับ เช่น รหัสผ่านฐานข้อมูล❌ ผู้ใช้เห็นทุกอย่าง✅ ซ่อนที่เซิร์ฟเวอร์ได้
🟨 สิ่งที่เราจะทำในหน่วยนี้ กับสิ่งที่ยังไม่ทำ

ทำ — สร้างเซิร์ฟเวอร์ที่เก็บคำร้องไว้ที่กลาง และให้ React เรียกใช้ผ่าน API

ยังไม่ทำ — ฐานข้อมูลจริง (หน่วย 4), ระบบล็อกอิน, การ deploy ขึ้นเซิร์ฟเวอร์จริง · หน่วยนี้เก็บข้อมูลในหน่วยความจำของเซิร์ฟเวอร์ไปก่อน

สรุปบทที่ 1
  • frontend อยู่ที่เครื่องผู้ใช้แต่ละคน · backend อยู่ที่เครื่องกลางเครื่องเดียว
  • backend คือ "ที่กลาง" ที่ทำให้ทุกคนใช้ข้อมูลชุดเดียวกันได้
  • server = โปรแกรมที่รอรับคำขอแล้วตอบกลับ ตลอดเวลา
  • หน่วยนี้สร้าง backend ให้ Campus Service Request เก็บข้อมูลในหน่วยความจำก่อน

บทที่ 2 · กลุ่มปูพื้นฐาน

Node.js — JavaScript ที่ออกนอกเบราว์เซอร์

เวลาอ่าน ≈ 9 นาที · ยังไม่มีโค้ด Express

มาถึงคำถามที่หลายคนสงสัย — เราเขียน JavaScript มาตลอด แต่ JavaScript ทำงานในเบราว์เซอร์ไม่ใช่หรือ แล้วจะเอามาเขียนเซิร์ฟเวอร์ได้อย่างไร

Node.js

โปรแกรมที่ทำให้เรารัน JavaScript นอกเบราว์เซอร์ได้ — บนเครื่องคอมพิวเตอร์โดยตรง · แปลว่าเราใช้ภาษาเดิมที่เขียน React มาเขียนเซิร์ฟเวอร์ได้เลย ไม่ต้องเรียนภาษาใหม่

2.1 ทำไม JavaScript ถึงออกจากเบราว์เซอร์ได้

เดิม JavaScript ทำงานได้เฉพาะในเบราว์เซอร์ เพราะเบราว์เซอร์มีเครื่องแปลภาษา (engine) อยู่ข้างใน · Chrome ใช้ engine ชื่อ V8

ปี 2009 มีคนเอา engine V8 ออกมาจาก Chrome แล้วห่อด้วยความสามารถเพิ่มเติม เช่น อ่านเขียนไฟล์และเปิดรับการเชื่อมต่อเครือข่าย — กลายเป็น Node.js · ทำให้ JavaScript ทำสิ่งที่เบราว์เซอร์ไม่ให้ทำได้

🟥 สิ่งที่หายไปเมื่อออกจากเบราว์เซอร์

ใน Node ไม่มี window, document, localStorage หรือ DOM ใด ๆ เพราะไม่มีหน้าเว็บให้จัดการ · ถ้าเผลอเรียก document.querySelector ในโค้ด Node จะได้ error ทันที

แต่ได้ของใหม่มาแทน เช่น process (ข้อมูลของโปรแกรมที่รันอยู่) และ module สำหรับอ่านไฟล์กับเปิดเซิร์ฟเวอร์

2.2 npm — คลังของสำเร็จรูป

npm (Node Package Manager)

คลังกลางที่เก็บโค้ดสำเร็จรูปที่คนอื่นเขียนไว้ให้เราหยิบมาใช้ · แทนที่จะเขียนทุกอย่างเอง เราติดตั้งของที่มีคนทำไว้แล้วมาต่อยอด · คุณใช้ npm มาตั้งแต่ Week 04 แล้วตอน npm install

ของแต่ละชิ้นใน npm เรียกว่า package · Express ที่เราจะใช้ก็เป็น package หนึ่ง · เมื่อติดตั้งแล้วรายชื่อจะถูกจดไว้ใน package.json

🟪 เทียบกับของที่คุ้น

npm เหมือนApp Store ของโค้ด · แทนที่จะเขียนแอปเองทั้งหมด คุณดาวน์โหลดแอปที่คนอื่นทำไว้ · package.json ก็เหมือนรายการแอปที่ติดตั้งไว้ในเครื่อง

สรุปบทที่ 2
  • Node.js ทำให้รัน JavaScript นอกเบราว์เซอร์ได้ — ภาษาเดิม ความสามารถมากขึ้น
  • ใน Node ไม่มี window, document, localStorage แต่อ่านไฟล์และเปิดเซิร์ฟเวอร์ได้
  • npm คือคลังโค้ดสำเร็จรูป · แต่ละชิ้นเรียก package · จดไว้ใน package.json

บทที่ 3 · กลุ่มปูพื้นฐาน

HTTP — ภาษาที่เครื่องคุยกันบนเว็บ

เวลาอ่าน ≈ 12 นาที · บทที่สำคัญที่สุดของกลุ่มปูพื้นฐาน

ก่อนจะสร้างเซิร์ฟเวอร์ ต้องเข้าใจก่อนว่า เบราว์เซอร์กับเซิร์ฟเวอร์คุยกันอย่างไร · ภาษาที่ทั้งสองใช้เรียกว่า HTTP

HTTP (HyperText Transfer Protocol)

ชุดกติกาที่กำหนดว่าเบราว์เซอร์กับเซิร์ฟเวอร์จะส่งข้อความหากันในรูปแบบไหน · เหมือนภาษาที่ทั้งสองฝ่ายตกลงกันว่าจะพูดแบบนี้ อีกฝ่ายถึงจะเข้าใจ · คำว่า protocol แปลว่า "พิธีการ" หรือ "ข้อตกลง"

คุณใช้ HTTP มาตลอดโดยไม่รู้ตัว — ทุกครั้งที่เปิดเว็บ เบราว์เซอร์ส่งคำขอ HTTP ไปหาเซิร์ฟเวอร์ · แม้แต่ fetch() ที่เราเขียนใน Week 05 ก็ส่งคำขอ HTTP

3.1 คำขอและคำตอบ — request กับ response

HTTP ทำงานเป็นคู่เสมอ — ฝั่งหนึ่งส่งคำขอ (request) อีกฝั่งส่งคำตอบ (response) กลับ · เหมือนถาม–ตอบ

3.2 HTTP Method — บอกว่าอยากทำอะไร

ส่วนแรกของ request คือ method ที่บอกว่าต้องการทำอะไรกับข้อมูล · มี 4 ตัวที่ใช้บ่อยที่สุด และตรงกับการกระทำที่เราทำใน Campus Service Request พอดี

Methodแปลว่าใน Campus Service Request
GETขอดูข้อมูล (ไม่เปลี่ยนแปลงอะไร)ดูรายการคำร้อง
POSTสร้างข้อมูลใหม่เพิ่มคำร้อง
PUT / PATCHแก้ไขข้อมูลที่มีอยู่เปลี่ยนสถานะคำร้อง
DELETEลบข้อมูลลบคำร้อง
🟪 เทียบกับของที่คุ้น

คิดถึงตู้เอกสาร — GET คือหยิบมาอ่าน (แล้ววางคืน ไม่แก้อะไร) · POST คือใส่เอกสารใหม่เข้าไป · PUT คือแก้เอกสารเดิม · DELETE คือฉีกทิ้ง · ทั้ง 4 อย่างทำกับ "ตู้" เดียวกัน แต่เจตนาต่างกัน

🟥 GET ห้ามเปลี่ยนแปลงข้อมูล

มีกติกาสำคัญ — GET ต้องเป็นการอ่านอย่างเดียว ห้ามลบหรือแก้ข้อมูล · เพราะเบราว์เซอร์และระบบอื่นถือว่า GET ปลอดภัย เรียกซ้ำกี่ครั้งก็ได้ · ถ้าเผลอทำให้ GET ลบข้อมูล จะเกิดบั๊กร้ายแรงที่ข้อมูลหายโดยไม่ตั้งใจ

3.5.1 Public API — API ฟรีที่ให้เราลองเล่น

Public API

API ที่เปิดให้ใครก็ได้เรียกใช้ฟรี มักไม่ต้องสมัครสมาชิก · มีไว้ให้นักพัฒนาทดลองและเรียนรู้ · เราจะใช้ตัวหนึ่งชื่อ JSONPlaceholder ที่จำลองข้อมูลโพสต์ ผู้ใช้ และคอมเมนต์

ลองเปิด URL นี้ในเบราว์เซอร์ตอนนี้เลย

https://jsonplaceholder.typicode.com/posts/1

คุณจะเห็นข้อมูล JSON ตอบกลับมาแบบนี้ — นี่คือ response จริงจากเซิร์ฟเวอร์จริง

{
  "userId": 1,
  "id": 1,
  "title": "sunt aut facere...",
  "body": "quia et suscipit..."
}
🟨 โครงข้อมูลนี้คุ้น ๆ ไหม

โครง posts ของ JSONPlaceholder คล้ายกับ requests ของ Campus Service Request ที่เราทำ — มี id และ field ข้อมูล · ตอนสร้าง API เราจะทำแบบเดียวกันแต่เป็นคำร้องแทนโพสต์

3.5.2 ดู request/response จริงด้วย Chrome DevTools

ทุกครั้งที่เปิดเว็บ เบราว์เซอร์ส่ง request มากมายโดยที่เราไม่เห็น · Network tab ใน DevTools ให้เราเห็น request/response เหล่านั้นทั้งหมด

🏫 ทำในห้อง · CP00b

เปิดเว็บอะไรก็ได้ที่คุณใช้ประจำ → กด F12 → แท็บ Network → รีเฟรช · ดูว่ามี request กี่อัน แต่ละอัน method อะไร status เท่าไร · หาให้เจอว่า request ไหนได้ข้อมูล JSON กลับมา

3.5.3 ยิง request เองด้วย Postman หรือ Thunder Client

เบราว์เซอร์ยิงได้แค่ GET (พิมพ์ URL แล้ว Enter) · แต่ถ้าอยากลอง POST หรือ DELETE ต้องใช้เครื่องมือเฉพาะ

Postman / Thunder Client

โปรแกรมสำหรับยิง request ไปหา API แล้วดู response โดยไม่ต้องเขียนโค้ด · เลือก method ได้ (GET/POST/DELETE) ใส่ body ได้ ดู status code ได้ · Postman เป็นโปรแกรมแยก · Thunder Client เป็นส่วนขยายใน VS Code เบากว่า ไม่ต้องติดตั้งเพิ่ม

เครื่องมือข้อดีเหมาะกับ
Postmanครบเครื่อง เก็บ collection ได้ ทีมใช้ร่วมกันได้งานจริง มาตรฐานอุตสาหกรรม
Thunder Clientอยู่ใน VS Code ไม่ต้องสลับหน้าต่าง เบาทดสอบเร็ว ๆ ระหว่างเขียนโค้ด
🏫 ทำในห้อง · CP00c

ใช้ Postman หรือ Thunder Client ยิง request เหล่านี้ไปที่ JSONPlaceholder แล้วดู response กับ status code

  • GET https://jsonplaceholder.typicode.com/posts — ดูทั้งหมด (จะได้ status อะไร)
  • GET https://jsonplaceholder.typicode.com/posts/1 — ดูอันเดียว
  • POST https://jsonplaceholder.typicode.com/posts พร้อม body — ลองสร้าง (จะได้ status อะไร)
🟩 ทายก่อนอ่านต่อ

ตอนยิง POST สร้างโพสต์ใหม่สำเร็จ คุณคิดว่าจะได้ status code อะไรกลับมา · (คำใบ้: ไม่ใช่ 200)

เฉลย

ได้ 201 Created — เพราะสร้างของใหม่สำเร็จ · เราจะเรียนเรื่อง status code เต็ม ๆ ในบทที่ 9 แต่ตอนนี้คุณเห็นของจริงมาแล้วว่า POST สำเร็จตอบ 201 ไม่ใช่ 200

นี่คือประโยชน์ของการดูของจริงก่อน — พอถึงตอนสร้าง API เอง คุณจะรู้แล้วว่าควรตอบ status อะไร เพราะเคยเห็นมาแล้ว

สรุปบทที่ 3.5
  • รู้จัก API จากฝั่งผู้ใช้ก่อนสร้างเอง — เหมือนหัดอ่านก่อนหัดเขียน
  • public API เช่น JSONPlaceholder ให้ลองเล่นฟรี
  • Chrome DevTools → Network ดู request/response จริงได้
  • Postman/Thunder Client ยิง request เองได้ทุก method ดู status code ได้

บทที่ 4 · กลุ่ม Express

Express คืออะไร และทำไมไม่เขียน Node เปล่า ๆ

เวลาอ่าน ≈ 9 นาที

Node.js เปิดเซิร์ฟเวอร์ได้ด้วยตัวเอง แต่โค้ดจะยาวและยุ่งยากมาก · ลองดูเซิร์ฟเวอร์ Node เปล่า ๆ ที่แค่ตอบ "hello"

import http from 'node:http';

const server = http.createServer((req, res) => {
  if (req.url === '/' && req.method === 'GET') {
    res.writeHead(200, { 'Content-Type': 'text/plain' });
    res.end('hello');
  } else {
    res.writeHead(404);
    res.end();
  }
});
server.listen(3001);

สังเกตว่าเราต้องเช็ค req.url และ req.method เองทุกครั้ง ต้องตั้ง header เอง · ถ้ามี 10 เส้นทางก็ต้องเขียน if ซ้อนกัน 10 อัน — ยุ่งมาก

Express.js

package ที่มาช่วยจัดการงานซ้ำ ๆ ของการทำเซิร์ฟเวอร์ให้ · แทนที่จะเช็ค url และ method เอง Express ให้เราเขียนสั้น ๆ ว่า "ถ้ามี GET ที่ /api/requests ให้ทำแบบนี้" · เป็น package ที่นิยมที่สุดสำหรับทำเซิร์ฟเวอร์ด้วย Node

โค้ดเดียวกันด้วย Express

import express from 'express';
const app = express();

app.get('/', (req, res) => {
  res.send('hello');
});

app.listen(3001);
🟪 เทียบกับของที่คุ้น

Node เปล่ากับ Express เหมือนทำอาหารจากวัตถุดิบดิบ กับ ใช้ชุดเครื่องปรุงสำเร็จ · ทำเองจากศูนย์ได้ทุกอย่างแต่ช้าและพลาดง่าย · Express เตรียมของที่ใช้บ่อยไว้ให้ เราโฟกัสที่ตรรกะของแอปได้เลย · เหมือน React ที่ช่วยจัดการ DOM ให้เราไม่ต้องเขียน document.createElement เอง

เราใช้ Express 5 ซึ่งเป็นเวอร์ชันล่าสุด · โค้ดส่วนใหญ่เหมือน Express 4 ที่เจอในบทเรียนเก่าทั่วไป แต่จัดการ error ของฟังก์ชัน async ได้ดีขึ้น ซึ่งเราจะเห็นประโยชน์ใน Week 07

บทที่ 5 · กลุ่ม Express

Routing — เซิร์ฟเวอร์เลือกตอบอย่างไร

เวลาอ่าน ≈ 11 นาที

คำว่า routing คุณเจอมาแล้วใน Week 05 ตอน React Router — แนวคิดเหมือนกัน แต่คนละที่

🟪 เทียบกับ Week 05

React Router — URL เปลี่ยน แล้วเลือกว่าจะแสดง component ไหน (ทำในเบราว์เซอร์)

Express routing — คำขอเข้ามา แล้วเลือกว่าจะรันโค้ดไหนตอบกลับ (ทำในเซิร์ฟเวอร์) · แนวคิด "จับคู่ URL กับสิ่งที่จะทำ" เหมือนกัน

Route

คู่ของ method + path กับโค้ดที่จะทำเมื่อมีคำขอตรงกับคู่นั้น · เช่น "GET ที่ /api/requests" คู่กับ "ส่งรายการคำร้องกลับไป"

5.1 หน้าตาของ route

app.get('/api/requests', (req, res) => {
  // โค้ดที่ทำเมื่อมี GET ที่ path นี้
  res.json(requests);
});
   └──┬──┘ └──────┬──────┘  └──────────┬──────────┘
   method     path              handler (โค้ดที่ทำ)
Handler (route handler)

ฟังก์ชันที่ทำงานเมื่อมีคำขอตรงกับ route นั้น · รับ 2 อย่างเสมอ: req (คำขอที่เข้ามา) และ res (คำตอบที่เราจะส่งกลับ) · เราเขียนในนี้ว่าจะตอบอะไร

5.2 route ทั้งหมดของ Campus Service Request

นี่คือ route ที่เราต้องสร้าง — ตรงกับฟังก์ชันใน requestService.js ที่ React มีอยู่แล้วจาก Week 05

method + pathทำอะไรตรงกับฟังก์ชัน React
GET /api/requestsส่งรายการคำร้องทั้งหมดgetRequests()
GET /api/requests/:idส่งคำร้องใบเดียวตามรหัสgetRequestById(id)
POST /api/requestsสร้างคำร้องใหม่addRequest(input)
DELETE /api/requests/:idลบคำร้องdeleteRequest(id)

5.3 route parameter — ส่วนที่เปลี่ยนได้ใน path

สังเกต :id ใน path — เครื่องหมาย : บอกว่าส่วนนี้เปลี่ยนแปลงได้ · คุณเคยเห็นแล้วใน React Router ตอน requests/:requestId

app.get('/api/requests/:id', (req, res) => {
  const id = req.params.id;   // อ่านค่าจาก path
  // ถ้าเรียก /api/requests/REQ-001 → id = 'REQ-001'
});
🟩 ทายก่อนอ่านต่อ

ถ้ามี route ทั้ง GET /api/requests/new (path คงที่) และ GET /api/requests/:id (path มีตัวแปร) แล้วมีคำขอ GET /api/requests/new เข้ามา — Express จะเลือก route ไหน

เฉลย

Express เลือก route ที่เขียนไว้ก่อน · ถ้าเขียน :id ไว้ก่อน คำว่า new จะถูกจับเป็น id = 'new' แทนที่จะไปที่ route /new

กฎ — เขียน route ที่เจาะจง (path คงที่) ไว้ก่อน route ที่มีตัวแปรเสมอ · นี่คือกับดักที่พบบ่อยและ checker จะตรวจ

สรุปบทที่ 5
  • route = method + path จับคู่กับ handler (โค้ดที่ทำ)
  • handler รับ req (คำขอ) และ res (คำตอบ) เสมอ
  • :id ใน path คือส่วนที่เปลี่ยนได้ อ่านด้วย req.params.id
  • เขียน route ที่เจาะจงไว้ก่อน route ที่มีตัวแปร

บทที่ 6 · กลุ่ม Express

Request และ Response — อ่านคำขอ เขียนคำตอบ

เวลาอ่าน ≈ 10 นาที

ใน handler ทุกตัวมี 2 ตัวแปรที่ใช้ตลอด — req กับ res · บทนี้เจาะว่าแต่ละตัวใช้อ่านและเขียนอะไรได้บ้าง

6.1 req — อ่านสิ่งที่ลูกค้าส่งมา

อ่านจากได้อะไรตัวอย่าง
req.paramsค่าจาก :id ใน pathreq.params.id → 'REQ-001'
req.queryค่าหลัง ? ใน URL?status=pending → req.query.status
req.bodyข้อมูลที่แนบมากับ POSTข้อมูลคำร้องใหม่ทั้งก้อน
req.methodmethod ที่ใช้'GET', 'POST'
🟥 req.body จะว่างถ้าไม่บอก Express ให้อ่าน JSON

โดยค่าเริ่มต้น Express ไม่รู้จะอ่าน body อย่างไร · ต้องบอกด้วยบรรทัดนี้ก่อน

app.use(express.json());   // บอก Express ว่า body เป็น JSON

ถ้าลืมบรรทัดนี้ req.body จะเป็น undefined ตลอด แล้ว POST จะพังโดยไม่รู้สาเหตุ · นี่คือกับดักอันดับหนึ่งของมือใหม่

6.2 res — เขียนคำตอบกลับไป

เขียนด้วยทำอะไร
res.json(data)ส่งข้อมูลกลับเป็น JSON (ใช้บ่อยที่สุด)
res.status(201)ตั้งรหัสสถานะ (บทที่ 9)
res.status(404).json({...})ตั้งสถานะแล้วส่งข้อมูล — ต่อกันได้
res.end()จบคำตอบโดยไม่ส่งข้อมูล
🟨 res.json() ทำสองอย่างให้อัตโนมัติ

แปลง object เป็นข้อความ JSON (เหมือน JSON.stringify ที่ใช้ใน Week 05) และตั้ง header Content-Type: application/json ให้ · เบราว์เซอร์จึงรู้ว่าข้อมูลที่ได้เป็น JSON

6.3 หนึ่งคำขอ ตอบได้ครั้งเดียว

🟥 ห้ามส่งคำตอบซ้ำ

แต่ละคำขอต้องส่งคำตอบครั้งเดียว · ถ้าเผลอเรียก res.json() สองครั้ง จะได้ error ว่า "ส่ง header ไปแล้ว"

app.get('/', (req, res) => {
  res.json({ a: 1 });
  res.json({ b: 2 });   // error! ส่งไปแล้ว
});

มักเกิดตอนลืมใส่ return หลังส่งคำตอบในกรณี error แล้วโค้ดไหลลงไปส่งอีกครั้ง

สรุปบทที่ 6
  • req อ่านคำขอ: params (จาก :id), query (จาก ?), body (จาก POST)
  • ต้องมี app.use(express.json()) ก่อน ไม่งั้น req.body ว่าง
  • res.json() ส่ง JSON · res.status() ตั้งรหัส · ต่อกันได้
  • หนึ่งคำขอตอบได้ครั้งเดียว · อย่าลืม return หลังส่งคำตอบ

บทที่ 7 · กลุ่ม Express

Middleware — ชั้นที่คำขอไหลผ่าน

เวลาอ่าน ≈ 12 นาที · แนวคิดใหม่ที่นามธรรมที่สุด

Middleware เป็นแนวคิดที่ทำให้ Express ทรงพลัง แต่ก็เป็นสิ่งที่มือใหม่งงมากที่สุด · เราจะค่อย ๆ สร้างความเข้าใจ

Middleware

ฟังก์ชันที่ทำงานกับคำขอ ก่อนที่มันจะถึง handler · คำขอทุกอันไหลผ่าน middleware เป็นชั้น ๆ เหมือนผ่านด่านตรวจ ก่อนถึงปลายทาง · คำว่า "middle-ware" = ของที่อยู่ตรงกลาง (ระหว่างคำขอกับคำตอบ)

🟪 เทียบกับของที่คุ้น

คิดถึงด่านตรวจที่สนามบิน — ก่อนขึ้นเครื่อง (handler) คุณต้องผ่านหลายด่านเรียงกัน: เช็คอิน → ตรวจกระเป๋า → ตรวจหนังสือเดินทาง · แต่ละด่านทำหน้าที่ของตัวเองแล้วส่งต่อด่านถัดไป · middleware ก็ทำงานเรียงกันแบบนี้ ทุกคำขอผ่านทุกด่านก่อนถึง handler

7.1 หน้าตาของ middleware

function logger(req, res, next) {
  console.log(`${req.method} ${req.url}`);   // ทำงานของตัวเอง
  next();                                // ส่งต่อชั้นถัดไป
}

app.use(logger);   // ติดตั้งให้ทุกคำขอผ่าน

middleware มี 3 พารามิเตอร์ ต่างจาก handler ที่มี 2 — ตัวที่เพิ่มมาคือ next · เรียก next() เพื่อบอกว่า "ฉันเสร็จแล้ว ส่งต่อได้"

next()

ฟังก์ชันที่ส่งคำขอต่อไปยัง middleware หรือ handler ชั้นถัดไป · ถ้าลืมเรียก คำขอจะค้างอยู่ที่ middleware นั้น ผู้ใช้จะรอคำตอบไปเรื่อย ๆ จนหมดเวลา

7.2 ลำดับสำคัญมาก

🟥 middleware ทำงานตามลำดับที่เขียน

ถ้าเขียน app.use(express.json()) หลัง route ที่ต้องอ่าน body — route นั้นจะอ่าน body ไม่ได้ เพราะ middleware ยังไม่ทำงานตอนที่ route ทำ

กฎ — middleware ที่ต้องใช้กับทุก route ให้เขียน ก่อน route ทั้งหมดเสมอ

7.3 middleware ที่เราจะใช้ในหน่วยนี้

middlewareทำอะไรทำเมื่อ
express.json()อ่าน JSON body ให้ req.body ใช้ได้Week 06 · CP03

cors()ให้ React ต่างพอร์ตเรียกได้Week 07

แทนที่จะเขียน "บันทึก log" ในทุก route (ซ้ำ 10 ที่) เราเขียน middleware ตัวเดียวแล้วทุกคำขอผ่านมันอัตโนมัติ · เป็นหลักการเดียวกับ AppLayout ใน Week 05 ที่เขียน header ครั้งเดียวใช้ทุกหน้า

สรุปบทที่ 7
  • middleware = ฟังก์ชันที่คำขอไหลผ่านก่อนถึง handler
  • มี 3 พารามิเตอร์: req, res, next · ต้องเรียก next() เพื่อส่งต่อ
  • ทำงานตามลำดับที่เขียน · middleware ที่ใช้ทุก route เขียนก่อน route
  • ช่วยไม่ต้องเขียนโค้ดซ้ำในทุก route

บทที่ 8 · กลุ่ม REST

REST — กติกาการออกแบบ API ที่คนทั้งโลกใช้

เวลาอ่าน ≈ 11 นาที

API (Application Programming Interface)

ช่องทางที่โปรแกรมหนึ่งเรียกใช้อีกโปรแกรม · ในบริบทของเรา คือช่องทางที่ React (โปรแกรมหนึ่ง) เรียกใช้เซิร์ฟเวอร์ (อีกโปรแกรม) · เหมือนเมนูร้านอาหาร — บอกว่าสั่งอะไรได้บ้างและสั่งอย่างไร โดยไม่ต้องรู้ว่าครัวทำอย่างไร

REST (REpresentational State Transfer)

ชุดแนวทางการออกแบบ API ที่คนส่วนใหญ่ทั้งโลกใช้ตรงกัน · ไม่ใช่เทคโนโลยีหรือ package แต่เป็นกติกาว่าควรตั้งชื่อ path และใช้ method อย่างไรให้เป็นมาตรฐาน · API ที่ทำตามกติกานี้เรียกว่า RESTful

8.1 หัวใจของ REST — มองทุกอย่างเป็น "ทรัพยากร"

REST มองข้อมูลเป็นทรัพยากร (resource) · ในแอปเราทรัพยากรคือ "คำร้อง" (requests) · แล้วใช้ method บอกว่าจะทำอะไรกับทรัพยากรนั้น

🟥 กับดักที่มือใหม่ทำบ่อย — เอาคำกริยาใส่ใน path
แบบที่ไม่ใช่ RESTแบบ RESTful
GET /getAllRequestsGET /api/requests
POST /createRequestPOST /api/requests
POST /deleteRequest/5DELETE /api/requests/5

ฝั่งซ้ายเอาการกระทำ (get, create, delete) ใส่ใน path · ฝั่งขวาให้ method บอกการกระทำ path บอกแค่ทรัพยากร · RESTful อ่านแล้วเดาได้ทันทีว่าทำอะไร

8.2 ทำไมต้องทำตาม REST

เพราะคนทั้งโลกใช้กติกาเดียวกัน · เมื่อคุณเจอ API ที่ทำตาม REST คุณเดาได้ทันทีว่า GET /users ดูผู้ใช้ทั้งหมด DELETE /users/5 ลบผู้ใช้คนที่ 5 — โดยไม่ต้องอ่านคู่มือ · API ของบริษัทใหญ่อย่าง GitHub, Twitter ก็ใช้ REST

สรุปบทที่ 8
  • API = ช่องทางที่โปรแกรมเรียกใช้กัน · REST = กติกาการออกแบบ API ที่เป็นมาตรฐาน
  • REST มองข้อมูลเป็นทรัพยากร · path เป็นคำนาม · การกระทำอยู่ที่ method
  • อย่าเอาคำกริยาใส่ path — ใช้ DELETE /requests/5 ไม่ใช่ /deleteRequest/5
  • ทำตาม REST เพราะคนทั้งโลกใช้ตรงกัน อ่านแล้วเดาได้

บทที่ 9 · กลุ่ม REST

HTTP Status Code — บอกผลด้วยตัวเลข

เวลาอ่าน ≈ 9 นาที

ทุก response มีรหัสสถานะ — ตัวเลข 3 หลักที่บอกว่าคำขอสำเร็จหรือไม่ · คุณเจอมาแล้วใน Week 05 ตอน response.ok และ 404

9.1 จำเป็นกลุ่ม ไม่ต้องท่องทุกตัว

รหัสมีเยอะ แต่แบ่งเป็นกลุ่มตามหลักร้อย · จำกลุ่มก็พอ

9.2 ผูกกับสถานการณ์ ไม่ใช่ท่องจำ

วิธีจำที่ดีที่สุดคือผูกกับสิ่งที่เกิดขึ้นจริง ใน Campus Service Request

สถานการณ์รหัสที่ถูกทำไม
ดูรายการคำร้องได้200สำเร็จ มีข้อมูลส่งกลับ
สร้างคำร้องใหม่สำเร็จ201สำเร็จ และ สร้างของใหม่ขึ้นมา
ลบคำร้องสำเร็จ204สำเร็จ แต่ไม่มีอะไรส่งกลับ
ส่งฟอร์มที่กรอกไม่ครบ400ผู้ใช้ส่งข้อมูลผิด
ขอคำร้อง REQ-999 ที่ไม่มี404ไม่พบทรัพยากรนั้น
🟩 ทายก่อนอ่านต่อ

POST สร้างคำร้องสำเร็จ ควรตอบ 200 หรือ 201 · ทั้งสองแปลว่าสำเร็จ ต่างกันตรงไหน

เฉลย

201 Created เจาะจงกว่า — บอกว่าสำเร็จและมีของใหม่ถูกสร้างขึ้น · ส่วน 200 OK แปลว่าสำเร็จเฉย ๆ

ใช้ 200 ก็ไม่ถึงกับผิด แต่ 201 สื่อความหมายชัดกว่าและเป็นมาตรฐาน REST · checker จะตรวจว่า POST ตอบ 201

🟨 เชื่อมกับ Week 05

ตอน Week 05 เราเขียน if (!response.ok) throw new Error(...) · response.ok เป็น true เมื่อ status เป็น 2xx และ false เมื่อ 4xx/5xx · ตอนนี้คุณเข้าใจแล้วว่าตัวเลขพวกนั้นมาจากไหน — จากฝั่งเซิร์ฟเวอร์ที่เรากำลังจะเขียนนี่เอง

สรุปบทที่ 9
  • status code บอกผลด้วยตัวเลข · จำกลุ่ม: 2xx สำเร็จ, 4xx ผู้ใช้ผิด, 5xx เซิร์ฟเวอร์ผิด
  • 6 ตัวที่ใช้จริง: 200, 201, 204, 400, 404, 500
  • POST สำเร็จ = 201 · DELETE สำเร็จ = 204 · ไม่พบ = 404 · ข้อมูลผิด = 400
  • ผูกรหัสกับสถานการณ์จริง ดีกว่าท่องตาราง

แยกชั้น Route / Controller / Service

เวลาอ่าน ≈ 9 นาที

เมื่อ API โตขึ้น การเขียนทุกอย่างในไฟล์เดียวจะยุ่งเหยิง · เราแยกความรับผิดชอบเป็นชั้น เหมือนที่แยก Page/Component/Service ใน React

🟪 เทียบกับ Week 05

backend แยกชั้นด้วยหลักการเดียวกับ frontend เป๊ะ — route เหมือน App.jsx (รับคำขอ ส่งต่อ) · controller เหมือน Page (ประสานงาน) · service เหมือน requestService (จัดการข้อมูล) · ถ้าเข้าใจการแยกชั้นของ React แล้ว อันนี้คือแนวคิดเดียวกัน

ชั้นรู้เรื่อง HTTP ไหมหน้าที่
Routeรู้ (method, path)จับคู่คำขอกับ controller
Controllerรู้ (req, res, status)อ่านคำขอ ตัดสิน status เรียก service
Serviceไม่รู้จัดการข้อมูลล้วน ๆ ใช้ที่ไหนก็ได้
🟦 มองไปข้างหน้า — หน่วยที่ 4

เหตุผลที่ service ไม่รู้จัก HTTP สำคัญมาก — ในหน่วย 4 เราจะเปลี่ยนจากเก็บข้อมูลใน memory ไปเป็นฐานข้อมูล SQLite · ถ้าแยกชั้นดี จะแก้แค่ service ชั้นบน (controller, route) ไม่ต้องแตะเลย · เหมือน Service Layer ของ React ที่เปลี่ยนจาก localStorage เป็น API โดย component ไม่ต้องแก้
