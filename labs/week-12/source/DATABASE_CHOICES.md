# ทางเลือกฐานข้อมูล — SQLite, NoSQL และ async

> บันทึกตอบคำถามจากบท "อ่านเพิ่มเติม" (CP41)

## 1. ทำไมโปรเจกต์นี้เลือก SQLite แทน MongoDB

ข้อมูลของเรา (users, requests) **มีโครงสร้างชัดเจนและมีความสัมพันธ์กัน** — คำร้องแต่ละใบชี้ไปหาผู้ใช้หนึ่งคนด้วย foreign key

SQL เหมาะกับข้อมูลแบบนี้เพราะ:
- บังคับโครงสร้าง (schema) และความถูกต้อง (constraint) ได้
- JOIN ดึงข้อมูลข้ามตารางได้ในคำสั่งเดียว
- ความสัมพันธ์ระหว่างตารางเป็นเรื่องหลักของ SQL

MongoDB (NoSQL) เหมาะกว่าเมื่อข้อมูล**ไม่มีโครงตายตัว** หรือแต่ละรายการหน้าตาต่างกันมาก เช่น log, เอกสารที่ field ไม่เท่ากัน

## 2. ถ้าวันหนึ่งต้องเปลี่ยนไป MongoDB จะกระทบชั้นไหน

| ชั้น | กระทบไหม | เพราะอะไร |
|---|---|---|
| Frontend | ❌ ไม่ | ยังเรียก API เดิม รับ JSON เดิม |
| Controller | ⚠ กระทบ | ต้องเติม `await` ทุกที่ (MongoDB เป็น async) |
| Service | ✅ กระทบเต็ม | เขียนใหม่ทั้งไฟล์ให้ใช้ MongoDB driver |
| Database | ✅ เปลี่ยน | จาก SQLite เป็น MongoDB |

> **ต่างจาก 4 ครั้งก่อน** ที่แก้แค่ service เพราะครั้งนี้เปลี่ยน sync→async ซึ่งเป็นการเปลี่ยน "สัญญา" ของ service จึงกระทบ controller ด้วย

## 3. async จำเป็นเมื่อไร ไม่จำเป็นเมื่อไร

| | ต้องรอไหม | ใช้ async ไหม |
|---|---|---|
| SQLite (ไฟล์ในเครื่อง) | อ่านเสร็จทันที | ❌ ไม่ต้อง |
| MongoDB Atlas (คนละเครื่อง) | รอข้อมูลข้ามเครือข่าย | ✅ ต้อง |
| เรียก API ภายนอก | รอเครือข่าย | ✅ ต้อง |
| อ่านไฟล์ขนาดใหญ่ | รอดิสก์ | ✅ ควร |

**หลักการ** — ใช้ async เมื่อต้อง**รอ**บางอย่างที่ไม่เสร็จทันที (เครือข่าย ดิสก์) เพื่อไม่ให้โปรแกรมค้างรอ
