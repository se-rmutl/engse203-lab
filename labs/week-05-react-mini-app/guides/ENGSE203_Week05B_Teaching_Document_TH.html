บทที่ 1

ทำไมข้อมูลถึงหายตอน refresh

เวลาอ่าน ≈ 7 นาที

สัปดาห์ที่แล้วเราแก้ปัญหาไปสองข้อจากสามข้อ — URL บอกได้แล้วว่ากำลังดูอะไร และผู้ใช้รู้แล้วว่าระบบกำลังโหลดหรือพลาด

เหลือข้อสุดท้าย กด refresh แล้วข้อมูลที่เพิ่งเพิ่มหายไปไหน

🟣 ทายก่อนอ่านต่อ

ใน Pre-LAB คุณเปลี่ยน preference แล้ว refresh — ค่านั้นไม่หาย แต่คำร้องที่เพิ่มใน LAB กลับหาย

ทั้งที่เป็นข้อมูลในเบราว์เซอร์เหมือนกัน ต่างกันตรงไหน

เฉลยคำถามตอนต้นบท

แอปใน Pre-LAB เขียนค่า preference ลง localStorage ทุกครั้งที่เปลี่ยน แล้วอ่านกลับมาตอนเปิดหน้า ส่วนแอป LAB ของเราเก็บคำร้องไว้ใน useState อย่างเดียว

พูดง่าย ๆ คือ Pre-LAB ทำสิ่งที่เรากำลังจะทำวันนี้ไปแล้ว — และนั่นคือเหตุผลที่ให้ไปสังเกตมาก่อน

ที่เก็บในเบราว์เซอร์มีหลายแบบ

ที่เก็บอยู่ได้นานแค่ไหนเหมาะกับ
localStorageจนกว่าจะลบเองข้อมูลสาธิต การตั้งค่า ← เราใช้ตัวนี้
sessionStorageเฉพาะแท็บนั้น ปิดแล้วหายข้อมูลชั่วคราวระหว่างทำงาน
IndexedDBจนกว่าจะลบเองข้อมูลจำนวนมากและซับซ้อน
🔴 สิ่งที่ห้ามเก็บใน Local Storage

ผู้ใช้แก้ข้อมูลตรงนี้ได้เองง่าย ๆ อย่างที่คุณเพิ่งลองทำใน Pre-LAB และสคริปต์ใด ๆ ที่รันในหน้าเดียวกันก็อ่านได้ทั้งหมด

ห้ามเก็บ — รหัสผ่าน โทเคน เลขบัตรประชาชน ข้อมูลส่วนบุคคลจริง หรืออะไรที่ถ้าถูกแก้แล้วระบบจะเสียหาย · LAB นี้ใช้ข้อมูลสาธิตทั้งหมด

สรุปบทที่ 1
  • state อยู่ในหน่วยความจำ refresh แล้วหาย · Local Storage อยู่ในดิสก์ จึงยังอยู่
  • แลกมาด้วย 3 ข้อ — เก็บได้แต่ข้อความ ผูกกับเครื่อง และผู้ใช้แก้เองได้
  • ห้ามเก็บข้อมูลสำคัญหรือข้อมูลส่วนบุคคลจริง

บทที่ 2

แปลงข้อมูลเป็นข้อความและกลับคืน

เวลาอ่าน ≈ 9 นาที

ข้อจำกัดข้อแรกจากบทที่แล้วคือ Local Storage เก็บได้เฉพาะข้อความ แต่ข้อมูลคำร้องของเราเป็น array ของ object

🟣 ทายก่อนอ่านต่อ

ถ้าเราเขียนแบบนี้ แล้วอ่านกลับมาจะได้อะไร

localStorage.setItem('test', { name: 'สมชาย' });
localStorage.getItem('test');   // → ?
เฉลย

ได้ข้อความว่า "[object Object]"

เบราว์เซอร์แปลง object เป็นข้อความให้เองโดยอัตโนมัติ แต่แปลงแบบไร้ประโยชน์ — ข้อมูลข้างในหายหมดและกู้กลับไม่ได้ ที่แย่คือไม่มี error ใด ๆ โปรแกรมทำงานต่อไปเงียบ ๆ แล้วคุณจะรู้ตัวตอนอ่านกลับมาไม่ได้

2.1 คู่แปลงที่ต้องใช้เสมอ

// ตอนเก็บ — object → ข้อความ
localStorage.setItem(key, JSON.stringify(data));

// ตอนอ่าน — ข้อความ → object
const data = JSON.parse(localStorage.getItem(key));

2.2 structuredClone — ทำไมต้องคัดลอกก่อนคืน

ในโค้ดของ LAB คุณจะเห็น structuredClone() ครอบผลลัพธ์อยู่หลายจุด

return { status: 'valid', requests: structuredClone(envelope.requests) };

เหตุผลคือ ใน JavaScript การส่ง array หรือ object ไปให้ใครคือการส่งกุญแจบ้าน ไม่ใช่ส่งรูปถ่ายบ้าน

🔴 บั๊กที่จะเกิดถ้าไม่คัดลอก

สมมติ Service คืน array ตัวเดิมออกไป แล้วหน้าจอเอาไปแก้

const requests = await getRequests();
requests.push(newItem);        // ตั้งใจแก้แค่ในหน้าจอ
// แต่ข้อมูลต้นทางใน Service เปลี่ยนตามไปด้วย

ผลคือข้อมูลเปลี่ยนในที่ที่ไม่ได้ตั้งใจ โดยไม่มี error ให้จับ เป็นบั๊กประเภทที่หายากที่สุดประเภทหนึ่ง

structuredClone() สร้างสำเนาลึกให้ ทุกคนที่เรียก Service จึงได้ข้อมูลชุดของตัวเอง แก้ยังไงก็ไม่กระทบใคร

🟡 หมายเหตุ

มีเทคนิคเก่าที่ใช้ JSON.parse(JSON.stringify(x)) เพื่อคัดลอกลึกเช่นกัน แต่จะทำให้ Date กลายเป็นข้อความ และรับมือกับข้อมูลที่อ้างถึงตัวเองไม่ได้ · structuredClone เป็นวิธีมาตรฐานของเบราว์เซอร์สมัยใหม่

สรุปบทที่ 2
  • Local Storage เก็บได้แต่ข้อความ ต้องใช้ JSON.stringify ตอนเก็บและ JSON.parse ตอนอ่าน
  • ลืม stringify แล้วจะได้ "[object Object]" โดยไม่มี error เตือน
  • structuredClone ทำให้ผู้เรียกได้ข้อมูลชุดของตัวเอง ป้องกันการแก้ข้ามกันโดยไม่ตั้งใจ

บทที่ 3

Envelope และหมายเลขเวอร์ชัน

เวลาอ่าน ≈ 8 นาที

เราไม่ได้เก็บ array ของคำร้องลงไปตรง ๆ แต่ห่อไว้ในกล่องที่มีข้อมูลกำกับด้วย เรียกว่า envelope

{
  "schemaVersion": 1,
  "updatedAt": "2026-08-13T09:15:00.000Z",
  "requests": [ … ]
}
🟣 ทายก่อนอ่านต่อ

ทำไมต้องมี schemaVersion ในเมื่อเราก็รู้อยู่แล้วว่าข้อมูลหน้าตาเป็นอย่างไร

เฉลย

เพราะ ข้อมูลอยู่ในเครื่องผู้ใช้ แต่โค้ดอยู่ที่เรา — สองอย่างนี้อัปเดตไม่พร้อมกัน

สมมติเทอมหน้าคุณเพิ่มฟิลด์ dueDate เข้าไปในคำร้อง ผู้ใช้ที่เคยเปิดเว็บเมื่อสัปดาห์ที่แล้วจะมีข้อมูลเก่าที่ไม่มีฟิลด์นั้นค้างอยู่ในเครื่อง พอเปิดเว็บใหม่ โค้ดใหม่จะอ่านข้อมูลเก่าแล้วพัง

มี schemaVersion ทำให้โปรแกรมรู้ทันทีว่า "ข้อมูลนี้เป็นของโครงสร้างรุ่นเก่า ฉันอ่านไม่ได้" แล้วเลือกทางออกได้อย่างปลอดภัย

ส่วนประกอบทั้งสามของ envelope

ฟิลด์ทำหน้าที่อะไร
schemaVersionบอกว่าโครงสร้างข้อมูลนี้เป็นรุ่นไหน — ถ้าไม่ตรงกับที่โค้ดรองรับ ถือว่าอ่านไม่ได้
updatedAtเวลาที่บันทึกล่าสุด · ใช้ตรวจสอบและแก้ปัญหาได้เมื่อมีอะไรผิดปกติ
requestsข้อมูลจริงที่เราต้องการเก็บ

คีย์ที่ใช้ก็มีความหมายเช่นกัน

export const STORAGE_KEY = 'engse203-campus-requests-v1';
//                            └─ วิชา ─┘└─ ชื่อข้อมูล ──┘└ รุ่น ┘

ตั้งชื่อเฉพาะเจาะจงเพื่อไม่ให้ชนกับข้อมูลของเว็บอื่นที่ใช้โดเมนเดียวกัน — ซึ่งบน GitHub Pages เกิดขึ้นได้จริง เพราะทุกโปรเจกต์ของคุณอยู่ใต้ username.github.io เหมือนกันหมด

🔴 กับดัก · localStorage.clear()

ตอนทำปุ่ม Reset หลายคนเผลอใช้ localStorage.clear() ซึ่ง ลบข้อมูลของทุกเว็บที่ใช้โดเมนเดียวกัน — งาน Week 03 และ Week 04 ของคุณเองก็โดนลบไปด้วย

ต้องใช้ localStorage.removeItem(STORAGE_KEY) ที่ลบเฉพาะคีย์ของเรา · checker ตรวจข้อนี้จริง

สรุปบทที่ 3
  • ไม่เก็บ array ตรง ๆ แต่ห่อใน envelope ที่มี schemaVersion, updatedAt และ requests
  • schemaVersion แก้ปัญหาข้อมูลเก่าค้างในเครื่องผู้ใช้ขณะที่โค้ดเปลี่ยนไปแล้ว
  • ตั้งชื่อคีย์ให้เฉพาะเจาะจง และลบเฉพาะคีย์ของตัวเองเสมอ

บทที่ 4

อ่านกลับมาแล้วอย่าเพิ่งเชื่อ

เวลาอ่าน ≈ 12 นาที · บทที่สำคัญที่สุดของคาบนี้

ขาไปเราควบคุมได้ทั้งหมด แต่ขากลับควบคุมไม่ได้เลย ระหว่างที่ข้อมูลนอนอยู่ในเครื่องผู้ใช้ อาจเกิดอะไรขึ้นก็ได้

  • ผู้ใช้เปิด DevTools แล้วแก้เอง — อย่างที่คุณทำใน Pre-LAB
  • ส่วนขยายเบราว์เซอร์เข้าไปยุ่ง
  • เขียนค้างกลางคันเพราะแท็บถูกปิด
  • เป็นข้อมูลจากโค้ดเวอร์ชันเก่า

ทุกกรณีข้างบนต้องไม่ทำให้แอปพัง — ผู้ใช้ควรได้แอปที่ใช้งานได้ ไม่ใช่หน้าจอขาว

🟣 ทายก่อนอ่านต่อ

ถ้าเราใส่ try/catch ครอบ JSON.parse แล้ว — พอหรือยัง

เฉลย

ยังไม่พอ เพราะ try/catch จับได้แค่กรณีที่ข้อความไม่ใช่ JSON เท่านั้น

แต่ข้อความนี้เป็น JSON ที่ถูกต้องสมบูรณ์ และ JSON.parse จะสำเร็จโดยไม่มี error

{ "schemaVersion": 99, "requests": "ไม่ใช่ array" }

parse ได้ ไม่ได้แปลว่าข้อมูลถูก — นี่คือประโยคสำคัญที่สุดของบทนี้

4.1 ตรวจสามชั้น

ชั้นป้องกันอะไรถ้าลบชั้นนี้ออกจะเกิดอะไร
ฟอร์มผู้ใช้กรอกผิดผู้ใช้ไม่รู้ว่ากรอกผิดตรงไหน ต้องกดส่งก่อนถึงจะรู้
Serviceโค้ดส่วนอื่นเรียกด้วยข้อมูลผิดข้อมูลเสียหลุดเข้าไปในระบบโดยไม่มีใครทัก
Storageข้อมูลถูกแก้จากภายนอกหรือเสียหายเปิดเว็บแล้วหน้าจอขาว

4.2 สามสถานะที่ต้องคืน

readStoredRequests() ต้องคืนสถานะหนึ่งในสามค่านี้เสมอ และห้าม throw ออกไป เพราะจะทำให้หน้าจอพังทั้งหน้า

statusเกิดเมื่อโปรแกรมทำอะไรต่อ
'missing'ยังไม่เคยเก็บ — เปิดเว็บครั้งแรกโหลดข้อมูลตัวอย่างแล้วเก็บไว้ · ไม่ต้องแจ้งผู้ใช้
'valid'อ่านได้และผ่านการตรวจครบใช้ข้อมูลนั้นได้เลย
'invalid'อ่านไม่ได้หรือรูปแบบผิดกู้ข้อมูลตัวอย่าง · ต้องแจ้งผู้ใช้
🟡 ทำไม missing ไม่แจ้งแต่ invalid ต้องแจ้ง

การเปิดเว็บครั้งแรกแล้วยังไม่มีข้อมูลเป็นเรื่องปกติ ไม่มีอะไรผิดพลาด · แต่การมีข้อมูลแล้วอ่านไม่ได้แปลว่าผู้ใช้อาจเพิ่งเสียข้อมูลไป ซึ่งเขามีสิทธิ์รู้

4.3 สามแบบที่ถือว่า invalid

ข้อมูลใน storageตรวจเจอด้วยอะไร
{ ไม่ใช่ JSONtry/catch รอบ JSON.parse
{"schemaVersion":99,…}เทียบกับ SCHEMA_VERSION
มีคำร้อง id ซ้ำกัน 2 รายการvalidateRequests() ที่ starter เตรียมไว้ให้

กรณีสุดท้ายน่าสนใจ — ข้อมูลถูกรูปแบบทุกอย่าง แต่มี id ซ้ำ ซึ่งจะทำให้ React แสดงรายการผิดและการลบทำงานผิดพลาด

🔴 กับดักที่พบบ่อยที่สุดของบทนี้

ทำแค่ try/catch แล้วคิดว่าเสร็จ — ผลคือกรณีที่ 2 และ 3 หลุดผ่านไปได้ทั้งคู่

ข่าวดี — checker ตรวจทั้งสามกรณีนี้จริง ถ้าทำไม่ครบจะขึ้นว่ารายการไหนยังไม่ผ่าน

  • parse ได้ ไม่ได้แปลว่าข้อมูลถูก

บทที่ 5

Recovery — แอปที่กู้ตัวเองได้

เวลาอ่าน ≈ 9 นาที

ตรวจเจอว่าข้อมูลเสียแล้ว — คำถามถัดไปคือ แล้วจะทำอะไรต่อ

🟣 ทายก่อนอ่านต่อ

ถ้าคุณเป็นผู้ใช้ แล้วเปิดเว็บมาเจอว่าข้อมูลของตัวเองเสียหาย คุณอยากให้แอปทำอะไร

ทางเลือกผลที่ผู้ใช้ได้ประเมิน
ปล่อยให้พัง หน้าจอขาวใช้อะไรไม่ได้เลย ไม่รู้ว่าเกิดอะไรขึ้นแย่ที่สุด
แสดง error แล้วให้กดลองใหม่กดกี่ครั้งก็เหมือนเดิม เพราะข้อมูลยังเสียอยู่ไม่ช่วย
กู้ข้อมูลตัวอย่างเงียบ ๆใช้งานต่อได้ แต่ไม่รู้ว่าข้อมูลตัวเองหายไปแล้วยังไม่ดีพอ
กู้ข้อมูลตัวอย่าง แล้วแจ้งให้ทราบใช้งานต่อได้ทันที และรู้ว่าเกิดอะไรขึ้น✅ ที่เราจะทำ

5.1 แจ้งผู้ใช้อย่างไรโดยที่ Storage ไม่ต้องรู้จักหน้าจอ

ปัญหาคือ Storage อยู่ชั้นล่างสุด ส่วนกล่องข้อความอยู่ที่หน้าจอชั้นบนสุด — ชั้นล่างไม่ควรรู้จักชั้นบน ไม่งั้นจะกลายเป็นผูกกันแน่นจนแยกไม่ออก

ทางออกคือให้หน้าจอส่งฟังก์ชันลงไป แล้วให้ Service เรียกกลับขึ้นมาเมื่อจำเป็น เรียกว่า callback

// หน้าจอส่งฟังก์ชันลงไป
getRequests({ scenario, onRecovery: setNotice })

// Service เรียกกลับขึ้นมาเมื่อเพิ่งกู้ข้อมูล
if (stored.status === 'invalid') {
  onRecovery?.('พบข้อมูลเดิมที่อ่านไม่ได้ ระบบจึงกู้ข้อมูลตัวอย่างให้แล้ว');
}
🟡 ทำไมต้องมีเครื่องหมายคำถามใน onRecovery?.()

เพราะผู้เรียกบางคนอาจไม่สนใจเรื่องนี้และไม่ส่ง callback มา เช่น getRequestById() ที่เรียก getRequests() ต่ออีกที · เครื่องหมาย ?. ทำให้ข้ามไปเฉย ๆ แทนที่จะพัง

คุณเคยเห็นรูปแบบนี้มาแล้ว — ตอน Week 04 ที่ RequestList รับ onDeleteRequest จาก App.jsx เป็นแนวคิดเดียวกันทุกประการ ต่างแค่คราวนี้เป็นการส่งลงไปข้ามชั้นถึง Service

สรุปบทที่ 5
  • ตรวจเจอว่าเสียแล้วต้องกู้ให้ใช้งานต่อได้ ไม่ใช่แค่แสดง error
  • ต้องเขียนทับที่เก็บด้วยข้อมูลสะอาด ไม่งั้นครั้งหน้าเจออีก
  • missing ไม่ต้องแจ้ง · invalid ต้องแจ้ง
  • ใช้ callback ให้ชั้นล่างแจ้งชั้นบนได้โดยไม่ต้องรู้จักกัน

เฉลย

6.1 cleanup function

ถ้า Effect คืนฟังก์ชันกลับไป React จะเรียกฟังก์ชันนั้นก่อนทำ Effect รอบใหม่ และก่อนที่ component จะถูกถอดออก

useEffect(() => {
  let ignore = false;

  getRequestById(requestId).then((result) => {
    if (ignore) return;          // ไม่เกี่ยวแล้ว ทิ้งไปเลย
    setRequest(result);
    setLoadState('success');
  });

  return () => { ignore = true; };   // React เรียกตอนออกจากหน้า
}, [requestId, reloadKey]);

สังเกตว่าเราไม่ได้ยกเลิกคำขอ — คำขอยังวิ่งไปจนเสร็จตามปกติ เราแค่เลือกไม่ใช้ผลลัพธ์ของมัน

6.2 แล้วทำไม React ถึงเรียก Effect 2 รอบ

ตอนนี้พร้อมรับคำตอบแล้ว

ในโหมดพัฒนา React จงใจ เรียก Effect → เรียก cleanup → เรียก Effect อีกรอบ เพื่อทดสอบว่า Effect ของคุณรับมือกับการถูกเรียกซ้ำได้หรือไม่

ถ้าเขียน Effect ถูกต้องถ้าเขียนผิด
เรียกซ้ำแล้วผลลัพธ์เหมือนเดิม ไม่มีอะไรผิดปกติ เกิดข้อมูลซ้ำ ตัวจับเวลาซ้อนกัน หรือการเชื่อมต่อค้าง — เห็นได้ทันทีตอนพัฒนา ไม่ต้องรอผู้ใช้เจอ
🟢 จุดที่ควรสังเกต

React ไม่ได้แค่บอกว่า "คุณควรเขียน cleanup" แต่สร้างสถานการณ์ให้คุณเห็นปัญหาเองตั้งแต่ตอนพัฒนา · เป็นแนวคิดการออกแบบเครื่องมือที่ดีมาก — ทำให้ความผิดพลาดปรากฏตัวเร็วที่สุดเท่าที่จะเป็นไปได้

🟡 ในการใช้งานจริงเป็นอย่างไร

เมื่อ npm run build แล้วนำขึ้นใช้งานจริง Effect จะทำงานรอบเดียว · พฤติกรรม 2 รอบมีเฉพาะตอนพัฒนาเท่านั้น

🔴 checker ตรวจเรื่องนี้ไม่ได้

cleanup guard เป็นการป้องกันบั๊กที่ยังไม่เกิด ตัวเลข checker จึงไม่ขยับเลยหลังเพิ่มเข้าไป · ต้องพิสูจน์ด้วยการกดสลับหน้าเร็ว ๆ ระหว่างที่ยังโหลดไม่เสร็จ แล้วดูว่ามีอะไรผิดปกติหรือไม่
