### 04a-1 · เขียนข้อมูลลงที่เก็บ (12 นาที)

เปิด `src/services/requestStorage.js` แล้วทำ `TODO 5B-B`

**สิ่งที่ต้องเขียนลงไปไม่ใช่ array ตรง ๆ** แต่เป็นกล่องที่มีข้อมูลกำกับด้วย เรียกว่า envelope

```json
{
  "schemaVersion": 1,
  "updatedAt": "2026-08-13T09:15:00.000Z",
  "requests": [ … ]
}
```

**ลำดับที่ต้องทำ**

1. ตรวจด้วย `validateRequests()` ที่ starter เตรียมไว้ให้ ถ้าไม่ผ่านให้ `throw`
2. สร้าง envelope
3. `setItem` — **อย่าลืม `JSON.stringify`**

> **ที่นี่ `throw` ได้** เพราะการเขียนข้อมูลผิดรูปแบบเป็นความผิดพลาดของโปรแกรมเราเอง ไม่ใช่ข้อมูลจากภายนอก · ต่างจาก `readStoredRequests()` ที่ห้าม `throw` เด็ดขาด

**ทดสอบก่อนไปต่อ** — เปิด DevTools → Application → Local Storage → ต้องเห็นคีย์ `engse203-campus-requests-v1` และค่าที่เป็นข้อความ JSON ที่อ่านออก

### 04a-4 · เพิ่มคำร้องใหม่ (15 นาที)

ทำ `TODO 5B-4` ใน service และ `TODO 5B-CP04a` ใน `NewRequestPage.jsx`

**สิ่งที่ `addRequest()` ต้องทำตามลำดับ**

1. ตรวจข้อมูลก่อนใช้งาน
2. โหลดรายการปัจจุบัน
3. สร้างรหัสที่ขึ้นต้นด้วย `REQ-` และไม่ซ้ำกับที่มีอยู่
4. ตัดช่องว่างหัวท้ายทุกฟิลด์ที่เป็นข้อความ
5. `status` เริ่มต้นเป็น `'pending'` เสมอ
6. **บันทึกให้เสร็จก่อน** แล้วค่อยคืน object ใหม่

> **ข้อ 6 สำคัญ** — ต้องบันทึกสำเร็จก่อนถึงจะบอกหน้าจอว่าสำเร็จ ไม่ใช่บอกว่าสำเร็จแล้วค่อยบันทึก เพราะถ้าบันทึกพลาด ผู้ใช้จะเข้าใจผิดว่าข้อมูลถูกเก็บแล้ว

**เรื่องการตรวจข้อมูล — จุดที่พลาดง่ายมาก**

อย่าเขียนแบบนี้

```js
if (input.requesterName?.trim().length < 2) throw new Error('ชื่อผู้แจ้งไม่ถูกต้อง');
```

ถ้า `requesterName` เป็น `undefined` เครื่องหมาย `?.` จะลัดวงจรทำให้ทั้งนิพจน์เป็น `undefined` แล้ว `undefined < 2` ให้ผลเป็น `false` — **ข้อมูลที่ไม่มีชื่อเลยจะผ่านการตรวจไปได้** แล้วไปพังเป็น `TypeError` ที่บรรทัดถัดไป ซึ่งผู้ใช้จะเห็นข้อความภาษาโปรแกรมเมอร์แทนที่จะเห็นว่า "กรุณากรอกชื่อ"

ให้ตรวจชนิดข้อมูลให้ชัดก่อนเสมอ

```js
const name = typeof input.requesterName === 'string' ? input.requesterName.trim() : '';
if (name.length < 2) throw new Error('ชื่อผู้แจ้งไม่ถูกต้อง');
```

**ใน `NewRequestPage.jsx`** — เรียก `addRequest()` แล้วใช้ `useNavigate()` พาผู้ใช้ไปหน้ารายละเอียดของคำร้องที่เพิ่งสร้าง

**ทดสอบ** — เพิ่มคำร้อง → ต้องเด้งไปหน้ารายละเอียด **และเห็นข้อมูลจริง** ถ้าเจอ "ไม่พบคำร้อง" แสดงว่ายังไม่ได้ทำ 04a-3

### 04b-3 · แจ้งผู้ใช้เมื่อกู้ข้อมูล (15 นาที)

ทำ `TODO 5B-2b` และ `TODO 5B-3b`

**โจทย์คือ** Storage อยู่ชั้นล่างสุด ส่วนกล่องข้อความอยู่ที่หน้าจอชั้นบนสุด — **ชั้นล่างไม่ควรรู้จักชั้นบน**

**ทางออก** ให้หน้าจอส่งฟังก์ชันลงไป แล้วให้ Service เรียกกลับขึ้นมาเมื่อจำเป็น

```js
// ใน DashboardPage
getRequests({ scenario, onRecovery: setNotice })

// ใน loadNormalRequests
if (stored.status === 'invalid') {
  onRecovery?.('พบข้อมูลเดิมที่อ่านไม่ได้ ระบบจึงกู้ข้อมูลตัวอย่างให้แล้ว');
}
```

**คุณเคยเห็นรูปแบบนี้มาแล้ว** — ตอน Week 04 ที่ `RequestList` รับ `onDeleteRequest` มาจาก `App.jsx` เป็นแนวคิดเดียวกันเป๊ะ ต่างแค่คราวนี้ส่งลงไปลึกกว่า ถึงชั้น Service

**ทำไมต้องมี `?.` ใน `onRecovery?.()`** — เพราะผู้เรียกบางคนไม่ส่ง callback มา เช่น `getRequestById()` ที่เรียก `getRequests()` ต่ออีกที · ถ้าไม่ใส่จะพัง

**สำคัญ** — เรียก `onRecovery` เฉพาะเมื่อ `status` เป็น `'invalid'` เท่านั้น **ไม่ใช่ `'missing'`** เพราะการเปิดเว็บครั้งแรกแล้วยังไม่มีข้อมูลเป็นเรื่องปกติ ไม่มีอะไรผิดพลาด

## 7. cleanup guard

**เวลา 30 นาที · ดูผู้สอนสาธิตก่อน แล้วทำเองใน 2 ไฟล์**

### ⚠ อ่านก่อน — ตัวเลขจะไม่ขยับ

`npm run check` จะยังได้ **133/133 เท่าเดิม** หลังทำช่วงนี้

**ไม่ใช่ว่าคุณทำผิด** — cleanup guard เป็นการป้องกันบั๊กที่ยังไม่เกิด checker จึงตรวจไม่ได้ เหมือนกับ CP01 เมื่อสัปดาห์ที่แล้วที่ refactor แล้วตัวเลขไม่ขยับ

### ปัญหาที่กำลังแก้

ผู้ใช้เปิดหน้า `#/requests/REQ-001` ซึ่งใช้เวลาโหลด 0.4 วินาที แต่ผ่านไป 0.1 วินาที เขากดกลับไปหน้า Dashboard

อีก 0.3 วินาทีต่อมา ข้อมูลของ `REQ-001` โหลดเสร็จ แล้วเรียก `setRequest()` ของหน้าที่**ผู้ใช้ออกไปแล้ว** — เรียกว่า **stale update**

### วิธีแก้

```js
useEffect(() => {
  let ignore = false;

  getRequestById(requestId).then((result) => {
    if (ignore) return;          // ไม่เกี่ยวแล้ว ทิ้งไปเลย
    setRequest(result);
    setLoadState('success');
  });

  return () => { ignore = true; };   // React เรียกตอนออกจากหน้า
}, [requestId, reloadKey]);
```

**สังเกตว่าเราไม่ได้ยกเลิกคำขอ** — คำขอยังวิ่งไปจนเสร็จตามปกติ เราแค่เลือกไม่ใช้ผลลัพธ์ของมัน

ทำใน **2 ไฟล์** — `DashboardPage.jsx` และ `RequestDetailPage.jsx` (มีคอมเมนต์ `TODO 5B: เพิ่ม cleanup guard` กำกับไว้)

### แล้วที่ Effect ทำงาน 2 รอบล่ะ

นี่คือคำตอบของคำถามที่ค้างมาจากสัปดาห์ที่แล้ว

React จงใจ **เรียก Effect → เรียก cleanup → เรียก Effect อีกรอบ** ในโหมดพัฒนา เพื่อทดสอบว่า Effect ของคุณรับมือกับการถูกเรียกซ้ำได้หรือไม่

- **เขียนถูก** → เรียกซ้ำแล้วผลเหมือนเดิม ไม่มีอะไรผิดปกติ
- **เขียนผิด** → เกิดข้อมูลซ้ำหรือการเชื่อมต่อค้าง แล้วคุณจะเห็นตั้งแต่ตอนพัฒนา ไม่ต้องรอผู้ใช้เจอ

ตอน `npm run build` ขึ้นใช้งานจริง Effect จะทำงาน**รอบเดียว**

### วิธีพิสูจน์ว่าทำงานจริง

เนื่องจาก checker ตรวจไม่ได้ ต้องพิสูจน์ด้วยตา

1. เปิด DevTools → Network → ตั้ง throttle เป็น **Slow 3G**
2. เปิด `#/requests/REQ-001`
3. กดกลับ Dashboard ทันทีก่อนโหลดเสร็จ
4. สังเกตว่าไม่มีอะไรกะพริบหรือเปลี่ยนแปลงผิดปกติ

### คำถามที่ต้องตอบได้

> **ทำไม React เรียก Effect 2 รอบตอนพัฒนา**
