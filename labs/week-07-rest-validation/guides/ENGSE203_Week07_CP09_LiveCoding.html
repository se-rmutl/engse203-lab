ดูผลที่ 3 ที่ — นี่คือหัวใจของช่วงนี้

7 นาที

① Console — จะเห็น error สีแดง

Access to fetch at 'http://localhost:3001/api/requests'
from origin 'http://localhost:5173' has been blocked by CORS policy:
No 'Access-Control-Allow-Origin' header is present on the requested resource.
สอนให้อ่าน error เป็น "ข้อความนี้บอกครบเลยนะครับ — เรียกจากไหน (origin 5173) ไปที่ไหน (fetch at 3001) และขาดอะไร (No Access-Control-Allow-Origin header)
error ที่ดีจะบอกครบแบบนี้ · อ่านให้เป็นแล้วจะแก้ได้เร็วขึ้นมาก"

② Network tab — คลิกที่ requests แล้วดู Response Headers

ดูอะไรจะเห็น
Statusอาจขึ้น 200 หรือ (failed)
Response Headersไม่มี Access-Control-Allow-Origin

③ Terminal ของ API — สลับไปดู Terminal 1

GET /api/requests 200 3.221 ms
⭐ จุดที่ต้องเน้นให้หนักที่สุดของช่วงนี้

"เห็นไหมครับ — คำขอไปถึง API แล้ว และ API ก็ตอบ 200 ไปแล้วด้วย"

"แปลว่า API ไม่ได้มีปัญหาอะไรเลย — เบราว์เซอร์ต่างหากที่เป็นคนบล็อกไม่ให้โค้ดเราอ่าน response"

ทำไมต้องย้ำจุดนี้ เพราะนักศึกษาส่วนใหญ่จะเข้าใจผิดว่า "API ตอบ CORS error กลับมา" แล้วไปนั่งแก้โค้ด fetch ฝั่ง React อยู่นาน · ถ้าเข้าใจตั้งแต่ตอนนี้ว่าใครเป็นคนบล็อก จะรู้ทันทีว่าต้องไปแก้ที่ฝั่งไหน
3

พิสูจน์ด้วย Postman

5 นาที
สาธิตให้เห็นชัด "ทีนี้ผมจะเอา URL เดียวกันเป๊ะ ไปยิงใน Postman" 
GET http://localhost:3001/api/requests
ผลที่ได้ 200 พร้อมข้อมูลครบ ไม่มีปัญหาอะไรเลย
ถามห้อง "URL เดียวกัน API ตัวเดียวกัน แต่ทำไม Postman ได้ แต่เบราว์เซอร์ไม่ได้ครับ"
คำตอบ — เพราะ Postman ไม่ใช่เบราว์เซอร์ · กฎ Same-Origin Policy เป็นกฎของเบราว์เซอร์เท่านั้น
เชื่อมกลับ Week 06 "นี่คือเหตุผลที่สัปดาห์ที่แล้วเราไม่เคยเจอปัญหานี้เลย — เพราะเราทดสอบด้วย Postman ตลอด"
✓

ผ่าน CP09 เมื่อ

✓เห็น CORS error ใน Console ด้วยตาตัวเอง
✓เห็นใน terminal ของ API ว่าคำขอไปถึงแล้ว
✓ยิง URL เดียวกันใน Postman ได้ข้อมูลปกติ
✓ชี้ได้ว่า Response Headers ไม่มี Access-Control-Allow-Origin
คำถาม Checkpoint ถ้า API ตอบ 200 แล้ว ทำไมโค้ดเราถึงอ่านข้อมูลไม่ได้
ประโยคเชื่อมไป CP10 "ทีนี้เรารู้แล้วว่าใครเป็นคนบล็อก — แล้วใครเป็นคนอนุญาตได้ล่ะครับ
คำตอบคือ เซิร์ฟเวอร์ · ต่อไปเราจะไปเปิดที่ฝั่ง API"
