บทที่ 2 · กลุ่มที่ 1

Origin และ Same-Origin Policy

เวลาอ่าน ≈ 11 นาที · รากของเรื่อง CORS ทั้งหมด

ก่อนจะเข้าใจ CORS ต้องเข้าใจก่อนว่าเบราว์เซอร์มองว่า "ที่เดียวกัน" คืออะไร

Origin

ที่อยู่ของเว็บหนึ่ง ๆ ประกอบด้วย 3 ส่วน — protocol + host + port · ถ้าสามส่วนนี้เหมือนกันทั้งหมดถึงจะนับว่าเป็น origin เดียวกัน · ต่างแม้แต่ส่วนเดียวก็ถือว่าคนละที่

Same-Origin Policy

กฎความปลอดภัยของเบราว์เซอร์ที่ว่า โค้ดจาก origin หนึ่ง ห้ามอ่านข้อมูลจากอีก origin หนึ่ง โดยไม่ได้รับอนุญาต · เป็นกฎที่เบราว์เซอร์ทุกตัวบังคับใช้มาตั้งแต่ยุคแรก ๆ ของเว็บ

2.1 ทำไมต้องมีกฎนี้ — ตัวอย่างที่ทำให้เห็นภาพ

🟪 ถ้าไม่มีกฎนี้จะเกิดอะไร

สมมติคุณล็อกอินธนาคารไว้ในแท็บหนึ่ง แล้วเปิดเว็บแปลก ๆ ในอีกแท็บ

ถ้าไม่มี Same-Origin Policy — เว็บแปลก ๆ นั้นจะเขียน JavaScript เรียก API ของธนาคารได้ทันที โดยใช้ session ที่คุณล็อกอินไว้ แล้วอ่านยอดเงินหรือโอนเงินออกไปได้เลย · กฎนี้คือสิ่งที่กันไม่ให้เกิดเรื่องแบบนั้น

🟥 ความเข้าใจผิดที่พบบ่อยที่สุด

"API ของผมมีปัญหา เลยตอบ CORS error กลับมา" — ไม่ใช่

API ตอบข้อมูลมาปกติ แต่เบราว์เซอร์เป็นคนบล็อกไม่ให้โค้ดเห็น response นั้น · CORS error ไม่ได้มาจากเซิร์ฟเวอร์ แต่มาจากเบราว์เซอร์ที่อยู่ตรงกลาง

2.2 หลักฐานว่าเบราว์เซอร์เป็นคนบล็อก

ลองสังเกตสิ่งนี้

เรียก API ด้วยอะไรติด CORS ไหมเพราะอะไร
React ในเบราว์เซอร์ติดเบราว์เซอร์บังคับใช้ Same-Origin Policy
Postmanไม่ติดไม่ใช่เบราว์เซอร์ ไม่มีกฎนี้
curl ใน terminalไม่ติดไม่ใช่เบราว์เซอร์
เซิร์ฟเวอร์อื่นเรียก API เราไม่ติดไม่ใช่เบราว์เซอร์
🟨 นี่คือเหตุผลที่ Week 06 ไม่เจอปัญหานี้

สัปดาห์ที่แล้วเราทดสอบด้วย Postman ตลอด จึงไม่เคยเจอ CORS · พอเปลี่ยนมาเรียกจากเบราว์เซอร์ถึงเจอทันที

  • origin = protocol + host + port · ต่างแม้แต่ส่วนเดียวถือว่าคนละที่
  • Same-Origin Policy คือกฎของเบราว์เซอร์ ที่ห้ามอ่านข้อมูลข้าม origin
  • มีไว้กันเว็บอันตรายเรียก API ที่เราล็อกอินไว้
  • Postman และ curl ไม่ติดกฎนี้ เพราะไม่ใช่เบราว์เซอร์

บทที่ 3 · กลุ่มที่ 1

CORS — ทางออกที่เซิร์ฟเวอร์เป็นคนเปิดให้

เวลาอ่าน ≈ 13 นาที · บทที่สำคัญที่สุดของสัปดาห์

CORS (Cross-Origin Resource Sharing)

กลไกที่ให้ เซิร์ฟเวอร์เป็นคนบอกเบราว์เซอร์ ว่า "origin ไหนบ้างที่ฉันอนุญาตให้เรียกฉันได้" · เบราว์เซอร์จะยอมให้โค้ดอ่าน response ก็ต่อเมื่อเซิร์ฟเวอร์ส่ง header อนุญาตมาด้วย

🟪 เทียบกับของที่คุ้น

คิดถึงรายชื่อแขกในงานเลี้ยง — เจ้าภาพ (เซิร์ฟเวอร์) ทำรายชื่อไว้ว่าใครเข้าได้บ้าง · พนักงานหน้างาน (เบราว์เซอร์) เช็คว่าคนที่มาอยู่ในรายชื่อไหม ถ้าไม่อยู่ก็ไม่ให้เข้า · คนที่ตัดสินว่าใครเข้าได้คือเจ้าภาพ ไม่ใช่พนักงาน

3.1 CORS ทำงานอย่างไร

🟥 จุดที่ต้องเข้าใจให้ชัด

แม้จะติด CORS คำขอก็ไปถึงเซิร์ฟเวอร์แล้ว และเซิร์ฟเวอร์ก็ทำงานไปแล้ว — ถ้าเป็น POST ข้อมูลก็ถูกสร้างจริง ๆ · เบราว์เซอร์แค่ไม่ให้โค้ดเราอ่าน response · CORS จึงไม่ใช่ระบบรักษาความปลอดภัยของ API การป้องกันจริงต้องทำที่เซิร์ฟเวอร์ (เช่น ตรวจสิทธิ์)

3.2 Preflight — คำขอที่ถูกส่งไปถามก่อน

สำหรับคำขอที่อาจเปลี่ยนแปลงข้อมูล (เช่น POST, PUT, DELETE) เบราว์เซอร์จะส่งคำขอไปถามก่อนว่าทำได้ไหม

Preflight request

คำขอ OPTIONS ที่เบราว์เซอร์ส่งไปถามเซิร์ฟเวอร์ล่วงหน้าว่า "ฉันจะส่ง POST มานะ อนุญาตไหม" · ถ้าเซิร์ฟเวอร์ตอบว่าได้ ถึงจะส่งคำขอจริงตามไป · เกิดขึ้นอัตโนมัติ เราไม่ได้เขียนเอง

// ① เบราว์เซอร์ส่งไปถามก่อน (เราไม่ได้เขียน — เบราว์เซอร์ทำเอง)
OPTIONS /api/requests
Origin: http://localhost:5173
Access-Control-Request-Method: POST

// ② เซิร์ฟเวอร์ตอบว่าอนุญาต
204 No Content
Access-Control-Allow-Origin: http://localhost:5173
Access-Control-Allow-Methods: GET,POST,PUT,DELETE

// ③ เบราว์เซอร์ถึงจะส่งคำขอจริง
POST /api/requests
{ "requesterName": "..." }
🟨 สังเกตใน DevTools

เวลากด POST จากแอป คุณจะเห็นใน Network tab 2 บรรทัด — OPTIONS หนึ่งบรรทัดตามด้วย POST อีกบรรทัด · ถ้าเห็นแค่ OPTIONS แล้วไม่มี POST ตามมา แปลว่า preflight ไม่ผ่าน

3.3 เปิด CORS ใน Express

import cors from 'cors';

// ต้องอยู่บนสุด ก่อน middleware และ route ทั้งหมด
app.use(cors({ origin: 'http://localhost:5173' }));
🟥 กับดัก 2 อันของการเปิด CORS

หนึ่ง · วางผิดที่ — ถ้าเขียน app.use(cors()) ไว้หลัง route คำขอ preflight จะไปไม่ถึง เพราะ route ตอบไปก่อนแล้ว · ต้องอยู่บนสุดเสมอ

สอง · ใช้ origin: '*' แบบไม่คิด — แปลว่าอนุญาตทุกเว็บในโลก · ตอนพัฒนาสะดวก แต่ถ้าเผลอติดไปตอนใช้งานจริงจะเปิดช่องให้เว็บใดก็ได้เรียก API เรา

3.4 CORS error หน้าตาเป็นอย่างไร

Access to fetch at 'http://localhost:3001/api/requests'
from origin 'http://localhost:5173' has been blocked by CORS policy:
No 'Access-Control-Allow-Origin' header is present on the requested resource.

อ่านให้เป็น — ข้อความบอกครบว่า เรียกจากไหน (origin 'http://localhost:5173') ไปที่ไหน (fetch at 'http://localhost:3001/...') และขาดอะไร (No 'Access-Control-Allow-Origin' header)

🟩 ทายก่อนอ่านต่อ

เจอ CORS error แล้ว ควรไปแก้ที่ไหน — โค้ด React หรือโค้ด API

เฉลย

แก้ที่ API — เพราะเซิร์ฟเวอร์คือคนที่ต้องส่ง header อนุญาตมา

แก้ฝั่ง React ไม่ได้เลย · ต่อให้เขียน fetch ยังไงก็ไม่ช่วย เพราะเบราว์เซอร์ไม่ได้ดูว่าเราเขียนโค้ดยังไง มันดูว่าเซิร์ฟเวอร์ส่ง header มาหรือเปล่า

สรุปบทที่ 3
  • CORS คือกลไกให้เซิร์ฟเวอร์บอกเบราว์เซอร์ว่าอนุญาต origin ไหนบ้าง
  • คำขอไปถึงเซิร์ฟเวอร์จริงเสมอ — เบราว์เซอร์แค่บล็อกไม่ให้โค้ดอ่าน response
  • preflight (OPTIONS) คือคำขอที่เบราว์เซอร์ส่งไปถามก่อนสำหรับ POST/PUT/DELETE
  • app.use(cors(...)) ต้องอยู่บนสุด ก่อน route ทั้งหมด
  • เจอ CORS error ให้แก้ที่ API ไม่ใช่ React

เวลาอ่าน ≈ 10 นาที

ในโค้ดเรามีค่าที่ไม่ควรฝังไว้ตายตัว เช่น พอร์ต, ที่อยู่ของ API, รหัสผ่านฐานข้อมูล

🟩 ทายก่อนอ่านต่อ

ถ้าเราเขียน fetch('http://localhost:3001/api/requests') ไว้ในโค้ด แล้ววันหนึ่งเอา API ขึ้นเซิร์ฟเวอร์จริงที่ https://api.rmutl.ac.th — ต้องแก้กี่ที่

เฉลย

ทุกที่ที่เขียน URL ไว้ — ซึ่งถ้ากระจายอยู่ 10 ไฟล์ก็ต้องแก้ 10 ที่ และถ้าลืมที่เดียวก็พังเฉพาะจุดนั้น หาสาเหตุยาก

ยิ่งกว่านั้น — ถ้าต้องสลับไปมาระหว่างเครื่องตัวเองกับเซิร์ฟเวอร์จริง จะต้องแก้โค้ดกลับไปกลับมาทุกครั้ง และมีโอกาสเผลอ commit ค่าผิดขึ้นไป

Environment variable

ค่าที่อยู่นอกโค้ด และเปลี่ยนได้ตามสภาพแวดล้อมที่รัน · เครื่องนักศึกษาใช้ค่าหนึ่ง เซิร์ฟเวอร์จริงใช้อีกค่าหนึ่ง โดยที่โค้ดเป็นชุดเดียวกัน

4.1 ฝั่ง API — ไฟล์ .env

# api/.env
PORT=3001
CORS_ORIGIN=http://localhost:5173
NODE_ENV=development

แล้วรวมการอ่านค่าไว้ที่ไฟล์เดียว

// api/src/config.js — ที่เดียวที่อ่าน process.env
import 'dotenv/config';

export const config = {
  port: Number(process.env.PORT ?? 3001),
  corsOrigin: process.env.CORS_ORIGIN ?? 'http://localhost:5173',
  nodeEnv: process.env.NODE_ENV ?? 'development',
  get isProduction() { return this.nodeEnv === 'production'; },
};

API Client — ชั้นกลางที่คุยกับเซิร์ฟเวอร์

เวลาอ่าน ≈ 12 นาที

ก่อนจะแก้ requestService.js เราจะสร้างไฟล์ใหม่ขึ้นมาชั้นหนึ่งก่อน

API Client

ไฟล์ที่เป็นที่เดียวในโปรเจกต์ที่เรียก fetch() · จัดการเรื่องซ้ำ ๆ ให้ครบ — ต่อ URL, ใส่ header, แปลง JSON, จัดการ error — แล้วให้ที่อื่นเรียกผ่านมันอย่างเดียว

🟪 ทำไมต้องมีอีกชั้น

เทียบกับฝั่ง backend — apiClient เหมือน middleware ที่จัดการเรื่องซ้ำ ๆ ให้ทุก route · ถ้าไม่มี เราจะต้องเขียน "ต่อ URL, ใส่ header, เช็ค response.ok, แปลง JSON" ซ้ำในทุกฟังก์ชันของ service ซึ่งมี 6 ฟังก์ชัน = เขียนซ้ำ 6 รอบ

5.1 สิ่งที่ apiClient ต้องจัดการ — 4 กรณี

กรณีเกิดเมื่อต้องทำอะไร
ต่อเซิร์ฟเวอร์ไม่ได้API ไม่ได้เปิด · เน็ตหลุดfetch โยน error → แปลงเป็นข้อความที่ผู้ใช้เข้าใจ
ตอบ 4xx / 5xxข้อมูลผิด · ไม่พบ · เซิร์ฟเวอร์พังโยน ApiError พร้อม status
ตอบ 204DELETE สำเร็จคืน null — ไม่มี body ให้ parse
ตอบ 2xx อื่นสำเร็จปกติคืน response.json()
🟥 กับดักที่สำคัญที่สุด — fetch ไม่โยน error เมื่อได้ 404

เราเจอเรื่องนี้มาแล้วใน Week 05 — fetch จะ resolve สำเร็จแม้เซิร์ฟเวอร์ตอบ 404 หรือ 500

const res = await fetch(url);   // ได้ 404 ก็ไม่ throw
if (!res.ok) { … }            // ต้องเช็คเอง

fetch จะโยน errorเฉพาะตอนต่อเซิร์ฟเวอร์ไม่ได้เลย เช่น API ไม่ได้เปิด

5.2 โครงของ apiClient

export class ApiError extends Error {
  constructor(message, status) {
    super(message);
    this.name = 'ApiError';
    this.status = status;   // เก็บ status ไว้ให้คนเรียกตัดสินใจได้
  }
}

export async function apiFetch(path, options = {}) {
  let response;
  try {
    response = await fetch(`${BASE_URL}${path}`, {
      headers: { 'Content-Type': 'application/json', ...options.headers },
      ...options,
    });
  } catch {
    // ① ต่อเซิร์ฟเวอร์ไม่ได้เลย
    throw new ApiError('ติดต่อเซิร์ฟเวอร์ไม่ได้ — ตรวจว่าเปิด API แล้วหรือยัง', 0);
  }

  if (!response.ok) {
    // ② เซิร์ฟเวอร์ตอบ แต่เป็น 4xx/5xx
    throw new ApiError(await parseError(response), response.status);
  }

  if (response.status === 204) return null;   // ③ ไม่มี body
  return response.json();                       // ④ ปกติ
}
🟨 ทำไมต้องเก็บ status ไว้ใน error

เพราะคนเรียกต้องตัดสินใจต่างกันตาม status — 404 อาจไม่ใช่ความผิดพลาด (แค่ไม่มีคำร้องรหัสนั้น) แต่ 500 คือระบบพังจริง · ถ้าไม่เก็บ status ไว้ จะแยกไม่ออก

สรุปบทที่ 5
  • apiClient เป็นชั้นเดียวที่เรียก fetch() — ไม่ต้องเขียนโค้ดซ้ำใน service
  • ต้องจัดการ 4 กรณี: ต่อไม่ได้ · 4xx/5xx · 204 · 2xx ปกติ
  • fetch ไม่โยน error เมื่อได้ 404 — ต้องเช็ค response.ok เอง
  • ApiError เก็บ status ไว้ให้คนเรียกตัดสินใจ

export async function getRequestById(requestId) {
  try {
    return await apiFetch(`/api/requests/${encodeURIComponent(requestId)}`);
  } catch (error) {
    // 404 ไม่ใช่ความผิดพลาดของระบบ — แปลว่าไม่มีคำร้องรหัสนี้
    if (error instanceof ApiError && error.status === 404) return null;
    throw error;   // error อื่นปล่อยผ่านไปให้หน้าจอจัดการ
  }
}

10.2 โครงของ test

import { test, before, describe } from 'node:test';
import assert from 'node:assert/strict';
import request from 'supertest';

describe('GET /api/requests', () => {
  test('คืนรายการทั้งหมด พร้อม status 200', async () => {
    const res = await request(app).get('/api/requests');
    assert.equal(res.status, 200);
    assert.ok(Array.isArray(res.body));
  });
});
🟨 supertest ยิง request จริงโดยไม่ต้องเปิดเซิร์ฟเวอร์

มันสร้างเซิร์ฟเวอร์ชั่วคราวขึ้นมาเองแล้วปิดให้อัตโนมัติ · จึงรัน test พร้อมกันหลายไฟล์ได้โดยไม่ชนพอร์ต และไม่ต้องจำว่าต้องเปิด API ก่อน
