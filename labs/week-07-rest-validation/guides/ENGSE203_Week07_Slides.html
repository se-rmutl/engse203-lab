Origin = protocol + host + port

React กับ API อยู่เครื่องเดียวกัน แต่เบราว์เซอร์ถือว่าคนละที่ เพราะพอร์ตต่างกัน

บทที่ 2 / 10 · Origin & SOP เหตุผลที่ต้องมีกฎนี้

Same-Origin Policy กันอะไร

บทที่ 3 / 10 · CORS กลไกการทำงาน

CORS — เซิร์ฟเวอร์เป็นคนเปิดให้

คำขอไปถึงเซิร์ฟเวอร์จริงและเซิร์ฟเวอร์ทำงานไปแล้ว · เบราว์เซอร์แค่ไม่ให้โค้ดเราอ่าน response

บทที่ 3 / 10 · CORS ลองเล่น — สลับเปิด/ปิด CORS

เห็นผลของการเปิด CORS

เกิดอะไรขึ้น
— กดปุ่มด้านบน —
โค้ดของเราได้อะไร
—

สังเกต — ทั้ง 3 กรณี เซิร์ฟเวอร์ตอบข้อมูลกลับมาเหมือนกันหมด ต่างกันที่เบราว์เซอร์ยอมให้เห็นหรือไม่

บทที่ 3 / 10 · CORS กรณีพิเศษของ POST/PUT/DELETE

Preflight — ถูกส่งไปถามก่อน

// ① เบราว์เซอร์ส่งไปถามก่อน — เราไม่ได้เขียน มันทำเอง
OPTIONS /api/requests
Access-Control-Request-Method: POST

// ② เซิร์ฟเวอร์ตอบว่าอนุญาต
204 No Content
Access-Control-Allow-Methods: GET,POST,PUT,DELETE

// ③ เบราว์เซอร์ถึงจะส่งคำขอจริง
POST /api/requests

สังเกตใน DevTools — เวลากด POST จะเห็น 2 บรรทัดใน Network · OPTIONS ตามด้วย POST · ถ้าเห็นแค่ OPTIONS แปลว่า preflight ไม่ผ่าน

บทที่ 3 / 10 · CORS ทดลองความเข้าใจ

เจอ CORS error ควรแก้ที่ไหน

Access to fetch at 'http://localhost:3001/api/requests'
from origin 'http://localhost:5173' has been blocked by CORS policy:
No 'Access-Control-Allow-Origin' header is present.

ควรไปแก้ที่ไหน

เพราะเบราว์เซอร์ไม่ได้ดูว่าเราเขียนโค้ดยังไง — มันดูว่าเซิร์ฟเวอร์ส่ง Access-Control-Allow-Origin มาหรือเปล่า · เขียน fetch แบบไหนก็ไม่ช่วย

บทที่ 3 / 10 · CORS

จบบทที่ 3 — CORS

✓ สิ่งที่ต้องจำจากบทนี้

  • CORS คือกลไกให้ เซิร์ฟเวอร์ บอกเบราว์เซอร์ว่าอนุญาต origin ไหนบ้าง
  • คำขอไปถึงเซิร์ฟเวอร์จริงเสมอ — เบราว์เซอร์แค่บล็อกไม่ให้โค้ดอ่าน response
  • preflight (OPTIONS) ถูกส่งไปถามก่อนสำหรับ POST/PUT/DELETE
  • เจอ CORS error ให้แก้ที่ API ไม่ใช่ React

Environment Variables

ที่อยู่ของ API ไม่ควรฝังไว้ในโค้ด — เพราะเครื่องนักศึกษา เครื่องทดสอบ และเซิร์ฟเวอร์จริงใช้ค่าต่างกัน

🏫 เรียนและลงมือในห้อง≈ 10 นาที
บทที่ 4 / 10 · Environment Config เหตุผลก่อน

ทำไมห้ามฝังที่อยู่ API ไว้ในโค้ด

ถ้าเขียน URL ไว้ในโค้ด แล้ววันหนึ่งย้ายขึ้นเซิร์ฟเวอร์จริง

ต้องไล่แก้ทุกที่ที่เขียน URL ไว้ · ถ้ากระจาย 10 ไฟล์ก็ต้องแก้ 10 จุด ลืมที่เดียวก็พังเฉพาะจุดนั้น หาสาเหตุยาก
และถ้าต้องสลับไปมาระหว่างเครื่องตัวเองกับเซิร์ฟเวอร์ ต้องแก้โค้ดกลับไปกลับมาทุกครั้ง — มีโอกาสเผลอ commit ค่าผิดขึ้นไป

บทที่ 4 / 10 · Environment Config กับดัก 3 อัน

เรื่องที่พลาดกันบ่อยเรื่อง .env

① process.env ได้ string เสมอ — process.env.PORT ได้ "3001" ไม่ใช่ 3001 · ต้อง Number() เอง

② ฝั่ง Vite ต้องขึ้นต้นด้วย VITE_ — ตั้งชื่อ API_BASE_URL เฉย ๆ จะได้ undefined
เพราะโค้ดฝั่งเบราว์เซอร์ผู้ใช้เปิดดูได้หมด · Vite จึงส่งเฉพาะตัวที่ตั้งใจให้เปิดเผย ไม่งั้นรหัสผ่านฐานข้อมูลจะหลุด

③ ห้าม commit .env — ใส่ .gitignore เสมอ แล้ว commit .env.example ที่มีแต่ชื่อตัวแปรแทน

รวมการอ่านไว้ที่ config.js ไฟล์เดียว — เปิดไฟล์เดียวรู้ทันทีว่าแอปต้องการค่าอะไรบ้างถึงจะรันได้

CP10 · เปิด CORS + Environment Config

// ① config.js — รวมค่าตั้งค่าไว้ที่เดียว
export const config = {
  port: Number(process.env.PORT ?? 3001),
  corsOrigin: process.env.CORS_ORIGIN ?? 'http://localhost:5173',
};

// ② app.js — ต้องอยู่บนสุด ก่อน middleware และ route ทั้งหมด
app.use(cors({ origin: config.corsOrigin }));

// ③ server.js — ใช้ config.port แทนเลขฝังในโค้ด
app.listen(config.port, ...);

⚠ วางผิดที่แล้วพัง — ถ้าเขียน cors() หลัง route คำขอ preflight จะไปไม่ถึง เพราะ route ตอบไปก่อน

    return await apiFetch(`/api/requests/${encodeURIComponent(requestId)}`);
  } catch (error) {
    // 404 ไม่ใช่ความผิดพลาดของระบบ — แปลว่าไม่มีคำร้องรหัสนี้
    if (error instanceof ApiError && error.status === 404) return null;
    throw error;
  }
}

ถ้าไม่แปลงจะเกิดอะไร
