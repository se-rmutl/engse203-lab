เปิดช่วงด้วยเหตุผล "ตอน Week 05 ข้อมูลอยู่ในเครื่อง อ่านเสร็จแทบทันที เราเลยแทบไม่เห็นสถานะ loading
ตอนนี้ข้อมูลอยู่คนละโปรแกรม — ความช้าและความล้มเหลวเป็นเรื่องจริง"
สถานะเกิดเมื่อผู้ใช้ควรเห็น
loadingกำลังรอ API ตอบ"กำลังโหลด…" หรือ skeleton
successได้ข้อมูลแล้วรายการตามปกติ
emptyสำเร็จ แต่ไม่มีรายการ"ยังไม่มีคำร้อง" + ปุ่มสร้างใหม่
errorผิดพลาดข้อความที่บอกว่าควรทำอะไรต่อ + ปุ่มลองใหม่

error ต้องต่างกันตามสาเหตุ

catch (error) {
  if (error instanceof ApiError && error.status === 0) {
    setError('ติดต่อเซิร์ฟเวอร์ไม่ได้ — ตรวจว่าเปิด API ที่พอร์ต 3001 แล้วหรือยัง');
  } else {
    setError(error.message);
  }
}
⚠ อย่าแสดงข้อความเทคนิคให้ผู้ใช้เห็น TypeError: Failed to fetch ไม่มีความหมายกับผู้ใช้ทั่วไป
แปลเป็นภาษาคนที่บอกว่าควรทำอะไรต่อ — นี่คือเหตุผลที่เราสร้าง ApiError พร้อมข้อความไทยไว้ใน apiClient

✕ ไม่ควรได้
  • หน้าขาว
  • Failed to fetch
  • หมุนค้างไปเรื่อย ๆ
✓ ต้องได้
  • "ติดต่อเซิร์ฟเวอร์ไม่ได้…"
  • บอกว่าควรทำอะไรต่อ
  • มีปุ่มลองใหม่
แล้วเปิด API กลับ กดปุ่มลองใหม่ → ข้อมูลกลับมา โดยไม่ต้อง refresh ทั้งหน้า
สิ่งที่จะเห็นชัดขึ้นเมื่อเรียกข้ามเครื่อง "ตอน Week 05 เราใส่ ignore guard ไว้กัน stale update แต่เห็นผลยากเพราะข้อมูลมาเร็วมาก
ตอนนี้เรียก API ข้ามเครื่อง ความช้าเป็นเรื่องจริง — ลองกดสลับหน้าเร็ว ๆ ระหว่างที่ข้อมูลยังโหลดไม่เสร็จ จะเห็นประโยชน์ของ guard ทันที"

"และเราเตรียมทางไว้แล้วด้วย — เปิดไฟล์ services/requestService.js ฝั่ง API ดูสิครับ ไม่มีคำว่า req หรือ res เลยสักคำ"

"แปลว่าหน่วยหน้าที่เราเปลี่ยนไปใช้ database จะแก้แค่ service ไฟล์เดียว · controller และ route ไม่ต้องแตะเลย"

"เหมือนที่วันนี้เราแก้แค่ requestService ฝั่ง React แล้ว component ไม่ต้องแก้ — หลักการเดียวกันเป๊ะ แค่คนละฝั่ง"
