## 2. ภาพรวมระบบ

> เขียน 2–4 ประโยคว่าระบบนี้ทำอะไร ใครใช้ และแก้ปัญหาอะไร
> **เขียนด้วยภาษาที่คนไม่ใช่โปรแกรมเมอร์ก็อ่านรู้เรื่อง** เพราะ contract มักถูกส่งให้ลูกค้าหรือหัวหน้าทีมอ่านด้วย

✅ *ตัวอย่าง*

ระบบรับคำร้องขอใช้บริการภายในมหาวิทยาลัย ให้นักศึกษาและบุคลากรแจ้งปัญหาหรือขอใช้อุปกรณ์ผ่านเว็บได้ เจ้าหน้าที่ดูรายการคำร้องทั้งหมด ปรับสถานะการดำเนินการ และปิดงานเมื่อเสร็จสิ้น

API นี้เป็นส่วนหลังบ้านที่ให้บริการข้อมูลแก่เว็บแอปพลิเคชัน (React) โดยแยกจากส่วนแสดงผลอย่างสมบูรณ์

## 3. โครงสร้างข้อมูลหลัก

> ระบุทุก field ที่ API รับหรือส่ง · บอกชนิด · บอกว่าจำเป็นไหม · บอกข้อจำกัด
> **ข้อจำกัดสำคัญมาก** — ถ้าไม่เขียนว่า "ชื่ออย่างน้อย 2 ตัวอักษร" ฝั่ง front-end จะไม่รู้ว่าต้องตรวจอะไรก่อนส่ง

### Request (คำร้อง)

| Field | ชนิด | จำเป็น | ข้อจำกัด | ตัวอย่าง |
|---|---|:---:|---|---|
| `id` | string | — | เซิร์ฟเวอร์สร้างให้ · ขึ้นต้นด้วย `REQ-` | `"REQ-001"` |
| `requesterName` | string | ✓ | อย่างน้อย 2 ตัวอักษร | `"สมชาย ใจดี"` |
| `requestType` | string | ✓ | 1 ใน 4 ค่าที่กำหนด (ดูด้านล่าง) | `"แจ้งซ่อม"` |
| `location` | string | ✓ | ห้ามว่าง | `"ห้องปฏิบัติการ 301"` |
| `details` | string | ✓ | อย่างน้อย 10 ตัวอักษร | `"เครื่องปรับอากาศไม่ทำงาน"` |
| `priority` | string | ✓ | `"normal"` หรือ `"urgent"` | `"urgent"` |
| `status` | string | — | เซิร์ฟเวอร์กำหนด · เริ่มต้นเป็น `"pending"` | `"pending"` |

**ค่าที่ยอมรับของ `requestType`**

`แจ้งซ่อม` · `บริการบัญชีผู้ใช้` · `ขอใช้อุปกรณ์` · `อื่น ๆ`

**ค่าที่ยอมรับของ `status`**

| ค่า | ความหมาย | ใครเปลี่ยนได้ |
|---|---|---|
| `pending` | รอดำเนินการ (ค่าเริ่มต้นเมื่อสร้าง) | ระบบตั้งให้อัตโนมัติ |
| `in-progress` | กำลังดำเนินการ | เจ้าหน้าที่ |
| `completed` | เสร็จสิ้น | เจ้าหน้าที่ |

## 4. สรุป Endpoint ทั้งหมด

> ตารางนี้คือ**หน้าสารบัญ** ให้คนกวาดตาดูครั้งเดียวรู้ว่า API ทำอะไรได้บ้าง
> รายละเอียดของแต่ละเส้นอยู่ในหัวข้อถัดไป

| # | Method | Endpoint | ทำอะไร | สำเร็จ | ผิดพลาดที่เป็นไปได้ |
|---|---|---|---|---|---|
| 1 | `GET` | `/api/requests` | ดูคำร้องทั้งหมด | `200` | — |
| 2 | `GET` | `/api/requests?status=` | กรองตามสถานะ | `200` | — |
| 3 | `GET` | `/api/requests/:id` | ดูคำร้องรายการเดียว | `200` | `404` |
| 4 | `POST` | `/api/requests` | สร้างคำร้องใหม่ | `201` | `400` |
| 5 | `PUT` | `/api/requests/:id` | เปลี่ยนสถานะคำร้อง | `200` | `400` · `404` |
| 6 | `DELETE` | `/api/requests/:id` | ลบคำร้อง | `204` | `404` |

## 5. รายละเอียดแต่ละ Endpoint

> **รูปแบบที่ใช้กับทุกเส้น** — ทำอะไร · รับอะไร · คืนอะไรเมื่อสำเร็จ · คืนอะไรเมื่อผิดพลาด
> ใส่**ตัวอย่างจริงเสมอ** เพราะคนอ่านตัวอย่างเข้าใจเร็วกว่าอ่านคำอธิบาย

### 5.1 ✅ `GET /api/requests` — ดูคำร้องทั้งหมด

**ทำอะไร** คืนรายการคำร้องทั้งหมดในระบบ เรียงตามลำดับที่สร้าง

**Query parameters**

| ชื่อ | จำเป็น | ค่าที่ใช้ได้ | ทำอะไร |
|---|:---:|---|---|
| `status` | — | `pending` · `in-progress` · `completed` | กรองเฉพาะสถานะที่ระบุ |

**ตัวอย่างคำขอ**

```http
GET /api/requests?status=pending HTTP/1.1
Host: localhost:3001
```

**ตอบกลับเมื่อสำเร็จ — `200 OK`**

```json
[
  {
    "id": "REQ-001",
    "requesterName": "สมชาย ใจดี",
    "requestType": "แจ้งซ่อม",
    "location": "ห้องปฏิบัติการ 301",
    "details": "เครื่องปรับอากาศไม่ทำงานตั้งแต่เช้า",
    "priority": "urgent",
    "status": "pending"
  }
]
```

> **หมายเหตุ** ถ้าไม่มีคำร้องเลย จะคืน array ว่าง `[]` พร้อม status `200` — **ไม่ใช่ `404`**
> เพราะ "ไม่มีข้อมูล" ไม่ใช่ "ไม่พบทรัพยากร" · ฝั่ง front-end ต้องแยกสองกรณีนี้ให้ออก

---

### 5.2 ✅ `GET /api/requests/:id` — ดูคำร้องรายการเดียว

**ทำอะไร** คืนคำร้องที่ตรงกับรหัสที่ระบุ

**Path parameters**

| ชื่อ | ชนิด | ตัวอย่าง |
|---|---|---|
| `id` | string | `REQ-001` |

**ตอบกลับเมื่อสำเร็จ — `200 OK`**

```json
{
  "id": "REQ-001",
  "requesterName": "สมชาย ใจดี",
  "requestType": "แจ้งซ่อม",
  "location": "ห้องปฏิบัติการ 301",
  "details": "เครื่องปรับอากาศไม่ทำงานตั้งแต่เช้า",
  "priority": "urgent",
  "status": "pending"
}
```

**ตอบกลับเมื่อไม่พบ — `404 Not Found`**

```json
{ "error": "ไม่พบคำร้องรหัส REQ-999" }
```

---

### 5.3 ✅ `POST /api/requests` — สร้างคำร้องใหม่

**ทำอะไร** สร้างคำร้องใหม่ · เซิร์ฟเวอร์จะสร้าง `id` และตั้ง `status` เป็น `pending` ให้เอง

**Request body**

```json
{
  "requesterName": "สุภาวดี รักเรียน",
  "requestType": "ขอใช้อุปกรณ์",
  "location": "ห้องประชุม 2",
  "details": "ขอยืมโปรเจกเตอร์สำหรับนำเสนอ",
  "priority": "normal"
}
```

> **สังเกต** ไม่ต้องส่ง `id` และ `status` มา — ถ้าส่งมาเซิร์ฟเวอร์จะไม่สนใจ
> นี่เป็นข้อตกลงสำคัญ เพราะถ้า client กำหนด id เองได้จะเกิดรหัสซ้ำ

**ตอบกลับเมื่อสำเร็จ — `201 Created`**

```json
{
  "id": "REQ-MTYOA3MX-YEX9",
  "requesterName": "สุภาวดี รักเรียน",
  "requestType": "ขอใช้อุปกรณ์",
  "location": "ห้องประชุม 2",
  "details": "ขอยืมโปรเจกเตอร์สำหรับนำเสนอ",
  "priority": "normal",
  "status": "pending"
}
```

> **ทำไมต้องคืนข้อมูลที่สร้างกลับไปด้วย** — เพราะ client ต้องรู้ `id` ที่เซิร์ฟเวอร์สร้างให้
> ถ้าคืนแค่ `201` เปล่า ๆ client จะต้องยิง `GET` ซ้ำอีกรอบเพื่อหาว่าของที่เพิ่งสร้างคืออันไหน

**ตอบกลับเมื่อข้อมูลไม่ถูกต้อง — `400 Bad Request`**

```json
{
  "error": "ข้อมูลคำร้องไม่ถูกต้อง",
  "details": [
    "ชื่อผู้แจ้งต้องมีอย่างน้อย 2 ตัวอักษร",
    "รายละเอียดต้องมีอย่างน้อย 10 ตัวอักษร"
  ]
}
```

> **`details` เป็น array เสมอ** แม้จะผิดข้อเดียว — เพื่อให้ฝั่ง front-end เขียนโค้ดจัดการแบบเดียวได้
> ถ้าบางครั้งเป็น string บางครั้งเป็น array คนใช้จะต้องเช็คชนิดทุกครั้ง

## 6. รูปแบบ Error มาตรฐาน

> ส่วนนี้สำคัญมากแต่คนมักลืม — **ถ้าไม่กำหนดรูปแบบ error ให้ตายตัว ฝั่ง front-end จะเขียนโค้ดจัดการไม่ได้**

ทุก error ตอบเป็น JSON ที่มี field `error` เสมอ

```json
{ "error": "ข้อความที่ผู้ใช้ทั่วไปอ่านเข้าใจ" }
```

กรณี validation จะมี `details` เพิ่มมาเป็น array บอกว่าผิดตรงไหนบ้าง

```json
{
  "error": "ข้อมูลคำร้องไม่ถูกต้อง",
  "details": ["ชื่อผู้แจ้งต้องมีอย่างน้อย 2 ตัวอักษร"]
}
```

### ตาราง Status Code ที่ใช้

| Status | ใช้เมื่อ | ฝั่งไหนผิด | ฝั่ง client ควรทำอะไร |
|---|---|---|---|
| `200` | สำเร็จ มีข้อมูลส่งกลับ | — | แสดงข้อมูล |
| `201` | สร้างสำเร็จ | — | แสดงรายการที่สร้าง |
| `204` | สำเร็จ ไม่มีข้อมูลส่งกลับ | — | อัปเดตหน้าจอ ไม่ต้อง parse body |
| `400` | ข้อมูลที่ส่งมาไม่ถูกต้อง | ผู้ใช้ | แสดงว่าผิดตรงไหน ให้แก้แล้วส่งใหม่ |
| `404` | ไม่พบทรัพยากรที่ขอ | ผู้ใช้ | แสดง "ไม่พบข้อมูล" |
| `500` | โค้ดเซิร์ฟเวอร์ผิดพลาด | เซิร์ฟเวอร์ | แสดง "เกิดข้อผิดพลาด ลองใหม่" |

> **ตอน production จะไม่ส่ง stack trace กลับไป** — เปิดเผยโครงสร้างภายในให้คนภายนอกเห็นไม่ได้
> เพราะ stack trace บอกโครงสร้างไฟล์ ชื่อตัวแปร และเวอร์ชัน library ที่ใช้ ซึ่งเป็นข้อมูลสำหรับหาช่องโหว่

## 7. CORS

> ถ้า API ถูกเรียกจากเบราว์เซอร์ **ต้องเขียนส่วนนี้เสมอ** ไม่งั้นคนเอาไปใช้จะงงว่าทำไมเรียกไม่ได้

API อนุญาตให้เรียกจาก origin ที่กำหนดใน `CORS_ORIGIN` เท่านั้น

```
Access-Control-Allow-Origin: http://localhost:5173
```

ถ้าเรียกจาก origin อื่น เบราว์เซอร์จะบล็อกก่อนที่โค้ดจะได้เห็น response

> ⚠ **CORS เป็นกลไกของเบราว์เซอร์เท่านั้น** — Postman และ `curl` ไม่ถูกบล็อก เพราะไม่ใช่เบราว์เซอร์
> จึงทดสอบด้วย Postman แล้วผ่าน ไม่ได้แปลว่าเรียกจากเว็บได้

## 8. Environment Variables

> บอกว่าต้องตั้งค่าอะไรบ้างถึงจะรันได้ — คนที่รับโปรเจกต์ต่อจะได้ไม่ต้องไล่อ่านโค้ด

### ฝั่ง API (`api/.env`)

| ตัวแปร | ค่าเริ่มต้น | คำอธิบาย |
|---|---|---|
| `PORT` | `3001` | พอร์ตที่ API รับคำขอ |
| `CORS_ORIGIN` | `http://localhost:5173` | origin ที่อนุญาตให้เรียก |
| `NODE_ENV` | `development` | `production` จะเปลี่ยนรูปแบบ log และซ่อน stack trace |

### ฝั่ง Frontend (`frontend/.env.local`)

| ตัวแปร | ค่าเริ่มต้น | คำอธิบาย |
|---|---|---|
| `VITE_API_BASE_URL` | `http://localhost:3001` | ที่อยู่ของ API |

> **ห้าม commit ไฟล์ `.env`** — ใช้ `.env.example` เป็นตัวอย่างแทน

## 9. วิธีรันระบบ

ต้องเปิด **2 terminal** พร้อมกัน

```bash
# Terminal 1 — API
cd api && npm install && cp .env.example .env && npm run dev
# → http://localhost:3001

# Terminal 2 — Frontend
cd frontend && npm install && cp .env.example .env.local && npm run dev
# → http://localhost:5173
```

**ลำดับสำคัญ** — เปิด API ก่อนเสมอ ไม่งั้น frontend จะขึ้นข้อความว่าติดต่อเซิร์ฟเวอร์ไม่ได้

> โดยเฉพาะการเปลี่ยนที่ทำให้ของเดิมใช้ไม่ได้ (breaking change) ต้องเน้นให้ชัด

| เวอร์ชัน | วันที่ | เปลี่ยนอะไร | Breaking? |
|---|---|---|:---:|
| 1.0.0 | `<วว/ดด/ปปปป>` | เวอร์ชันแรก — GET, POST, DELETE | — |
| 2.0.0 | `<วว/ดด/ปปปป>` | เพิ่ม `PUT /api/requests/:id` และ CORS | ไม่ |

## ✅ เช็คลิสต์ก่อนส่ง

> ไล่ดูทีละข้อ · ถ้าข้อไหนตอบว่า "ไม่" แปลว่ายังไม่เสร็จ

- [ ] ระบุ Base URL และรูปแบบข้อมูลครบ
- [ ] ตารางโครงสร้างข้อมูลมีครบทุก field พร้อม**ข้อจำกัด**
- [ ] มีครบทั้ง 6 endpoint
- [ ] ทุก endpoint มี**ตัวอย่าง request และ response จริง** (ไม่ใช่เดา)
- [ ] ทุก endpoint ระบุ**กรณีผิดพลาดครบทุกแบบ** ไม่ใช่เฉพาะกรณีสำเร็จ
- [ ] รูปแบบ error เหมือนกันทั้งระบบ
- [ ] มีตาราง status code พร้อมบอกว่า client ควรทำอะไร
- [ ] เขียนเรื่อง CORS และ environment variables
- [ ] มีวิธีรันระบบที่คนอื่นทำตามได้จริง
- [ ] มีประวัติการเปลี่ยนแปลง
- [ ] **ทุกตัวอย่างคัดลอกมาจากการยิงจริง ไม่ได้เดา**
- [ ] ลบคำอธิบายที่ขึ้นต้นด้วย `>` และช่อง `<...>` ออกหมดแล้ว

## 📌 หลักการที่ควรจำ

| หลักการ | เหตุผล |
|---|---|
| **เขียนให้คนอ่าน ไม่ใช่เครื่องอ่าน** | contract ถูกส่งให้ลูกค้าและหัวหน้าทีมอ่านด้วย |
| **ตัวอย่างจริงสำคัญกว่าคำอธิบายยาว ๆ** | คนอ่านตัวอย่างเข้าใจเร็วกว่าอ่านคำบรรยาย |
| **ต้องมีกรณีผิดพลาดเสมอ** | ฝั่ง client ต้องเขียนโค้ดรับมือ ไม่ใช่แค่ทางที่สำเร็จ |
| **รูปแบบ error ต้องเหมือนกันทั้งระบบ** | ไม่งั้น client ต้องเขียนโค้ดจัดการหลายแบบ |
| **แก้ contract ต้องบันทึกทุกครั้ง** | คนที่เขียนตามเวอร์ชันเก่าจะพังโดยไม่รู้ตัว |
| **contract มาก่อนโค้ด** | ตกลงกันก่อนแล้วสองฝั่งทำงานคู่ขนานได้ ไม่ต้องรอกัน |
