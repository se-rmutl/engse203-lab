บทที่ 1 · กลุ่มที่ 1

ภาพรวม Full-Stack — 3 ชั้นคุยกันครบวงจร

เวลาอ่าน ≈ 9 นาที

ตลอด 3 สัปดาห์เราต่อทีละชั้น — สัปดาห์นี้ถอยมามองทั้งระบบพร้อมกันว่าข้อมูลเดินทางอย่างไร

🟩 ทายก่อนอ่านต่อ

ระบบนี้รันได้ดีบนเครื่องเราตอน dev — แต่ถ้าเอาไปรันบนเครื่องคนอื่น (หรือ cloud) จะเจอปัญหาอะไรบ้าง

เฉลย

ปัญหาที่พบบ่อย —

  • พอร์ตชนกัน — เครื่องอื่นอาจใช้ 3001 อยู่แล้ว · เราจึง hardcode พอร์ตไม่ได้
  • ที่อยู่ frontend ต่างกัน — CORS origin บนเครื่องเราคือ localhost แต่บน cloud เป็นโดเมนจริง
  • path ของไฟล์ต่างกัน — เครื่องอื่นวางโปรเจกต์คนละที่
  • frontend ยังไม่ build — dev รัน 2 server แต่ production ต้อง build เป็นไฟล์ static

สัปดาห์นี้แก้ทั้งหมดนี้ทีละข้อ

สรุปบทที่ 1
  • ระบบมี 3 ชั้น — React (frontend) ↔ Express (API) ↔ SQLite (database)
  • request ไหลลง · response ไหลขึ้น · ทั้งหมดเกิดในเสี้ยววินาที
  • "รันได้บนเครื่องเรา" ยังไม่พอ — ต้องรันได้บนเครื่องคนอื่นด้วย
  • งานสัปดาห์นี้ — แก้สิ่งที่ทำให้ระบบไปรันที่อื่นไม่ได้

บทที่ 2 · กลุ่มที่ 1

รันระบบครบวงจร — เปิด 3 ส่วนพร้อมกัน

เวลาอ่าน ≈ 9 นาที

ก่อนขัดให้สมบูรณ์ ต้องเปิดทั้งระบบให้ทำงานพร้อมกันก่อน (CP35)

2.1 ลำดับการเปิด — ล่างขึ้นบน

ลำดับเปิดอะไรคำสั่งทำไมลำดับนี้
①ฐานข้อมูลnpm run db:setupต้องมี campus.db ก่อน API เปิด
②APInpm run dev (ใน api/)frontend ต้องมี API ให้เรียก
③frontendnpm run dev (ใน frontend/)เปิดท้ายสุด
🟪 เทียบกับร้านอาหาร

ฐานข้อมูล = คลังวัตถุดิบ · API = ครัว · frontend = หน้าร้าน
ต้องมีวัตถุดิบก่อน ครัวถึงทำอาหารได้ · หน้าร้านถึงเปิดรับลูกค้าได้ — เปิดจากหลังไปหน้า

🟩 ทายก่อนอ่านต่อ

ถ้าเปิด frontend ก่อน API (สลับลำดับ) — จะเกิดอะไรขึ้นเมื่อ Dashboard พยายามโหลดข้อมูล

เฉลย

frontend เปิดได้ แต่ Dashboard จะแสดง error หรือว่างเปล่า เพราะยิง API ไปแล้วไม่มีใครรับ (connection refused)

พอเปิด API ทีหลังแล้วรีเฟรช ก็ใช้ได้ · แต่เปิดตามลำดับ (DB → API → frontend) จะไม่เจอปัญหานี้เลย

2.2 ต้องเปิด 2 terminal

dev รัน API กับ frontend เป็นคนละ process — จึงต้องมี 2 terminal เปิดค้างไว้

# terminal 1 — API
cd api && npm run dev
# → http://localhost:3001

# terminal 2 — frontend
cd frontend && npm run dev
# → http://localhost:5173
🟨 ทำไม dev ต้องแยก 2 server

Vite (ตัวรัน React) มี dev server ที่ โหลดหน้าใหม่อัตโนมัติเมื่อแก้โค้ด (hot reload) · แยกจาก API เพื่อให้แก้ frontend แล้วเห็นผลทันทีโดยไม่กระทบ API
แต่ตอน production เราจะรวมเป็น server เดียว — บทที่ 6 จะอธิบาย

2.3 ตรวจว่าทั้ง 3 ชั้นทำงาน

ตรวจอะไรทำอย่างไรต้องเห็น
ฐานข้อมูลมีไฟล์ campus.dbไฟล์อยู่จริง
APIcurl localhost:3001/api/requestsJSON 5 รายการ
frontendเปิด localhost:5173Dashboard แสดงข้อมูล
เชื่อมครบวงจรเพิ่มคำร้องจากหน้าเว็บข้อมูลบันทึกและแสดง
สรุปบทที่ 2
  • เปิดจากล่างขึ้นบน — ฐานข้อมูล → API → frontend
  • dev ต้อง 2 terminal เพราะ API กับ frontend เป็นคนละ process
  • Vite dev server มี hot reload — แก้โค้ดเห็นผลทันที
  • ตรวจครบวงจร — เพิ่มข้อมูลจากหน้าเว็บแล้วเห็นบันทึกจริง

บทที่ 3 · กลุ่มที่ 1

Environment Variable — แยก dev/production

เวลาอ่าน ≈ 11 นาที

Environment Variable

ค่าที่กำหนดจากภายนอกโค้ด — เปลี่ยนได้ตามเครื่องที่รัน โดยไม่ต้องแก้โค้ด · เก็บใน process.env

🟩 ทายก่อนอ่านต่อ

ถ้าเขียนพอร์ตตรง ๆ ในโค้ด app.listen(3001) แล้วเอาไป deploy บน cloud ที่กำหนดพอร์ตให้เอง — จะเกิดอะไรขึ้น

เฉลย

Cloud ส่วนใหญ่ (Render, Railway, Heroku) กำหนดพอร์ตให้ผ่าน process.env.PORT — ไม่ใช่ให้เราเลือก

ถ้า hardcode 3001 ระบบจะฟังผิดพอร์ต → cloud เข้าไม่ถึง → deploy ไม่สำเร็จ · ต้องอ่านจาก process.env.PORT ?? 3001

3.1 รวม config ไว้ที่เดียว

ปัญหาของการอ่าน process.env กระจายทั่วโค้ด — หายาก แก้ยาก ลืมง่าย · แก้ด้วยการรวมไว้ไฟล์เดียว

// config.js — อ่าน env ที่เดียว ที่อื่น import จากนี่
export const config = {
  env:        process.env.NODE_ENV ?? 'development',
  isProd:     process.env.NODE_ENV === 'production',
  port:       Number(process.env.PORT ?? 3001),
  corsOrigin: process.env.CORS_ORIGIN ?? 'http://localhost:5173',
  dbFile:     process.env.DB_FILE ?? '...',
};
🟩 ทำไมรวมที่เดียวดีกว่า

① เห็นทั้งหมดว่าระบบต้องการ env อะไรบ้าง — ในไฟล์เดียว
② มี ?? ค่า default ทุกตัว — ลืมตั้งก็ยังรันได้
③ ที่อื่นเขียน config.port — อ่านง่ายกว่า process.env.PORT กระจาย

3.2 NODE_ENV — ตัวแยก dev/production

developmentproduction
ตั้งค่าค่าเริ่มต้นNODE_ENV=production
loggingdev — สั้น อ่านง่ายcombined — ละเอียด เก็บ log
frontendรัน dev server แยกเสิร์ฟไฟล์ build
errorแสดงรายละเอียดเต็มซ่อนรายละเอียดภายใน
🟥 อย่า commit ไฟล์ .env

.env มักมีค่าลับ (รหัสผ่าน ฐานข้อมูล key) — ต้องอยู่ใน .gitignore
แทนที่ด้วย .env.example ที่มีแต่ชื่อตัวแปร ไม่มีค่าจริง — บอกคนอื่นว่าต้องตั้งอะไรบ้าง

🟨 เชื่อมกับ Week 07

เราใช้ process.env.PORT และ CORS_ORIGIN มาตั้งแต่ Week 07 แล้ว · สัปดาห์นี้แค่จัดระเบียบให้รวมที่เดียวและเพิ่ม NODE_ENV เข้ามาแยกสภาพแวดล้อม

สรุปบทที่ 3
  • Environment variable = ค่าที่กำหนดจากภายนอก เปลี่ยนตามเครื่องได้
  • รวม config ไว้ไฟล์เดียว — เห็นครบ มี default ครบ
  • NODE_ENV แยก dev/production — กระทบ logging, frontend, error
  • ห้าม commit .env — ใช้ .env.example แทน

บทที่ 4 · กลุ่มที่ 2

Health Check — ระบบบอกสถานะตัวเอง

เวลาอ่าน ≈ 10 นาที

Health Check

endpoint พิเศษที่บอกว่าระบบยังทำงานปกติไหม — โดยไม่ต้องเปิดหน้าเว็บดู · มักเป็น GET /api/health

4.1 ทำไมต้องมี

🟩 ทายก่อนอ่านต่อ

deploy ระบบขึ้น cloud แล้ว — cloud จะรู้ได้อย่างไรว่า deploy สำเร็จและระบบพร้อมรับผู้ใช้

เฉลย

Cloud เรียก health check endpoint อัตโนมัติ — ถ้าตอบ 200 แปลว่าพร้อม ถ้าไม่ตอบหรือตอบ error แปลว่ายังไม่พร้อม (จะไม่ส่งผู้ใช้เข้ามา)

โดยไม่มี health check cloud จะเดาว่าระบบพร้อมหรือไม่ไม่ได้ · และเราเองก็ต้องเปิดหน้าเว็บเช็คเอง ซึ่งไม่อัตโนมัติ

4.2 health check ที่ดีบอกอะไรบ้าง

// GET /api/health
{
  "status": "ok",              // ระบบพร้อมไหม
  "env": "production",       // สภาพแวดล้อมไหน
  "uptime": 3600,            // เปิดมากี่วินาที
  "database": {
    "connected": true,       // ต่อ DB ได้ไหม ← สำคัญสุด
    "driver": "sqlite",
    "tables": 3
  }
}
🟨 บรรทัด database.connected สำคัญที่สุด

API เปิดอยู่ไม่ได้แปลว่าระบบใช้ได้ — ถ้าต่อฐานข้อมูลไม่ได้ ระบบก็ทำงานจริงไม่ได้
health check ที่ดีจึงต้องเช็คถึงฐานข้อมูล ไม่ใช่แค่ตอบว่า "API เปิดอยู่"

4.3 status code ต้องสื่อความหมาย

สถานการณ์status fieldHTTP code
ทุกอย่างปกติ"ok"200
API เปิดแต่ต่อ DB ไม่ได้"degraded"503 Service Unavailable
🟥 อย่าตอบ 200 เสมอ

ถ้าต่อ DB ไม่ได้แต่ยังตอบ 200 — cloud จะคิดว่าระบบปกติแล้วส่งผู้ใช้เข้ามา · ผู้ใช้จะเจอ error
ตอบ 503 เมื่อระบบทำงานได้ไม่เต็มที่ เพื่อให้ cloud รู้ว่ายังไม่พร้อม

สรุปบทที่ 4
  • health check = endpoint ที่บอกว่าระบบพร้อมไหม โดยไม่ต้องเปิดหน้าเว็บ
  • cloud เรียกอัตโนมัติเพื่อเช็คว่า deploy สำเร็จ
  • ต้องเช็คถึงฐานข้อมูล ไม่ใช่แค่ว่า API เปิดอยู่
  • ตอบ 200 เมื่อปกติ · 503 เมื่อทำงานได้ไม่เต็มที่

Error Handling และ Logging ครบวงจร

เวลาอ่าน ≈ 10 นาที

ระบบที่พร้อมใช้จริงต้องจัดการเมื่อมีอะไรผิดพลาดได้ดี — ไม่ใช่แค่ทำงานตอนทุกอย่างถูก

5.1 error handling — เรามีแล้วตั้งแต่ Week 06

สัปดาห์นี้ไม่ได้เริ่มใหม่ — แค่ตรวจว่าครบวงจรจริง

มีไหมทำอะไรจาก
errorHandlerจับ error รวมศูนย์ ตอบ JSONWeek 06
notFoundroute ที่ไม่มี → 404Week 06
validationข้อมูลไม่ครบ → 400Week 06
constraint → statusDB ปฏิเสธ → 400 ไม่ใช่ 500Week 10
🟩 ทายก่อนอ่านต่อ

ตอน production ถ้าเกิด error ที่เราไม่ได้คาดไว้ (เช่น bug ในโค้ด) — ควรส่งรายละเอียด error เต็ม ๆ กลับไปให้ผู้ใช้ไหม

เฉลย

ไม่ควร — รายละเอียด error (stack trace, ชื่อไฟล์, query) บอกโครงสร้างภายในระบบ ซึ่งคนไม่หวังดีเอาไปหาช่องโหว่ได้

dev แสดงเต็มเพื่อ debug · production ตอบแค่ "เกิดข้อผิดพลาด" แล้วเก็บรายละเอียดไว้ใน logฝั่งเซิร์ฟเวอร์แทน

5.2 logging — dev ต่างจาก production

// app.js — morgan logging แยกตามสภาพแวดล้อม
app.use(morgan(config.isProd ? 'combined' : 'dev'));
รูปแบบหน้าตาใช้ตอน
devGET /api/requests 200 5ms (มีสี)development — อ่านเร็วตอน debug
combinedIP · เวลา · user-agent · ครบproduction — เก็บวิเคราะห์ทีหลัง
🟪 เทียบกับกล้องวงจรปิด

dev log = ดูสดหน้าจอ — เห็นสิ่งที่เกิดตอนนี้ เอาไว้ debug
production log = บันทึกเก็บไว้ — ย้อนดูได้ว่าเกิดอะไรตอนไหน ใครเข้ามา · จำเป็นตอนระบบมีปัญหาแล้วต้องสืบ

🟨 log ที่ดีช่วยตอนระบบพัง

ตอน dev เราเห็น error ทันทีบนจอ · แต่ production ระบบรันบน cloud เราไม่ได้นั่งดู
log คือสิ่งเดียวที่บอกได้ว่าเกิดอะไรขึ้นเมื่อผู้ใช้แจ้งว่าระบบมีปัญหา

สรุปบทที่ 5
  • error handling เรามีครบตั้งแต่ Week 06/10 — สัปดาห์นี้ตรวจว่าครบวงจร
  • production ไม่ส่งรายละเอียด error ให้ผู้ใช้ — เก็บใน log แทน
  • logging แยก dev (dev) / production (combined)
  • log คือสิ่งเดียวที่บอกได้ว่าเกิดอะไรตอนระบบรันบน cloud

บทที่ 6 · กลุ่มที่ 2

Production Build — dev ต่างจาก production

เวลาอ่าน ≈ 11 นาที

นี่คือความต่างที่ใหญ่ที่สุดระหว่าง "รันได้บนเครื่องเรา" กับ "พร้อมใช้จริง"

🟩 ทายก่อนอ่านต่อ

ทำไม production ต้องรวมเป็นพอร์ตเดียว — รัน 2 server แยกเหมือน dev ไม่ได้หรือ

เฉลย

ได้ แต่ยุ่งกว่าและมีปัญหา —

  • ต้องจ่ายค่า cloud 2 ที่ · ตั้งค่า 2 ที่
  • เจอปัญหา CORS ตลอด เพราะคนละโดเมน
  • dev server ของ Vite ไม่ได้ออกแบบมาให้รัน production — ช้าและไม่ปลอดภัย

build เป็น static แล้วให้ API เสิร์ฟ — ง่ายกว่า ถูกกว่า เร็วกว่า · เป็นวิธีมาตรฐาน

6.1 build frontend

cd frontend
npm run build
# → สร้างโฟลเดอร์ dist/ ที่มี HTML/JS/CSS พร้อมใช้
Build

แปลงโค้ด React (JSX หลายไฟล์) เป็น ไฟล์ static ที่เบราว์เซอร์เปิดได้ตรง ๆ — รวมไฟล์ ย่อขนาด ปรับให้เร็ว

6.2 ให้ API เสิร์ฟ static ตอน production

// app.js — เฉพาะตอน production
if (config.isProd && existsSync(config.staticDir)) {
  app.use(express.static(config.staticDir));      // เสิร์ฟ dist/
  app.get(/^\/(?!api).*/, (req, res) => {           // ทุก path ที่ไม่ใช่ /api
    res.sendFile(path.join(config.staticDir, 'index.html'));
  });
}
🟨 ทำไมต้อง /^\/(?!api).*/

React Router จัดการ path ฝั่ง frontend เอง (เช่น /about) · เราจึงต้องคืน index.html ให้ทุก path ยกเว้น /api ที่เป็นของ API จริง
ถ้าไม่แยก /api ออก จะคืนหน้าเว็บแทนข้อมูล API

🟥 อย่าลืม build ใหม่เมื่อแก้ frontend

production เสิร์ฟจาก dist/ ที่ build ไว้ — แก้โค้ด frontend แล้วไม่ build ใหม่ ผู้ใช้จะเห็นของเก่า
ต่างจาก dev ที่ hot reload ให้อัตโนมัติ

สรุปบทที่ 6
  • dev = 2 server แยก (hot reload) · production = build static แล้ว API เสิร์ฟพอร์ตเดียว
  • npm run build แปลง React เป็นไฟล์ static ใน dist/
  • API เสิร์ฟ dist/ + คืน index.html ทุก path ยกเว้น /api
  • แก้ frontend ต้อง build ใหม่ — production ไม่มี hot reload

บทที่ 7 · กลุ่มที่ 3 🏠 ทำที่บ้าน

Deploy — เอาระบบขึ้นให้คนอื่นใช้

เวลาอ่าน ≈ 10 นาที

Deploy

เอาระบบขึ้นไปรันบนเครื่องที่เข้าถึงได้จากอินเทอร์เน็ต — เพื่อให้คนอื่นใช้ได้ ไม่ใช่แค่บนเครื่องเรา

7.1 ก้าวแรก — จำลอง production ในเครื่องเรา

ก่อนขึ้น cloud จริง เราจำลองสิ่งที่ cloud จะทำ ในเครื่องเราเองได้ — เข้าใจ production เต็มที่โดยไม่ต้องสมัครอะไร

🟪 เทียบกับซ้อมก่อนแสดงจริง

จำลอง production ในเครื่อง = ซ้อมใหญ่ — ทำทุกอย่างเหมือนงานจริงแต่ยังอยู่ในห้องซ้อม · deploy ขึ้น cloud = แสดงจริงต่อหน้าคนดู
ถ้าซ้อมผ่าน โอกาสแสดงจริงผ่านก็สูง

# ① build frontend เป็น static
cd frontend && npm run build

# ② รัน API แบบ production — เสิร์ฟ frontend ที่ build แล้ว
cd ../api && NODE_ENV=production npm start
# เปิด http://localhost:3001 ได้ทั้งเว็บและ API จากพอร์ตเดียว
🟩 นี่คือสิ่งที่ cloud จะทำให้อัตโนมัติ

cloud รับโค้ดเรา → รัน 2 คำสั่งข้างบนนี้ให้ → เปิดพอร์ตให้คนทั้งโลกเข้าถึง
เราทำ 2 ขั้นแรกเองได้ในเครื่อง — เข้าใจ production โดยไม่ต้องพึ่ง cloud · คาบนี้ทุกคนทำแค่นี้ (CP43)

🟨 deploy จริงขึ้น cloud เป็น Challenge (ไม่บังคับ)

นักศึกษาส่วนใหญ่ยังไม่เคยใช้ cloud — เราจึงเข้าใจ production ให้แน่นในเครื่องก่อน · ใครอยากเห็นระบบตัวเองออนไลน์จริงให้เพื่อนเปิดจากมือถือได้ ทำ Challenge ในคู่มือ Take-Home ที่มีคู่มือ Render จับมือทำทีละขั้น

7.2 ถ้าจะขึ้น cloud จริง — cloud ทำอะไรให้

ส่วนนี้อ่านเพื่อเข้าใจภาพ ว่า cloud ทำงานอย่างไร (ไม่ต้องลงมือ)

7.1 สิ่งที่ต้องมีก่อน deploy

ฐานข้อมูล SQLite เป็นไฟล์ในเครื่อง — เมื่อ deploy บน cloud ที่ restart บ่อย จะเกิดปัญหาอะไร

เฉลย

cloud หลายเจ้าล้างไฟล์ทุกครั้งที่ restart/deploy ใหม่ (ephemeral filesystem) — ข้อมูลใน campus.db จะหาย

ทางแก้ — ① ใช้ persistent disk (cloud บางเจ้ามีให้) · ② ย้ายไปฐานข้อมูลที่แยกต่างหาก (เช่น MongoDB Atlas หรือ PostgreSQL cloud) · ซึ่งเป็นเหตุผลหนึ่งที่โลกจริงมักใช้ฐานข้อมูลแยกเครื่อง — โยงกับบทอ่านเพิ่มเติมถัดไป

8.1 SQL เทียบกับ NoSQL

8.2 ทำไมวิชานี้เลือก SQLite

ข้อมูลเรา (users, requests) มีโครงชัดและมีความสัมพันธ์กัน — คำร้องชี้ไปหาผู้ใช้ด้วย foreign key

ลักษณะข้อมูลเราSQL ตอบโจทย์เพราะ
โครงชัด (ทุกคำร้องมี field เดียวกัน)schema บังคับโครงได้

8.3 async — เมื่อฐานข้อมูลอยู่คนละเครื่อง

เราใช้ SQLite แบบ sync มาตลอด เพราะไฟล์อยู่ในเครื่องเดียวกัน อ่านเสร็จทันที

🟩 ทายก่อนอ่านต่อ

ถ้าเปลี่ยนจาก SQLite เป็น MongoDB จริง — จะกระทบชั้นไหนบ้าง (นึกถึง 4 ครั้งที่ผ่านมาที่แก้ชั้นเดียว)

เฉลย
ชั้นกระทบไหม
frontend❌ ไม่ — ยังเรียก API เดิม
service✅ เขียนใหม่ให้ใช้ MongoDB
controller⚠ กระทบ — ต้องเติม await เพราะ service เป็น async

ต่างจาก 4 ครั้งก่อนที่แก้ชั้นเดียว — เพราะครั้งนี้เปลี่ยน sync→async ซึ่งเป็นการเปลี่ยน "สัญญา" ของ service จึงกระทบผู้เรียก (controller)

นี่คือบทเรียนสำคัญ — การแยกชั้นช่วยได้มาก แต่การเปลี่ยนสัญญาของชั้น (sync/async) ยังกระทบผู้เรียกเสมอ
