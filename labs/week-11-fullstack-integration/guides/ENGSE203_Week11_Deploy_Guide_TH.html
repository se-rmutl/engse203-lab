ส่วนที่ 1

ภาพรวม — dev · production · cloud ต่างกันอย่างไร

🟨 Render ทำอะไรแทนเรา

Render สร้างเครื่อง Linux ให้ → ดึงโค้ดจาก GitHub → รัน Build Command → รัน Start Command → ตรวจ health check → เปิด URL ให้
เราไม่ต้องติดตั้ง Ubuntu · ไม่ต้องตั้ง Nginx · ไม่ต้องจัดการ HTTPS — ซึ่งเป็นเหตุผลที่เหมาะกับคนที่ยังไม่เคยใช้ cloud

ส่วนที่ 2

ระบบทำงานอย่างไรตอน production (พอร์ตเดียว)

เมื่อผู้ใช้เปิด URL · Express เป็นคนตัดสินว่าแต่ละคำขอจะได้ หน้าเว็บ หรือ ข้อมูล JSON

// api/src/app.js — ลำดับสำคัญ: API ก่อน แล้วค่อยหน้าเว็บ
app.get('/api', ...);                        // ข้อความต้อนรับย้ายมาอยู่ใต้ /api
app.use('/api/health', healthRoutes);
app.use('/api/requests', requestRoutes);

if (config.isProd && existsSync(config.staticDir)) {
  app.use(express.static(config.staticDir));    // ① ไฟล์ใน dist/
  app.get(/^\/(?!api).*/, (req, res) =>          // ② ทุก path ที่ไม่ใช่ /api
    res.sendFile(path.join(config.staticDir, 'index.html')));
} else {
  app.get('/', ...);                             // dev เท่านั้น — บอกว่าหน้าเว็บอยู่พอร์ต 5173
}

ส่วนที่ 3

3 กับดักที่ "จำลองในเครื่องผ่าน แต่ขึ้น cloud แล้วพัง"

ทั้ง 3 ข้อนี้ เจอจริงตอนตรวจงานชุดนี้ — และ checker สัปดาห์ 11 ตรวจให้แล้วทุกข้อ

กับดัก ① — bundle ฝัง localhost:3001

# frontend/.env.production — ใช้ตอน npm run build เท่านั้น · commit ได้ (ไม่มีค่าลับ)
VITE_API_BASE_URL=
🟨 ทำไมไม่แก้ที่ .env.local

Vite อ่าน .env.production ตอน build และให้ความสำคัญเหนือ .env.local · ตอน npm run dev ยังใช้ localhost:3001 ตามเดิม — dev ไม่พัง

กับดัก ② — หน้าแรก / ตอบ JSON

route app.get('/') ที่ตอบ {"message":"Campus Service API is running"} มีมาตั้งแต่ Week 06 · Express ตรวจ route ตามลำดับ — ตัวแรกที่ตรงชนะ จึงชิงหน้าแรกไปก่อน static

แก้ — ย้ายข้อความต้อนรับไปไว้ที่ /api และให้ / ตอบ JSON เฉพาะตอน dev (ดูโค้ดในส่วนที่ 2)

กับดัก ③ — vite: not found ตอน build บน cloud

Render ตั้ง NODE_ENV=production ไว้ตั้งแต่ขั้น build · npm install จึงข้าม devDependencies — แต่ Vite เป็น devDependency

// package.json ระดับบนสุด
"build": "npm install --include=dev --prefix frontend && npm run build --prefix frontend && npm install --prefix api"
🟥 ทำไมกับดักทั้ง 3 ข้อนี้หายาก

ทั้ง 3 ข้อไม่แสดงอาการตอนรัน npm run dev และส่วนใหญ่ไม่แสดงอาการแม้จำลอง production ที่พอร์ต 3001 · ส่วนที่ 5 จึงให้จำลองแบบ "เข้มงวด" — clone ใหม่ · NODE_ENV=production ตั้งแต่ build · ใช้พอร์ต 10000

🟥 ทำไมต้อง clone แยก

build ในโหมด production จะลบ devDependencies ของ api (เช่น vitest) · ถ้าซ้อมในโฟลเดอร์งานจริง ให้รัน npm install --prefix api หลังซ้อมเสร็จเพื่อคืนเครื่องมือทดสอบ

🟨 Windows (PowerShell)

ตรวจ 5 จุด (เปิดอีก terminal)

curl -s http://localhost:10000/api/health          # "status":"ok" · "env":"production"

grep -l "localhost:3001" frontend/dist/assets/*.js  # ต้องไม่มีผลลัพธ์

ขั้นที่ 5 — Health Check Path

เปิด Advanced → Health Check Path ใส่ /api/health → กด Deploy Web Service

ทางเลือก: ใช้ Blueprint (render.yaml) แทนการกรอกฟอร์ม

ไฟล์ render.yaml ในโปรเจกต์บันทึกค่าทั้งหมดข้างบนไว้แล้ว · Render ค้นหาไฟล์นี้ที่ root ของ repository — จึงต้องย้าย (หรือคัดลอก) ไปไว้ที่ root ของ Student Repository ก่อน แล้วใช้ New → Blueprint

services:
  - type: web
    name: campus-service
    runtime: node
    plan: free
    region: singapore
    rootDir: labs/week-11/source
    buildCommand: npm install && npm run build
    startCommand: npm start
    healthCheckPath: /api/health
    envVars:
      - key: NODE_ENV
        value: production
      - key: NODE_VERSION
        value: "22"

สำหรับมือใหม่แนะนำกรอกฟอร์มมากกว่า — เห็นทุกช่อง เข้าใจว่าแต่ละค่าทำอะไร

ส่วนที่ 11 · Challenge ⭐⭐

ข้อมูลถาวรด้วย Turso

ส่วนที่ 9 แสดงว่าบน free tier ไฟล์ campus.db จะกลับเป็นเวอร์ชันใน git ทุกครั้งที่ restart · ทางแก้ของระบบจริงคือย้ายฐานข้อมูลไปไว้คนละเครื่องกับ API — Turso เป็นบริการฐานข้อมูลที่ใช้ SQLite จึงใช้ schema และ query เดิมได้ทั้งหมด

11.1 ต้องแก้อะไร — service ไฟล์เดียว

// api/src/services/requestService.js — เลือกฐานข้อมูลจาก env (แนวคิดเดียวกับบทที่ 3)
async function openDatabase() {
  const url = process.env.TURSO_DATABASE_URL;
  if (url) {
    const { default: Database } = await import('libsql');   // npm install libsql --prefix api
    driver = 'turso';
    return new Database(url, { authToken: process.env.TURSO_AUTH_TOKEN });
  }
  driver = 'sqlite';
  return new DatabaseSync(DB_FILE);
}

export async function loadSeed() {
  db = await openDatabase();    // ← บรรทัดเดียวที่เปลี่ยนใน loadSeed
  ...
}
🟨 ทำไมแก้แค่ service

libsql มี prepare().all() · .get() · .run() แบบ sync หน้าตาเดียวกับ node:sqlite · query ทุกตัวใช้ต่อได้ และ controller ไม่ต้องเติม await — ต่างจาก MongoDB ที่เป็น async จึงกระทบ controller ด้วย (บทที่ 8)

11.2 ข้อควรระวัง 4 ข้อ (จากการทดลองทำจริงของผู้ช่วยสอน)

#ข้อควรระวังถ้าพลาด
①script build ต้องมี npm install --prefix api และ libsql ต้องอยู่ใน dependencies ของ api — Render จึงติดตั้งให้ก่อน npm startCannot find package 'libsql'
②ใช้ await import('libsql') ในฟังก์ชัน ไม่ใช่ import บนหัวไฟล์ — เครื่องที่ไม่มี libsql, checker และ npm test ยังใช้ node:sqlite ได้ทุกเครื่องที่ไม่มี libsql เปิด API ไม่ได้
③ใช้แพ็กเกจ libsql (sync) ไม่ใช่ @libsql/client (async) ที่เอกสาร Turso มักแนะนำservice + controller ต้องเป็น async ทั้งชุด
④URL และ token อยู่ได้แค่ api/.env (ใน .gitignore) และ Environment ของ Render · .env.example ต้องค่าว่างtoken หลุดขึ้น GitHub

11.4 ความปลอดภัยของ token

ทำห้ามทำ
เก็บใน api/.env (อยู่ใน .gitignore) และใน Environment ของ Renderใส่ในโค้ด · commit · แปะในแชทกลุ่ม
commit .env.example ที่มีแต่ชื่อตัวแปรค่าว่างใส่ URL หรือ token จริงใน .env.example · ใช้ token ของเพื่อน

ทดสอบกับ sqld (server แบบ open source ตัวเดียวกับที่ Turso ใช้) ผ่าน HTTP พร้อม auth token แบบ JWT: checker ทั้ง 3 ตัวผ่านครบบนฐานข้อมูลระยะไกล · จำลอง Render (build แบบ production) แล้ว redeploy บนเครื่องใหม่ ข้อมูลยังอยู่ · token ผิดหรือไม่ใส่ได้ 401 ตามตาราง 11.4
