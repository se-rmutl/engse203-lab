Environment Variable

ค่าที่กำหนดจากภายนอกโค้ด เปลี่ยนตามเครื่องได้ — หัวใจของการ deploy

🏫 เรียนและลงมือในห้อง≈ 11 นาที
บทที่ 3 / 9 · env config ลองคิด

hardcode port แล้ว deploy ไม่ได้

เขียน app.listen(3001) แล้ว deploy บน cloud ที่กำหนดพอร์ตให้เอง — เกิดอะไร

// config.js — อ่าน env ที่เดียว ที่อื่น import จากนี่
export const config = {
  env:        process.env.NODE_ENV ?? 'development',
  isProd:     process.env.NODE_ENV === 'production',
  port:       Number(process.env.PORT ?? 3001),
  corsOrigin: process.env.CORS_ORIGIN ?? 'http://localhost:5173',
};

รวม config ที่เดียว — ① เห็นครบว่าต้องการ env อะไร · ② มี ?? default ทุกตัว ลืมตั้งก็รันได้ · ③ ที่อื่นเขียน config.port อ่านง่าย

⚠ ห้าม commit .env — มักมีค่าลับ · ใช้ .env.example ที่มีแต่ชื่อตัวแปร ไม่มีค่าจริง

บทที่ 3 / 9 · env config ลองเล่น — กดสลับ dev/production

โค้ดเดิม ทำงานถูกทั้ง dev และ cloud

process.env ที่ตั้งไว้

config อ่านได้เป็น

สังเกต — โค้ดไม่เปลี่ยนเลย · dev ไม่ตั้ง env ก็ใช้ default (??) · cloud ตั้ง env มา config ก็อ่านค่าจริง · นี่คือเหตุผลที่ต้องอ่านจาก env ไม่ใช่ hardcode

บทที่ 3 / 9 · env config เห็นภาพ

.env → process.env → config → โค้ด

ค่าไหลทางเดียว — ตั้งที่ต้นทาง อ่านที่ปลายทาง · config.js เป็นจุดรวมที่มี default

  • รวม config ไฟล์เดียว — เห็นครบ มี default ครบ

ระบบบอกสถานะตัวเอง

// กดปุ่มด้านบนเพื่อดูว่า /api/health ตอบอะไร

บทที่ 4 / 9 · Health Check ลองคิด

ต่อ DB ไม่ได้ — health ควรตอบ code ไหน

API เปิดอยู่ แต่ต่อฐานข้อมูลไม่ได้ · health check ควรตอบ HTTP อะไร

ทำไม 503 ไม่ใช่ 200

Production Build

ความต่างที่ใหญ่ที่สุดระหว่าง "รันบนเครื่องเรา" กับ "พร้อมใช้จริง"

🏫 เรียนและลงมือในห้อง≈ 11 นาที
บทที่ 6 / 9 · Production Build เห็นภาพ

2 server แยก vs พอร์ตเดียว

DEVELOPMENT

React dev server (5173) + API (3001)
2 server แยก · hot reload
เหมาะกับตอนพัฒนา

PRODUCTION

build frontend เป็น static
API เสิร์ฟทั้งหมดพอร์ตเดียว
/ → เว็บ · /api → API

// app.js — เฉพาะ production
if (config.isProd && existsSync(config.staticDir)) {
  app.use(express.static(config.staticDir));
  app.get(/^\/(?!api).*/, (req,res) => res.sendFile(indexHtml));
}

/^\/(?!api).*/ — คืน index.html ทุก path ยกเว้น /api (React Router จัดการต่อ)
⚠ แก้ frontend ต้อง build ใหม่ — production ไม่มี hot reload

บทที่ 6 / 9 · Production Build ลองเล่น — กดดูว่าแต่ละ path ไปไหน

พอร์ตเดียว แต่แยก / กับ /api อย่างไร

กฎเดียว — path ขึ้นต้น /api เข้า API · ที่เหลือคืน index.html ให้ React Router จัดการ · นี่คือหน้าที่ของ /^\/(?!api).*/

บทที่ 6 / 9 · Production Build จำลองในเครื่องผ่าน — แต่ขึ้น cloud แล้วพัง

localhost คือเครื่องของ "คนที่เปิดเว็บ"

ทดสอบในเครื่องที่พอร์ต 3001 แล้วข้อมูลขึ้นครบ — ทำไมบน cloud ถึงว่าง

กับดักแก้
① bundle ฝัง localhost:3001frontend/.env.production → VITE_API_BASE_URL= (ว่าง)
② app.get('/') จาก Week 06 ชิงหน้าแรก → เห็น JSONย้ายข้อความต้อนรับไป /api · / ตอบ JSON เฉพาะ dev

บทที่ 7 / 9 · Deploy CP43 · ทุกคนทำ

จำลอง production ในเครื่อง — ก้าวแรกก่อน cloud

ยังไม่ต้องขึ้น cloud — จำลองสิ่งที่ cloud จะทำ ในเครื่องเราก่อน

เข้าใจ production เต็มที่โดยไม่ต้องสมัครอะไร · เหมือนซ้อมใหญ่ก่อนแสดงจริง

# ซ้อมให้เหมือน cloud — NODE_ENV=production ตั้งแต่ build · พอร์ตไม่ใช่ 3001
NODE_ENV=production npm run build
NODE_ENV=production PORT=10000 npm start
# เปิด http://localhost:10000 ได้ทั้งเว็บและ API

นี่คือสิ่งที่ cloud จะทำให้อัตโนมัติ
cloud รับโค้ด → รัน 2 คำสั่งนี้ → เปิดพอร์ตให้คนทั้งโลกเข้าถึง · เราทำเองในเครื่องได้ = เข้าใจ production จริง

deploy ขึ้น cloud จริงเป็น Challenge — ใครอยากเห็นระบบออนไลน์ให้เพื่อนเปิดจากมือถือ มีคู่มือ Render จับมือทำใน Take-Home

มีทางเลือกอื่น ต่างกันอย่างไร

SQL (SQLite) — ที่เราใช้

ตาราง/แถว · โครงตายตัว · มีความสัมพันธ์
เหมาะกับข้อมูลที่มีโครงชัด

NoSQL (MongoDB)

collection/document · ยืดหยุ่น
เหมาะกับข้อมูลไม่มีโครงตายตัว

ถ้าเปลี่ยนไป MongoDB จะกระทบชั้นไหน (นึกถึง 4 ครั้งที่แก้ชั้นเดียว)

บทเรียนสำคัญ — การแยกชั้นช่วยได้มาก แต่การเปลี่ยน "สัญญา" ของชั้น (sync→async) ยังกระทบผู้เรียกเสมอ · ครั้งนี้จึงกระทบ controller ด้วย ต่างจาก 4 ครั้งก่อน
