จากไฟล์ JSON สู่ฐานข้อมูล

Week 06 เราเก็บข้อมูลลงไฟล์ JSON แล้วมันก็ใช้ได้ — แล้วทำไมยังต้องมีฐานข้อมูลอีก

🏫 เรียนและลงมือในห้อง≈ 9 นาที
บทที่ 1 / 10 · ทำไมต้องมี DB ลองคิดก่อน

ถ้ามีคำร้อง 50,000 รายการในไฟล์เดียว

อยากดู "คำร้องที่ยังไม่เสร็จ" 3 รายการ — โปรแกรมต้องทำอะไร

ต่อให้คำตอบมีแค่ 3 รายการ ก็ต้องอ่านทั้งไฟล์อยู่ดี · และถ้ามีคนขอพร้อมกัน 10 คน ก็อ่านทั้งไฟล์ 10 รอบ

ไฟล์ JSON = สมุดจดเล่มเดียว — จดเร็ว แต่หาอะไรทีต้องพลิกทั้งเล่ม และสองคนเขียนพร้อมกันต้องแย่งสมุด
ฐานข้อมูล = ตู้เอกสารที่มีระบบ — มีดัชนี หลายคนหยิบพร้อมกันได้ และมีกฎว่าอะไรใส่ช่องไหนได้

บทที่ 1 / 10 · ทำไมต้องมี DB สิ่งที่ไฟล์ JSON ทำไม่ได้

ฐานข้อมูลให้อะไรเพิ่ม

ปัญหาของไฟล์ JSONฐานข้อมูลแก้ให้อย่างไร
ช้าเมื่อข้อมูลเยอะค้นเฉพาะที่ต้องการ ไม่ต้องอ่านทั้งหมด
เขียนพร้อมกันแล้วพังจัดการการเขียนพร้อมกันให้เอง
ไม่มีใครตรวจความถูกต้องบังคับกฎเอง (constraint)
ข้อมูลซ้ำและไม่ตรงกันเชื่อมข้อมูลข้ามตารางได้ (relationship)

SQLite — เก็บทั้งฐานไว้ในไฟล์เดียว ไม่ต้องติดตั้งเซิร์ฟเวอร์ · Node 22 มีมาให้แล้ว · commit ขึ้น git ได้ · ใช้ SQL มาตรฐานเหมือนฐานข้อมูลตัวใหญ่

02

ตาราง แถว คอลัมน์ และ Primary Key

ฐานข้อมูลเชิงสัมพันธ์เก็บข้อมูลเป็นตาราง — หน้าตาเหมือนที่คุณคุ้นเคย แต่มีกฎมากกว่า

🏫 เรียนและลงมือในห้อง≈ 10 นาที
บทที่ 2 / 10 · ตาราง & PK เห็นภาพรวมก่อนลงรายละเอียด

ฐานข้อมูลประกอบด้วยอะไรบ้าง

ฐานข้อมูล 1 ไฟล์ → หลายตาราง → แต่ละตารางมีคอลัมน์และแถว → จุดตัดคือค่าในช่อง

บทที่ 2 / 10 · ตาราง & PK เทียบกับสิ่งที่เคยใช้

ตาราง = array ของ object

ใน JavaScript (Week 06)ในฐานข้อมูล
array ของ objectตาราง (table)
object 1 ตัวแถว (row)
property ของ objectคอลัมน์ (column)

ความต่างที่สำคัญ — ใน JavaScript แต่ละ object มี property ไม่เหมือนกันก็ได้
แต่ในตาราง ทุกแถวต้องมีคอลัมน์เหมือนกันหมด · ถ้าแถวไหนไม่มีค่าจะเก็บเป็น NULL แต่ช่องนั้นยังมีอยู่

Primary Key — คอลัมน์ที่ใช้ระบุแถวได้ไม่ซ้ำกัน · ห้ามซ้ำ ห้ามเป็น NULL · ทุกตารางควรมี

บทที่ 2 / 10 · ตาราง & PK การตัดสินใจที่สำคัญ

เลือก Primary Key ให้ถูก

ตัวเลือกดีไหมเพราะอะไร
เลขที่ระบบสร้างให้ดีที่สุดไม่มีทางซ้ำ ไม่เปลี่ยน ไม่ต้องคิดเอง
รหัสที่ออกแบบเอง REQ-001ดีคนอ่านเข้าใจ ใช้อ้างอิงจริงได้
อีเมลพอได้ไม่ซ้ำจริง แต่ เปลี่ยนได้
ชื่อ-นามสกุลไม่ดีซ้ำได้ · เปลี่ยนได้ · สะกดผิดได้

โปรเจกต์ของเราใช้ทั้งสองแบบ
users.id เป็นตัวเลข เพราะผู้ใช้ไม่ต้องเห็น · requests.id เป็น REQ-001 เพราะผู้ใช้เห็นและใช้อ้างอิงจริง

หลักการ → เลือก PK ที่ ไม่เปลี่ยน · อย่าใช้สิ่งที่แก้ได้ — เดี๋ยวบทที่ 8 จะเห็นว่าทำไมสำคัญ
บทที่ 2 / 10 · ตาราง & PK เทียบกับของที่คุ้นเคย

จบบทที่ 2 — ตาราง & Primary Key

ชนิดข้อมูลและข้อกำหนด

ตอนสร้างตารางเราไม่ได้บอกแค่ว่ามีคอลัมน์อะไร แต่บอกด้วยว่าแต่ละคอลัมน์ยอมรับอะไรได้บ้าง

🏫 เรียนและลงมือในห้อง≈ 10 นาที
บทที่ 3 / 10 · ชนิด & constraint กฎที่ฐานข้อมูลบังคับเอง

Constraint — ด่านสุดท้ายที่ไม่มีใครข้ามได้

Constraintบังคับอะไรใช้ที่ไหน
PRIMARY KEYไม่ซ้ำ + ไม่เป็น NULLusers.id
NOT NULLต้องมีค่าเสมอlocation · details
UNIQUEห้ามซ้ำกับแถวอื่นusers.email
DEFAULTถ้าไม่ใส่ ใช้ค่านี้status = 'pending'
CHECKค่าต้องตรงเงื่อนไขstatus ต้องเป็น 1 ใน 3
FOREIGN KEYต้องมีอยู่จริงในอีกตารางrequester_id

เรามี validation ที่ API แล้วตั้งแต่ Week 06 — ทำไมยังต้องมี CHECK อีก

ข้อมูลอาจเข้ามาทาง — สคริปต์นำเข้า · คนแก้ด้วยมือ · ระบบอื่นที่มาเชื่อมทีหลัง · โค้ดที่เขียนผิดในอนาคต
validation ที่ API ให้ข้อความดี ๆ กับผู้ใช้ · constraint เป็นด่านสุดท้าย — ป้องกันสองชั้นดีกว่าชั้นเดียว

บทที่ 3 / 10 · ชนิด & constraint

จบบทที่ 3 — ชนิด & constraint

✓ สิ่งที่ต้องจำจากบทนี้

  • SQLite มี 4 ชนิดหลัก — TEXT · INTEGER · REAL · BLOB
  • constraint คือกฎที่ ฐานข้อมูลบังคับเอง ไม่ว่าข้อมูลจะเข้ามาทางไหน
  • มี validation ที่ API แล้วก็ยังควรมี constraint — ป้องกันสองชั้น
  • ต้องสั่ง PRAGMA foreign_keys = ON ไม่งั้น FK ไม่ทำงาน

// try.mjs — สนามซ้อม SQL แบบออฟไลน์
import { DatabaseSync } from 'node:sqlite';
const db = new DatabaseSync(':memory:');   // เก็บใน RAM ไม่สร้างไฟล์

db.exec(`
  CREATE TABLE requests (id TEXT, status TEXT, priority TEXT);
  INSERT INTO requests VALUES ('REQ-001','pending','urgent');
  INSERT INTO requests VALUES ('REQ-002','completed','normal');
`);

// เปลี่ยน SQL บรรทัดนี้แล้วรันใหม่ได้เรื่อย ๆ
console.table(db.prepare("SELECT * FROM requests WHERE status = 'pending'").all());

สลับลำดับไม่ได้

SELECT   คอลัมน์      -- เอาอะไร
FROM     ตาราง        -- จากไหน

ORDER BY priority DESC จะเรียง 'urgent' กับ 'normal' อย่างไร

ที่ได้ผลถูกเป็นความบังเอิญ — ถ้าวันหนึ่งเพิ่มระดับ 'critical' ที่ควรมาก่อน urgent จะเรียงผิดทันที เพราะ c มาก่อน n และ u

Foreign Key

คอลัมน์ที่ชี้ไปยังอีกตาราง และฐานข้อมูลจะตรวจให้ว่าสิ่งที่ชี้ไปมีอยู่จริง

🏫 เรียนและลงมือในห้อง≈ 10 นาที
บทที่ 8 / 10 · Foreign Key กลไกการทำงาน

ฐานข้อมูลตรวจให้ว่ามีอยู่จริง

CREATE TABLE requests (
  id            TEXT PRIMARY KEY,
  requester_id  INTEGER NOT NULL,
  ...
  FOREIGN KEY (requester_id) REFERENCES users(id)
);

อ่านว่า — "requester_id ต้องเป็นค่าที่มีอยู่ในคอลัมน์ id ของตาราง users"

ถ้าลองทำฐานข้อมูลจะ
ใส่คำร้องที่ requester_id = 999 (ไม่มีคนนี้)ปฏิเสธ — FOREIGN KEY constraint failed
ลบผู้ใช้ที่ยังมีคำร้องค้างอยู่ปฏิเสธ — ไม่ให้เกิดข้อมูลกำพร้า
ลบผู้ใช้ที่ไม่มีคำร้องเลยอนุญาต

⚠ SQLite ปิดการตรวจ FK ไว้เป็นค่าเริ่มต้น — ต้องสั่ง PRAGMA foreign_keys = ON; ทุกครั้งที่เปิดฐานข้อมูล ไม่งั้นคำสั่งที่ควรถูกปฏิเสธจะผ่านหมด และคุณจะไม่รู้เลยว่าข้อมูลเสียแล้ว

บทที่ 8 / 10 · Foreign Key ย้อนกลับไปบทที่ 2

ทำไมไม่ชี้ด้วยชื่อ จะได้อ่านง่าย

ทำไมไม่ให้ requests เก็บ requester_name แล้วชี้ไปที่ users.name

ถ้าสมชายเปลี่ยนชื่อ ค่าใน users.name เปลี่ยน แต่ requests.requester_name ยังเป็นชื่อเก่า — ความเชื่อมโยงขาด
แต่ users.id เป็นตัวเลขที่ไม่มีวันเปลี่ยน · เปลี่ยนชื่อกี่ครั้งก็ยังเป็นคนเดิม id เดิม

นี่คือเหตุผลที่บทที่ 2 บอกว่า → อย่าเลือกสิ่งที่แก้ได้มาเป็น Primary Key

FK อยู่ตารางไหน — ในความสัมพันธ์หนึ่งต่อหลาย FK อยู่ฝั่ง "หลาย" เสมอ
ถ้าให้ users เก็บ request_id จะเก็บได้แค่คำร้องเดียวต่อคน · แจ้ง 20 รายการต้องมี 20 คอลัมน์

บทที่ 8 / 10 · Foreign Key

จบบทที่ 8 — Foreign Key

✓ สิ่งที่ต้องจำจากบทนี้

  • FK ชี้ไปยัง Primary Key ของอีกตาราง · ฐานข้อมูลตรวจให้ว่ามีอยู่จริง
  • ป้องกันทั้งใส่ค่าที่ไม่มีจริง และลบข้อมูลที่ยังมีคนอ้างถึง
  • ต้องสั่ง PRAGMA foreign_keys = ON ทุกครั้งที่เปิดฐานข้อมูล
  • ชี้ด้วย id ที่ไม่เปลี่ยน · FK อยู่ฝั่ง "หลาย" เสมอ

JOIN — ดึงข้อมูลสองตารางมารวมกัน

เราแยกข้อมูลเพื่อไม่ให้ซ้ำ แต่เวลาใช้งานจริงต้องการเห็นพร้อมกัน

🏫 เรียนและลงมือในห้อง≈ 12 นาที
บทที่ 9 / 10 · JOIN อ่านทีละบรรทัด

JOIN ... ON — เชื่อมตรงไหน

SELECT r.id,
       u.name AS requesterName,
       r.status
FROM requests r
JOIN users u ON u.id = r.requester_id;
บรรทัดหมายความว่า
FROM requests rเริ่มจากตาราง requests · ตั้งชื่อย่อว่า r
JOIN users uเอาตาราง users มาต่อ · ตั้งชื่อย่อว่า u
ON u.id = r.requester_idเชื่อมตรงไหน — แถวที่ค่าตรงกัน

ชื่อย่อ (alias) จำเป็นเมื่อสองตารางมีคอลัมน์ชื่อเหมือนกัน — ทั้งสองตารางมี id · ถ้าไม่ระบุว่า r.id หรือ u.id ฐานข้อมูลจะไม่รู้ว่าหมายถึงอันไหน

⚠ ลืม ON — เขียน FROM requests, users เฉย ๆ จะได้ ทุกแถวจับคู่กับทุกแถว · 5 × 4 = 20 แถวที่ไม่มีความหมาย และไม่มี error บอก
ผลลัพธ์เยอะผิดปกติ → ตรวจ ON เป็นอันดับแรก

บทที่ 9 / 10 · JOIN ความต่างที่ต้องรู้

เลือกใช้ให้ถูก

แบบคืนอะไรใช้เมื่อ
JOINเฉพาะแถวที่จับคู่ได้ทั้งสองฝั่งต้องการเฉพาะคำร้องที่มีผู้แจ้งอยู่จริง
LEFT JOINทุกแถวจากตารางซ้าย แม้จับคู่ไม่ได้ต้องการผู้ใช้ทุกคน รวมคนที่ยังไม่เคยแจ้ง
-- ใครแจ้งกี่รายการ — คนที่ยังไม่เคยแจ้งต้องติดมาด้วย
SELECT u.name, COUNT(r.id) AS total
FROM users u
LEFT JOIN requests r ON r.requester_id = u.id
GROUP BY u.id
ORDER BY total DESC;

ถ้าใช้ JOIN ธรรมดา คนที่ยังไม่เคยแจ้งจะหายไปจากรายงาน — ซึ่งอาจเป็นข้อมูลที่เราอยากรู้ที่สุด

จบบทที่ 9 — JOIN

✓ สิ่งที่ต้องจำจากบทนี้

  • JOIN ... ON รวมสองตารางเป็นตารางเดียวชั่วคราว

  • ผลของ JOIN = รูปแบบที่ API ส่งให้ React — สะพานไปสัปดาห์หน้า

บทที่ 10 / 10 · พร้อมใช้จริง CP25

constraint ทำงานจริงไหม ต้องพิสูจน์

เขียน constraint ไว้ ไม่ได้แปลว่ามันทำงาน

ต้องลองทำผิดแล้วดูว่าถูกปฏิเสธจริงไหม — โดยเฉพาะ Foreign Key ที่ถ้าลืม PRAGMA จะเงียบไปเลย

ทดสอบต้องได้ error
ใส่คำร้องที่ requester_id ไม่มีจริงFOREIGN KEY constraint failed
ใส่ status นอกรายการCHECK constraint failed
ใส่อีเมลซ้ำUNIQUE constraint failed
ใส่คำร้องที่ id ซ้ำUNIQUE constraint failed
ไม่ระบุ locationNOT NULL constraint failed
