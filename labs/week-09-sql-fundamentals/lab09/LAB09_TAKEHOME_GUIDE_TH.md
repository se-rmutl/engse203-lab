# CP22 · เขียน queries.sql

**🏠 60 นาที · อย่างน้อย 8 ข้อ**

## กฎเหล็กของ checkpoint นี้

> **ทุก query ต้องรันจริงแล้วได้ผลลัพธ์ถูกต้อง**
>
> ห้ามเขียนจากความจำหรือเดาเอา · ผู้สอนจะสุ่มรัน 2–3 ข้อจากไฟล์ของคุณ

## โจทย์ 8 ข้อ

| ข้อ | เขียน query ที่ | ใช้อะไร |
|---|---|---|
| ① | คำร้องทั้งหมด เรียงตามรหัส | `ORDER BY` |
| ② | คำร้องที่ยังไม่ได้ดำเนินการ | `WHERE` |
| ③ | คำร้องเร่งด่วนที่ยังไม่เสร็จ | `WHERE` + `AND` |
| ④ | ค้นคำร้องจากคำบางส่วนในรายละเอียด | `LIKE` |
| ⑤ | คำร้องพร้อม**ชื่อผู้แจ้ง** | **`JOIN`** |
| ⑥ | คำร้องเฉพาะของภาควิชาหนึ่ง | `JOIN` + `WHERE` |
| ⑦ | รายชื่อผู้แจ้งที่ไม่ซ้ำกัน | `DISTINCT` |
| ⑧ | คำร้อง 3 รายการล่าสุด | `ORDER BY` + `LIMIT` |

## รูปแบบที่ต้องเขียน

```sql
-- ① คำร้องทั้งหมด เรียงตามรหัส
SELECT * FROM requests ORDER BY id;

-- ② คำร้องที่ยังไม่ได้ดำเนินการ
SELECT id, location, details FROM requests
WHERE status = 'pending'
ORDER BY id;
```

**ใส่คอมเมนต์บอกว่าข้อนั้นตอบโจทย์อะไร** — เพื่อให้คนอ่านรู้ว่าคุณตั้งใจทำอะไร

## เพิ่มข้อมูลให้พอทดสอบ

checker ต้องการ **คำร้องอย่างน้อย 8 รายการ** — ตอนจบคาบมี 5 · ให้เพิ่มอีกอย่างน้อย 3

```sql
INSERT INTO requests (id, requester_id, request_type, location, details, priority, status)
VALUES ('REQ-006', 2, 'แจ้งซ่อม', 'ห้องปฏิบัติการ 401', 'ไฟในห้องกะพริบตลอดเวลา', 'normal', 'pending');
```

> **เพิ่มข้อมูลที่หลากหลาย** — ให้มีทั้ง 3 สถานะ ทั้ง 2 ระดับความเร่งด่วน และกระจายหลายภาควิชา
> ไม่งั้น query บางข้อจะได้ผลลัพธ์ว่างเปล่าและทดสอบไม่ได้จริง

### ⚠ กับดักที่พบบ่อย

| ปัญหา | วิธีแก้ |
|---|---|
| query ได้ผลว่างเปล่า | ข้อมูลไม่พอ หรือเงื่อนไขสะกดผิด — ลอง `SELECT *` ดูก่อนว่ามีอะไรบ้าง |
| `LIKE` ไม่เจอ | ลืมใส่ `%` ทั้งสองข้าง |
| JOIN ได้ผลเยอะผิดปกติ | ลืม `ON` |

# CP23 · ทำ schema.sql ให้สมบูรณ์

**🏠 45 นาที**

## ทำไมต้องมีไฟล์นี้ ทั้งที่มี campus.db แล้ว

`campus.db` เป็น **ไฟล์ไบนารี** — เปิดอ่านด้วยตาไม่ได้ และ **git บอกไม่ได้ว่าเปลี่ยนอะไรไป**

`schema.sql` เป็นข้อความ จึงทำให้

| ข้อดี | ทำไมสำคัญ |
|---|---|
| **เห็นประวัติใน git** | ดูได้ว่าใครเพิ่มคอลัมน์ไหนเมื่อไร และเพราะอะไร |
| **คนอื่นสร้างเหมือนกันได้** | เพื่อนร่วมทีมรันไฟล์เดียวได้ฐานข้อมูลเหมือนกัน |
| **สร้างใหม่ได้ถ้าไฟล์เสีย** | ไม่ต้องเริ่มจากศูนย์ |

## โครงที่ต้องมี

```sql
PRAGMA foreign_keys = ON;

-- ① ลบของเดิมก่อน เพื่อให้รันซ้ำได้
DROP TABLE IF EXISTS requests;
DROP TABLE IF EXISTS users;

-- ② สร้างตาราง
CREATE TABLE users ( ... );
CREATE TABLE requests ( ... );

-- ③ ใส่ข้อมูลตั้งต้น
INSERT INTO users ... ;
INSERT INTO requests ... ;
```

## ⚠ ลำดับการลบสำคัญมาก

**ต้องลบ `requests` ก่อน `users` เสมอ**

เพราะ `requests` มี Foreign Key ชี้ไป `users` — ถ้าลบ `users` ก่อน จะเหลือคำร้องที่ชี้ไปหาตารางที่ไม่มีแล้ว

> **กฎง่าย ๆ — ลบฝั่งที่ "ชี้ไปหา" ก่อน แล้วค่อยลบฝั่งที่ "ถูกชี้"**

## ทดสอบว่ารันซ้ำได้จริง

**รันไฟล์เดิม 2 ครั้งติดกัน** — ครั้งที่สองต้องไม่ error

ถ้าครั้งที่สอง error ว่า `table users already exists` แปลว่าลืม `DROP TABLE IF EXISTS`

### ✓ ผ่าน CP23 เมื่อ

- [ ] `schema.sql` มี `CREATE TABLE` ทั้งสองตาราง
- [ ] มี `FOREIGN KEY` หรือ `REFERENCES`
- [ ] มี `DROP TABLE IF EXISTS` (รันซ้ำได้)
- [ ] มี `INSERT` ข้อมูลตั้งต้น
- [ ] **รันจริงแล้วสร้างฐานข้อมูลได้ และรันซ้ำได้ไม่ error**

# CP25 · ทดสอบ constraint

**🏠 30 นาที**

## ทำไมต้องทดสอบ

**เขียน constraint ไว้ไม่ได้แปลว่ามันทำงาน**

โดยเฉพาะ Foreign Key ที่ถ้าลืม `PRAGMA foreign_keys = ON` จะ **เงียบไปเลย** ไม่มี error บอกว่าไม่ได้ทำงาน

> เหมือนที่เราทำใน Week 06 — ทดสอบว่า API ตอบ **400 เมื่อข้อมูลไม่ครบ** ไม่ใช่แค่ทดสอบว่าตอบ 201 เมื่อข้อมูลถูก
>
> **ระบบที่ดีต้องปฏิเสธสิ่งที่ผิดได้ ไม่ใช่แค่รับสิ่งที่ถูก**

## 5 การทดสอบที่ต้องทำ

| # | ลองทำ | ต้องได้ error |
|---|---|---|
| ① | ใส่คำร้องที่ `requester_id = 99999` | `FOREIGN KEY constraint failed` |
| ② | ใส่ `status = 'ยกเลิก'` | `CHECK constraint failed` |
| ③ | ใส่อีเมลซ้ำกับคนที่มีอยู่ | `UNIQUE constraint failed` |
| ④ | ใส่คำร้องที่ `id` ซ้ำ | `UNIQUE constraint failed` |
| ⑤ | ใส่คำร้องโดยไม่ระบุ `location` | `NOT NULL constraint failed` |

# ⭐ Challenge — คะแนนเพิ่ม

## ① GROUP BY — สรุปข้อมูล

```sql
-- นับจำนวนคำร้องแยกตามสถานะ
SELECT status, COUNT(*) AS total
FROM requests
GROUP BY status
ORDER BY total DESC;
```

**`GROUP BY` รวมแถวที่มีค่าเหมือนกันเข้าด้วยกัน** แล้วใช้ฟังก์ชันรวม (`COUNT`, `SUM`, `AVG`) คำนวณจากกลุ่มนั้น

## ② LEFT JOIN — รวมคนที่ยังไม่เคยแจ้ง

```sql
SELECT u.name, u.department, COUNT(r.id) AS total
FROM users u
LEFT JOIN requests r ON r.requester_id = u.id
GROUP BY u.id
ORDER BY total DESC, u.name;
```

### ทำไมต้องใช้ LEFT JOIN

**ถ้าใช้ `JOIN` ธรรมดา คนที่ยังไม่เคยแจ้งจะหายไปจากรายงาน** — ซึ่งอาจเป็นข้อมูลที่เราอยากรู้ที่สุด

ลองเปลี่ยนเป็น `JOIN` ธรรมดาแล้วเทียบผลดู

## ③ CREATE INDEX — ให้ค้นเร็วขึ้น

```sql
CREATE INDEX IF NOT EXISTS idx_requests_status ON requests(status);
CREATE INDEX IF NOT EXISTS idx_requests_requester ON requests(requester_id);
```

**Index เหมือนดัชนีท้ายเล่มหนังสือ** — แทนที่จะพลิกทุกหน้า ก็เปิดดัชนีแล้วกระโดดไปหน้าที่ต้องการเลย

| | ข้อดี | ข้อเสีย |
|---|---|---|
| มี index | ค้นเร็วขึ้นมาก | เขียนข้อมูลช้าลงเล็กน้อย · ใช้พื้นที่เพิ่ม |

> **สร้าง index กับคอลัมน์ที่ใช้ค้นบ่อย** — `status` และ `requester_id` ถูกใช้ใน `WHERE` และ `JOIN` บ่อยที่สุด
